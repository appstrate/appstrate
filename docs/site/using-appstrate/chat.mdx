The **Chat** page of the dashboard is a conversational assistant built into Appstrate. You ask in plain words, and it uses the platform for you: it finds and launches your agents, reads their runs and files, connects accounts, and can even create agents. It acts with **your own permissions**, never more. It is the quickest way for someone who does not want to learn the interface to get work done.

The chat is a module (`@appstrate/module-chat`) that is part of the default `MODULES`, so it is there on a standard install. If an administrator removed it from `MODULES`, the Chat entry does not exist.

## What you need

- **A model.** The chat runs on one of your organization's models. An administrator adds them under **Settings → Organization → Models**. If you have several, choose one in the composer. Until you choose, the chat follows the organization's default model, so a change of that default reaches everyone who never picked one.
- **Access to the spaces used by the conversation.** Conversations belong to their author within an organization. Reading one requires chat read access in its origin space, if set, and in every space it has touched. Every built-in space role can read conversations, and the `admin`, `builder`, `operator` and `runner` roles can also write. The `viewer` role is read-only.

## Using it

Open **Chat** in the sidebar (under Activity) and type. Your conversations are listed on the left. A conversation can work across the spaces where you can act. When a request names no space, an inline run, a new agent or a direct integration call goes to your personal space first, and any other action to the space the conversation was opened in; if that space cannot do it, the assistant asks you instead of switching. Limit the conversation to its origin space to keep every turn there. Existing conversations from beta.68 start unrestricted. You can leave while the assistant is answering and read its saved response when you return. Deleting a conversation asks for confirmation, then deletes its messages and files, except a file that a run still uses. The address of a deleted conversation, or of one that belongs to another account or organization, shows "Conversation not found". A role that can only read conversations does not get the **New conversation** button. The chat interface follows the dashboard's language (English or French).

Things the assistant can do for you:

- **Run your agents.** Ask for an agent by name, or describe the task. The conversation shows a progress card for the run with its status, a link to the run page, and the files it produced.
- **Read and explain.** Look up runs, files and anything else the API shows your role.
- **Connect accounts.** When an agent needs an integration you have not connected, the chat shows a connect card that starts the sign-in flow. If your browser blocks the window, use the link to open it in a new tab.
- **Work with files.** Attach files to a message. A file you attach (button or drop) is stored in your personal space (« My space »), private to you, whatever space the conversation works in, and it is deleted with the conversation, even when a run of a team space used it. The assistant reads it, and can give it to a run in any space where you can launch one: the run's outputs are then visible to that space's readers. A conversation limited to one space stays limited. A side panel next to the conversation has Preview, Runs, Files and Info tabs for what the conversation touched.
- **Schedule runs and create agents**, where your role allows it (see below).

The assistant shows its reasoning as a collapsible row while it thinks, and names the model that answered. If a turn fails, the message says why (a provider refused the key, a rate limit, the organization out of credits, a connection that needs to be renewed) and offers **Retry**. When the server returned one, the failure shows a request ID that an administrator can look up in the logs.

For example, ask “What is the renewal date in the contract in my connected drive?” For a temporary read, Chat retrieves the file with your access to the source and sends its content to your configured model provider for the current turn. Text and raster images are supported when the model accepts them. Images are sent unless the model is declared without vision; a model whose capabilities are unknown receives them. A PDF is read natively through the OpenAI, Anthropic and OpenAI-compatible Chat Completions APIs, unless the model is declared without vision (providers read each page of a PDF as text and an image). Appstrate’s Mistral Conversations adapter has no PDF encoder, so PDFs are not sent to it. When a file is not sent, the attachment chip says so and the assistant still gets a reference it can open through an inline run. If a provider refuses a request that carries a file, the chat retries without the file, at most twice, and the assistant, told the file was withheld, answers without it for the rest of that turn. A failure that arrives after the assistant started answering is reported as is, without a retry. An error unrelated to the file is reported after those retries. Nothing is remembered across turns: a PDF is sent only on the turn it is attached or read, and an image for the three most recent messages you sent. With a connector, this mode reads one file up to 700 KiB, with a smaller limit for text. Ordinary JSON API calls use their usual response format and limits. Your conversation keeps a receipt and the assistant’s answer, including anything it quotes.

If you ask “Keep this version of the contract”, an inline run retrieves that revision with the integration and publishes a file. You need permission to launch the run. The file appears on its run page and in the conversation, and its visibility follows the run’s access rules. If the exact revision cannot be retrieved, the assistant asks before keeping a different version. A run can also process Office documents and larger files.

## Control what it can do

### Assistant access

The access chip in the composer lists, for the spaces the conversation can act in, what the assistant can do for you: use the Appstrate API on your behalf, run agents, create agents, see runs, browse files, connect accounts, activate an integration, schedule runs. Each line is marked allowed or denied by your role, or turned off in the composer. The assistant never exceeds your role.

### Agent authoring

A toggle in the composer controls whether the assistant may **create or edit agents** and compose a one-off agent on the fly for a single task. Each execution of such an agent costs a run. Turned off, the assistant sticks to your published agents and does not run drafts. The setting is remembered per account in your browser.

### Model of inline runs

By default, a one-off agent the assistant composes runs on the organization's default model, not on the conversation's. **Inline runs on the chat's model**, in the composer's **Assistant settings** menu, makes those runs use the conversation's model and its settings (temperature, reasoning level) instead, and a chip in the composer shows it is on. It is off by default because the assistant can split a task into several runs, and the conversation's model is often the most expensive one. It does not change a saved agent's run, which keeps its own model. The model is checked like any model chosen for a run you launch, and billed to you the same way; a model that is no longer usable falls back to the default model with a **Model replaced** notice on the run. The setting is remembered per account in your browser.

### Skills

[Skills](/features/skills) give the assistant instructions for a domain. Each conversation has two skill settings, in the composer's skills panel:

- **Pinned skills**: a checked skill is pinned to the conversation, and each turn tries to load it in full. Each row shows whether the last message actually loaded it:
  - no caption: loaded, or not yet evaluated;
  - "Cited in the message": named in the message you are typing, so locked until you remove the mention;
  - "Not loaded" with the reason: skill budget exceeded, unavailable or unreadable.

  A skill that is not loaded stays pinned and is not counted as loaded. A gauge shows the pinned skills' share of the 64,000-character budget and warns before a pin would exceed it. Changes apply from the next message, as a line at the foot of the panel says, even while a reply is being written. Uncheck any pinned skill to remove it from the conversation: it leaves the context from the next message on, and earlier turns are unchanged.

- **Automatic discovery** (on by default): the assistant sees the other skills of the spaces the conversation can act in, one line each, and loads the one that fits. The skills you pinned are not listed again. When it is off, the assistant has no access to any other skill: it cannot list, load, declare or write one, whatever your role. The skills you pinned still apply.

A skill the assistant reads this way is not pinned: it serves that message and its text stays in the conversation's history, shown in the thread as a "Read for this message" chip with a "Pin" action. Only you pin a skill. A conversation holds at most 5 pinned skills, sharing a budget of 64,000 characters; pinning a sixth is refused, so uncheck a skill to make room.

## For administrators

- Every chat turn runs inside the API process, on the Pi engine. `CHAT_PI_MAX_CONCURRENCY` (default 6) caps concurrent turns per API process, and a full instance answers new turns with `429`. Size it from measured capacity before opening chat to many users. The variables are in [Environment Variables](/self-hosting/environment-variables).
- Inference goes through the platform's LLM proxy: the model's key is injected server-side and the usage is metered like any run. With the billing module, a chat can stop on an exhausted quota.
- The assistant drives the platform through the same [MCP tools](/using-appstrate/mcp-clients#the-tools) an external client gets, which enforce your permissions on every call.
- Developers can reach the same surface over the API: `POST /api/orgs/{orgId}/chat` and `/api/orgs/{orgId}/chat/sessions`. See the [API reference](/api).

### Commands

Type `/` in the composer to open the list of commands: the skills the conversation can read and the agents you can launch, in the spaces the conversation acts in (the origin space alone when it is limited to it). The list is the one the Appstrate MCP server serves to any client, with your own permissions, and it shows skills even when automatic discovery is off.

- **A skill** is added to your message as a chip. When you send the message it is pinned to the conversation, like ticking it in the skills panel, and stays pinned on every later turn until you remove it there; removing the chip before sending pins nothing. A message citing more than the 5 pinned skills allowed cannot be sent.
- **An agent** asks the assistant to run it. Type what you want after the command; the assistant builds the run's input from it, asks for what is missing, then launches the agent. Each launch is a metered run. The conversation shows what you typed, and the assistant is given the launch instructions the server returns, which are kept with the message. Later turns replay the most recent launch instructions within a 64,000-character budget; older ones are replaced by a short note, and you can launch the agent again. If the platform's MCP server cannot answer, the launch fails with a gateway error (502) and nothing is sent.
