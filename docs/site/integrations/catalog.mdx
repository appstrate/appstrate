An **integration** is the definition of an external service (Gmail, Slack, ClickUp...): how to authenticate against it, which URLs a credential may be sent to, and how the agent reaches it. For the model behind this page (sources, auth methods, connections, credential isolation), read [How integrations work](/integrations/how-integrations-work).

Appstrate ships **77 built-in integrations**. They are `.afps` archives in [`system-packages/`](https://github.com/appstrate/appstrate/tree/main/system-packages), loaded at boot and addressable as `@appstrate/<name>`. System integrations are versioned and can be forked (`POST /api/packages/{scope}/{name}/fork`): publish a fork under your own scope to add a scope or an authorized URI, and make your agents depend on the fork. If the service you need is not listed, [write your own](/integrations/custom-integrations).

To list what your instance actually offers, with the activation state in the current space:

```bash
appstrate api GET /api/integrations
```

## How to read the table

| Source       | Meaning                                                                                                                                                                                                                                                                          |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `api_call`   | No MCP server. The agent gets an `api_call` tool: the sidecar checks the target URL against the integration's `authorized_uris`, injects the credential and forwards the request. 62 integrations work this way.                                                                 |
| Remote MCP   | The integration is backed by the vendor's MCP server: a hosted one, or, for GitLab, Twenty, Coolify, Browserless and Playwright MCP, the one of the instance the user names when connecting. The sidecar opens the MCP connection and injects the access token. 13 integrations. |
| Local runner | The integration is backed by an `mcp-server` package that runs in its own sandboxed runner container, one per connection. 2 integrations (they need the `docker` or `firecracker` run adapter).                                                                                  |

Integrations with an own page link to it. The API and MCP variants of GitHub, Gmail, Notion and ClickUp share one page, and so do Garmin Connect and Garmin LiveTrack.

By authentication method: 43 OAuth 2.0 and 15 API key integrations reached through `api_call`, 4 with custom credential fields (Webhooks, WooCommerce, WordPress, Garmin LiveTrack), 13 remote MCP integrations (GitHub and Twenty accept OAuth or a key, Browser Use, Browserless, Coolify and Playwright MCP take a key only, and the other seven use OAuth) and 2 local runners (GitHub Git and SSH). The two `mcp-server` packages that back the local runners, `@appstrate/github-git-mcp` and `@appstrate/ssh-mcp`, ship in the same directory.

An API-key integration needs no OAuth client: the user creates a key in the service's dashboard and pastes it into the hosted connect form. When the service offers restricted keys (Stripe does), give the key only the permissions the agent needs.
