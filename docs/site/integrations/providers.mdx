An **integration** is the definition of an external service (Gmail, Slack, ClickUp...): how to authenticate against it, which URLs a credential may be sent to, and how the agent reaches it. For the model behind this page (sources, auth methods, connections, credential isolation), read [How integrations work](/docs/integrations/how-integrations-work).

Appstrate ships **67 built-in integrations**. They are `.afps` archives in [`system-packages/`](https://github.com/appstrate/appstrate/tree/main/system-packages), loaded at boot and addressable as `@appstrate/<name>`. System integrations are versioned and can be forked (`POST /api/packages/{scope}/{name}/fork`): publish a fork under your own scope to add a scope or an authorized URI, and make your agents depend on the fork. If the service you need is not listed, [write your own](/docs/integrations/custom-providers).

To list what your instance actually offers, with the activation state in the current space:

```bash
appstrate api GET /api/integrations
```

## How to read the table

| Source       | Meaning                                                                                                                                                                                                          |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `api_call`   | No MCP server. The agent gets an `api_call` tool: the sidecar checks the target URL against the integration's `authorized_uris`, injects the credential and forwards the request. 59 integrations work this way. |
| Remote MCP   | The integration is backed by the vendor's hosted MCP server. The sidecar opens the MCP connection and injects the access token. 6 integrations.                                                                  |
| Local runner | The integration is backed by an `mcp-server` package that runs in its own sandboxed runner container, one per connection. 2 integrations (they need the `docker` or `firecracker` run adapter).                  |

Integrations with an own page link to it. The API and MCP variants of GitHub, Gmail, Notion and ClickUp share one page.

## What changed from "providers"

Earlier documentation described 60 hand-written "providers". Those are now integrations, with a different manifest shape and a different runtime. Notable differences:

- Trello is no longer shipped, and the `oauth1` auth type no longer exists.
- Gmail, GitHub, Notion, ClickUp and Canva exist twice: once as a direct API integration, once backed by the vendor's MCP server. They are separate packages with separate connections.
- OAuth scopes are no longer picked in a provider form. They are inferred from the tools each agent selects. See [Scopes](/docs/integrations/how-integrations-work#scopes).
- The sidecar `/proxy` endpoint and its `X-Provider` headers are gone. The agent calls `{namespace}__api_call` as an MCP tool.
