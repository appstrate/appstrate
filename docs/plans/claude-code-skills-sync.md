# `appstrate code sync` — decisions

Goal: a user installs one Claude Code plugin and, from then on, every skill of
the spaces they reach in their pinned Appstrate organization is
available locally as `/appstrate:<skill>`, kept up to date without a manual
step. The connected plugin also supplies the organization's MCP endpoint, and
every agent active in the pinned space as `/appstrate:run-<agent>`, a generated
command that launches it through that endpoint (D18–D25). The same sync feeds
OpenAI Codex skills; Codex MCP is configured separately.

**How it behaves is documented in `apps/cli/README.md` → `appstrate code sync`**
— flags, targets, failure modes, ownership rules, the marketplace command
string, and the cron / `launchd` fallback. This file records only the choices
behind it and what is still open.

The mechanism is entirely client-side: Claude Code plugin marketplaces accept
`source: "command"`, a locally installed tool prints the path of a directory
holding a complete plugin, and Claude Code re-runs the command once per session
in the background and installing a new copy when the directory's content hash
changes. A fresh session applies context and MCP changes reliably. No daemon
or server change.

Writing and comparing the connected plugin use the same expected fixed files.
An instance, org or space change therefore updates `.mcp.json` even when every
skill is unchanged. Skill sources default to every space this profile is a member of with
`skills:read` there; repeated `--space` flags, then profile `syncSpaces`,
narrow that set. Agent commands ignore that selection: they come from the
pinned space alone (D19), so a space change replaces them too. The
listings run concurrently but merge in selection order, so a package attributed
to several spaces is downloaded once, from the first that listed it — and which
one that is never changes the version, which `versions/latest` resolves per org.
Explicit flags accept IDs or unambiguous exact names. Persistent selections
contain space IDs and are cleared when the organization changes. An empty
`syncSpaces` list installs no business skills and retains MCP. The server
validates `X-Space-Id` against the org (`resolveMcpSpaceRow`) and forwards it
on every in-process dispatch, so the header cannot reach another org's space.
The CLI reference documents OAuth, reloads, legacy connection coexistence and
opt-out.

## Active context and removal

There is one managed context per destination, not one accumulated installation
per profile. A successful context switch replaces the old installation. The
plugin's skills, agent commands and generated MCP connection are prepared and
replaced together; a failed replacement preserves the previous plugin. The MCP
header always uses the pinned active space, even when skills are selected from
several spaces — and the pin is not part of the context (D9): switching space
rewrites `.mcp.json` and the agent commands and keeps every installed skill,
without the all-or-nothing rule a context switch carries. A pin that moves
mid-run still aborts the swap.

Explicit logout removes the profile's managed shared skills and replaces its
generated plugin with setup files, without `.mcp.json` or agent commands.
Another profile's targets are preserved. Logout still removes local
credentials when remote revocation or skill cleanup fails; cleanup failures
retain ownership for a later retry. The same sync lock serializes cleanup and
installation. A ledger names its context, and one that does not is not this
format: it is refused whole rather than read as "owner unknown", so no code
path has to decide whose directories those are.
The next sync re-materializes and owns them again.

Cleanup changes the generated source immediately. Claude's installed cache and
an active session are separate: the next command-source refresh, or
`claude plugin update appstrate@appstrate` followed by a fresh session, applies
the new copy. Removing the default CLI profile may activate another configured
profile; that next sync installs the newly active profile instead of setup.
Without a configured profile, it keeps setup. These operations distribute
skills and agent commands; they do not introduce package authoring or bidirectional folders.

Codex supports plugins and plugin-provided MCP servers. Its current documented
plugin installation does not provide the Claude marketplace command-source
sync mechanism used here; direct skill directories plus explicit MCP setup
keep this implementation small. See [building Codex plugins](https://learn.chatgpt.com/docs/build-plugins)
and [Codex MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli).

## Still open

- **Release**: tag `cli@<version>` after merge. The companion
  `appstrate/claude-plugins` change is merged only once the CLI release that
  carries the command is on npm. It changes:
  - `.claude-plugin/marketplace.json`: the `command`, to
    `appstrate code sync --target claude-plugin --target codex --print-path`
    (both branches: the local binary and the `npx` fallback); the `homepage`
    anchor, to `#appstrate-code-sync`; the plugin `description`, from skills to
    skills and agent commands;
  - its `README.md`, every `packages sync` mention: the command Claude Code
    shows at install; the note on a changed marketplace command, whose example
    becomes this rename; the troubleshooting line "Run `appstrate packages sync`
    in a terminal", which must name the marketplace's own targets
    (`appstrate code sync --target claude-plugin --target codex --print-path`)
    to reproduce its failure message; and the `--target claude-user` fallback
    for `disableCommandPluginSources`.

  Each machine re-accepts the changed command once
  (`claude plugin update appstrate@appstrate`). The marketplace runs a globally
  installed `appstrate` before `npx`, so a machine with an older one fails until
  it is upgraded; the release note says so, as it says that cron / `launchd`
  entries must be edited.

## Follow-ups (not in this plan)

- **Integration test** (label `integration`, real API via `getTestApp`):
  publish two skills, sync, assert the tree; publish a new version, sync,
  assert only that one re-downloaded. Every server interaction is covered today
  by a stub built from real `.afps` archives
  (`apps/cli/test/helpers/skills-server.ts`); what is missing is the round-trip
  against the real routes.
- **Bulk endpoint**: extend the skills list DTO with `latest_version` +
  `latest_integrity` (one LEFT JOIN on the `latest` dist-tag) to drop the N
  version calls. Server change + OpenAPI + `generate:api`.
- **Codex MCP automation**: consider a wrapper only if the documented setup
  proves insufficient. It would need an explicit ownership and conflict policy
  for existing entries, org switches and client failures before it could write
  client configuration safely.
- **Push freshness**: a plugin `monitor` polling `GET /api/packages/skills` and
  `GET /api/packages/agents` and re-running the sync — only if once-per-session
  proves too slow in practice.
- **Package events** on the webhook module (`package.version_created`) — would
  benefit any external sync, not just this one.
- **Multi-space agents**: agent commands from every space the profile reaches.
  The right shape is a multi-space MCP session — the space an argument of every
  tool, the tool surface computed per call — an issue of its own, not a
  `space_id` argument on `run_and_wait` alone (D19).
- **Codex agent commands**: need an MCP server on the Codex side first (D13,
  D18).
