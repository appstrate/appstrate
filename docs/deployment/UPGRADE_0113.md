# Upgrading through core migration 0113

Use the candidate binaries for both checks below. A standard beta.68 database has 97 core journal entries, beta.70 has 110, and the release through 0113 has 114. Record the actual journal, image revisions and the original 0053 cutoff of the installation. Rehearse on an isolated, consistent restore before scheduling maintenance.

1. Drain runs and stop all writers. Back up PostgreSQL and object storage to a common restore point. When upgrading directly from beta.68, run only steps 1 and 2 of the [beta.68 maintenance window](BETA_69.md#maintenance-window), including 0054 **before** Drizzle, then continue here: steps 3 and 4 below replace its steps 3 and 4, because its 0052 would copy notifications into `run_reads` before the check below has run. Use the candidate images together throughout the upgrade.
2. Run `bun scripts/migration/verify-beta68-upgrade.ts before-schema` with the target database explicitly configured. Every pending count must be zero. The check examines the notifications that 0052 will copy, existing read markers and OAuth grants. It recognizes the notification types on either side of 0103. For notification mismatches, see [repair 0057](../../scripts/migration/README.md#0057--run-notification-scope). For a conflicting read marker or grant, verify the owning run or grant, recipient and tenant using the restored data and audit history. Resolve ambiguous ownership individually before continuing.
3. Apply the candidate schema through 0113 with the migrator and verify the journal. On a direct beta.68 upgrade, complete the historical data steps, including 0052, 0053 with the recorded cutoff and 0055. On later installations verify their postconditions and complete any pending steps using the original cutoff. Apply [0056](../../scripts/migration/0056-delete-marked-oauth-refresh-tokens.sql) for previously marked OAuth refresh tokens. Keep writers stopped.
4. Run `bun scripts/migration/verify-beta68-upgrade.ts before-traffic --before <original-0053-cutoff>`. Resolve every nonzero count on the restore first. Check that the API boots with `MIGRATIONS_ON_BOOT=verify`, platform, Pi and sidecar share the reviewed revision, and every enabled module loads. Open a historical chat, retry a turn, verify a failed run and its recipient's read state, and exercise an integration with the release browser tests. Reopen writes and schedules only after acceptance.
5. If acceptance fails, keep writers stopped and restore the database and objects together before restarting the previous images. If traffic has already reopened, preserve and reconcile intervening writes before restoring.
