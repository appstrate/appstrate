# Sidecar Protocol

Runtime detail beyond the architecture diagram in `AGENTS.md`. Complements `docs/architecture/INTEGRATIONS_RUNTIME.md`.

### Sidecar Protocol (details beyond the architecture diagram)

- **Sidecar lifecycle**: One fresh sidecar container per run — every run has one — spawned in parallel with the agent. The agent container holds only the credential placeholder, sends inference to the sidecar's `/llm` proxy (`MODEL_BASE_URL`), and runs on the restricted network — the run's internal network under Docker, the guest firewall's loopback + platform-sink allowlist under Firecracker — so its other outbound traffic leaves through the sidecar's forward proxy. `DockerOrchestrator.initialize()` calls `ensureImage()` for the PI + sidecar images at boot to amortise cold-pull (20–45 s) off the first run's critical path. There is no sidecar pool — empirical measurement showed the agent's own Bun cold start (~1 s) already masks warm-image sidecar boot, so pre-warming offered no user-visible latency win while carrying meaningful complexity (`/configure` endpoint, `CONFIG_SECRET`, standby network, replenish loop).
- **Parallel startup**: `pi.ts` runs sidecar setup in parallel with agent container creation + file injection via `Promise.all`. Files are batch-injected as a single tar archive before `startContainer()`. `DockerOrchestrator.createSidecar` does not await `/health` — it returns once the container is created + started, and the agent's MCP handshake retries on connection-level errors (both Node's `ECONNREFUSED` / `ENOTFOUND` / `ECONNRESET` and Bun's `ConnectionRefused` / `DNSNotFound` / `ConnectionTimeout` — see "MCP transport retry" below) with AWS full-jitter backoff (50ms→1s, 60s deadline) until the sidecar's listener comes up (#406). The run launcher races the sidecar's exit against the agent's, so a sidecar that dies (on boot or mid-run) fails the run at once and logs its exit code and log tail, rather than surfacing as an MCP handshake timeout.
- **Agent-facing surface**: every sidecar-backed capability is registered as a typed Pi tool by `runtime-pi/mcp/direct.ts`. The LLM sees the canonical first-party set — `run_history`, `recall_memory` — plus, per AFPS integration that opts into the `_meta["dev.appstrate/api"]` vendor extension, a `{ns}__api_call` outbound proxy (+ optional `{ns}__api_upload` when that auth declares `upload_protocols`) and any other tool the integration advertises, all exposed under a `{namespace}__{tool}` prefix (Phase 1.4, see "AFPS Integrations runtime" below). The agent never sees the sidecar URL.
  - `{ns}__api_call({ method, target, headers?, body?, responseMode?, connection? })` — credential-injecting proxy. `connection` exists only when the namespace holds several bound connections: `McpHost` then injects it as a required enum of connection labels on every tool of the namespace and routes the call by it. `api_call` is an Appstrate VENDOR capability declared via `_meta["dev.appstrate/api"].auths.{authKey}` — ORTHOGONAL to `source.kind` (a `local`/`remote` integration with an MCP server can ALSO expose it). Single opted-in auth → tool named `api_call`; multiple → `api_call__{authToken}` per auth. Keys up to 17 characters remain verbatim; longer keys use a stable 18-character token, while the complete auth key travels separately for credential lookup. Declared synthetic names and persisted long-key aliases are reserved over same-named native MCP tools; without the extension those native names remain ordinary. Tool description, schema, and execution are all served by the sidecar's MCP `tools/call` handler, which validates against the auth's `authorized_uris` (AFPS §7.9) and injects the configured credential header server-side.
  - `run_history({ limit?, fields? })` — recent past-run metadata. Dispatched to the sidecar's MCP handler, which reads from the platform's internal run-history endpoint via the per-run token.
  - `recall_memory({ query?, limit? })` — search the agent's memory archive (rows in `package_persistence` written via the `note(content)` built-in runtime tool). Same MCP path; scoped to the caller's actor.
  - **Zero-knowledge enforcement**: the run-scoped secrets — `SIDECAR_URL`, `SIDECAR_AUTH_TOKEN` and the three `APPSTRATE_SINK_*` keys (`RUNTIME_SECRET_ENV_KEYS`, `@appstrate/runner-pi/secret-env`) — are never in the environment of the process that runs the agent. The container's first process is `runtime-pi/launcher.ts` (Docker ENTRYPOINT, Firecracker supervisor argv): it makes itself non-dumpable (`prctl(PR_SET_DUMPABLE, 0)`, `runtime-pi/non-dumpable.ts`), starts `entrypoint.ts` with an explicit environment that excludes them and hands them over on its stdin. The entrypoint makes itself non-dumpable before reading them and holds them only in memory. So nothing the agent spawns inherits them — including processes Pi starts without an explicit `env`, which get the entrypoint's STARTUP environment whatever `process.env` says later — and no other process of the agent uid can read either process's `/proc/<pid>/environ`, `mem` or `fd`. The process orchestrator does the same handover itself (no launcher; `prctl` only on Linux — dev mode isolates nothing by design). The secrets are held only in the runtime process's memory, and the code that runs in that process comes only from the read-only runtime image: `/runtime` (the bundle, `node_modules`, the transpiler cache) is root-owned and not writable by the agent uid, and the entrypoint's working directory is that read-only tree — so the agent cannot get code loaded into the process that holds the secrets. As PID 1 the launcher also reaps the processes the agent orphans (`runtime-pi/reap-orphans.ts`). Pinned in the built image by `runtime-pi/test/runtime-secrets-container.e2e.test.ts`. The legacy `curl $SIDECAR_URL/…` bash pattern is fully retired — no prompt path documents it anymore. Withholding the URL removes the convenience, **not** the knowledge: `NO_PROXY` names the sidecar's host and curl prints it on every invocation (`Uses proxy env variable no_proxy == '…'`), Docker's embedded DNS resolves it, and a production run reached the sidecar's ports that way. Withholding the TOKEN is what removes the capability — see “Agent authentication” below. Neither touches `RUN_TOKEN`, which never enters the agent container at all: the security boundary toward the PLATFORM is still that the sidecar is the only party holding it.
- The sidecar exposes `/mcp` (Streamable HTTP, stateless, per-request transport) as the agent's MCP entrypoint, alongside `/health`, `GET /integrations/boot-report` (agent-authenticated like `/mcp` — the agent's boot gate + observability source, see the AFPS Integrations runtime section), and `ALL /llm/*`. The legacy `/proxy`, `/run-history`, and `/configure` HTTP routes were retired (the latter alongside the sidecar pool — sidecars now boot fully configured via env vars). `/llm/*` is intentionally kept: the in-container Pi SDK calls `${MODEL_BASE_URL}/v1/chat/completions` and consumes the upstream stream natively, so the `/llm/*` reverse proxy is load-bearing for primary chat completions. For an **aliased** model the same route is not a proxy at all: the container speaks `pi-messages` (pi-ai's vendor-neutral protocol) so that no vendor request shape or response dialect ever reaches it, and `POST /llm/messages` TERMINATES that protocol — `runtime-pi/sidecar/pi-messages-backend.ts` rebuilds the real backing's pi-ai `Model` and re-originates the call through pi-ai, projecting the events back onto the closed `PiMessagesEvent` union. This is why the sidecar image carries `@earendil-works/pi-ai` (via its own `pi-sdk.ts` barrel, +0.31 MB on the compiled binary): every vendor quirk keeps being derived by pi-ai itself, one process to the left of the container, with no quirk table mirrored anywhere. See `docs/architecture/MODEL_ALIASES.md` → "The canonical dialect". There is no MCP-side completion tool — sub-agent flows are handled by spawning a separate run via the platform API (each sub-task = a first-class run with its own logs, status, cost, RBAC scope, providers, and skills). For OAuth **subscription** credentials (Claude Pro/Max, ChatGPT Codex) the `/llm` oauth branch is **provider-neutral**: it applies `applyOauthBearerSwap` (`@appstrate/core/oauth-bearer-swap`) — force the real subscription bearer onto `authorization`, drop any `x-api-key`, forward every other header the shared LLM policy keeps. It injects no provider-specific header and ensures no `anthropic-beta` flag; the Pi SDK (`@earendil-works/pi-ai`) emits each provider's request fingerprint itself. The real token is swapped in server-side, so it never enters the agent container (see `docs/architecture/SUBSCRIPTION_COMPLIANCE.md`). For an **API-key** model — platform-provided (a `SYSTEM_PROVIDER_KEYS` preset) or the organization's own — the sidecar holds no provider credential (`authMode: "platform"`, env `PI_LLM_PLATFORM_API_SHAPE` + `PI_BASE_URL`), only the run token, which authorises this run's metered inference: its `/llm/*` upstream is the platform's metered LLM proxy at `<PLATFORM_API_URL>/internal/llm-proxy/<apiShape>`, authenticated with `Authorization: Bearer <RUN_TOKEN>` in place of the placeholder, and narrowed to the one inference endpoint that route serves (anything else is a 404 before any upstream call). An aliased run re-originates there too, pi-ai signing with an inert key and the same bearer; its `Model` keeps the backing's own base URL (`PI_BASE_URL`, never dialed), because pi-ai derives vendor dialect from it, and the transport swaps that prefix for the proxy route. The proxy serves the run's own model whatever the request names and meters every call on the run — see `docs/architecture/RUN_COST.md`.
- **Agent authentication — the per-run network is NOT the boundary**: the whole control surface (`ALL /llm/*`, `ALL /mcp`, `GET /integrations/boot-report`, `GET /runtime-events`) requires the run's `x-appstrate-sidecar-auth` token; `/health` is the single exemption, because it is the container health gate the orchestrator probes before the run exists. One `app.use("*")` middleware in `runtime-pi/sidecar/app.ts` denies by DEFAULT — a route added later is protected without anyone remembering to say so — and compares the header in constant time (`timingSafeEqual`). A missing header, a wrong header, and a sidecar that was never handed a token are all 401; there is no unauthenticated fallback.
  - **Why**: the earlier posture (“no inbound auth, the per-run Docker network IS the boundary”) assumed the agent is alone on that network. It is not. `integration-runtime-adapter-docker.ts` attaches every third-party integration runner to the same `appstrate-exec-<runId>` bridge and hands it `http://sidecar:<port>` for its egress proxy, so a `source.kind: "local"` integration could reach the LLM proxy with one `curl` and spend the org's provider credential, unauthenticated and unattributed. `--internal` blocks egress, not sibling-to-sibling traffic. For an ALIASED run the proxy does not even need a plausible credential — `pi-messages-backend.ts` re-originates against the backing using the sidecar's own config.
  - **What the token is not**: it is NOT `RUN_TOKEN` and is not derived from it. `RUN_TOKEN` stays outside the agent container (only the sidecar can call the platform back) and that invariant is unchanged. `SIDECAR_AUTH_TOKEN` is a per-run random secret with exactly one meaning — “I am the agent container talking to my own sidecar” — and no authority outside the run's network.
  - **Where it comes from**: minted per run in `apps/api/src/services/run-launcher/pi.ts` (32 random bytes, base64url), in the one frame that feeds both halves of the pair — `SidecarLaunchSpec.sidecarAuthToken` → the sidecar's `SIDECAR_AUTH_TOKEN` env var (via `services/orchestrator/sidecar-env.ts`, shared by the docker, process and firecracker orchestrators), and `buildRuntimePiEnv({ sidecarAuthToken })` → the agent container's `SIDECAR_AUTH_TOKEN`. Never persisted, never logged. `buildRuntimePiEnv` **throws** without one, the same way it does without `sidecarUrl`: a run that cannot authenticate to its sidecar must fail at launch rather than 401 on its first inference call. Connect-runs mint none — their sidecar exits before it ever serves the agent surface. On Firecracker the key is classified in BOTH `SIDECAR_SECRET_KEYS` and `AGENT_SECRET_KEYS` (`modules/firecracker/credential-split.ts`), so it rides MMDS in memory instead of the at-rest config drive.
  - **How it rides**: the boot-report fetch and the runtime-event drainer set the header directly; the MCP client sets it via `extraHeaders`. On `/llm/*` there is no per-call hook — the Pi SDK owns the request — so `buildPiModelFromEnv` puts it on `Model.headers`, which `pi-coding-agent`'s provider composer folds into the per-request options for every api shape, including `pi-messages` (aliased runs), whose pi-ai adapter reads `options.headers` and nothing else. `Authorization` was unusable: on `/llm/*` that slot already carries the placeholder credential the sidecar replaces with its own upstream auth. Both `/llm/*` forwarding paths drop it (and the `x-appstrate-pi-sdk` sibling) with every other `x-appstrate-*` header, so a live secret never travels on to a provider.
  - **Not covered by the token**: the per-connection egress / MITM listeners, the transparent plane, the DNS responder and the forward proxy are their own listeners, not routes on this Hono app. Runners hold no token; the CONNECT listeners, the transparent splicers, the MITM listeners and the agent's forward proxy attribute the connecting peer instead — by source IP in docker mode, by the uid owning the client socket in process mode (see "Runner egress allowlist" below). The DNS responder does not: it answers any peer with the plane's own address, which grants nothing. A network split was considered instead and rejected: in container and VM mode the sidecar binds `0.0.0.0` (in process mode, loopback through `LISTEN_HOST`) and must stay reachable from the runner side for exactly those listeners, so splitting networks would not close `:8080` without per-interface binding.
- **Forwarded LLM request headers**: one policy, `forwardedLlmRequestHeaders` (`packages/connect/src/llm-request-headers.ts`, the authority for the exact names and prefixes), shared by `/llm/*` and the platform's `/api/llm-proxy/*`. It is a denylist, so a header a Pi upgrade adds for a new provider keeps working: every header Pi sent goes upstream except transport and hop-by-hop headers, inbound credentials, platform-internal headers, vendor account scoping (OpenAI organization/project), client network identity (forwarding chains, client-IP headers, every Cloudflare `cf-*` header), identity asserted by an auth proxy or CDN in front of the caller, and request-rewriting overrides (method / original-URL headers). Each proxy then sets its own auth on the result — here the run token (platform mode) or the fresh subscription bearer (oauth mode). The llm-proxy alone adds its billing guard on the result (`anthropic-beta` narrowed to Pi's own betas, `x-anthropic-beta` dropped, on every wire); the sidecar does not, because its subscription passthrough needs Pi's OAuth betas.
- Sidecar substitutes `{{variable}}` placeholders in headers/URL/proxy (and request body if `substituteBody: true`), validates against `auths.{key}.authorized_uris` per integration.
- **Credential-exfiltration guard** (`credentialUrlPolicy`, `@appstrate/afps-runtime/resolvers`, shared with the CLI resolver and the platform proxy): a call that carries a credential — one templated into the target, a header or a substituted body (scanned on exactly the strings substituted — buffered text, multipart field templates, JSON leaves), or one the proxy injects itself (`injectsCredential`) — drops `allow_all_uris`, and an `authorized_uris` entry whose host the caller picks (`https://**`, `https://*.com/**`: `isHostUnboundedUriPattern`, `@appstrate/afps-shared/authorized-uris`) refuses it. Every reader of an entry (this rule, the URL matcher, the runner egress policy, the literal-host pin) goes through one parser, `parseAuthorizedUriPattern`: an entry whose authority (after `scheme://`, up to the first `/`) is empty, is not spelled as WHATWG serialises it (only case and a default port may differ), or holds `%`, `\`, `@`, `?`, `#`, whitespace, a control or non-ASCII character is malformed — it matches nothing and counts as host-unbounded. The target and every hop must then match `authorized_uris` as rendered for the call's connection — only a URL-form entry the manifest declares (`{$credential.site_url}/**`, #1627) can bring a credential value in, never an implicit widening from any URL-valued field (its origin is often shared by tenants, e.g. `hooks.slack.com`); with none left, the call is refused (`unauthorized_target`), so a connection left with no entry has every call refused. An auth that declares no `authorized_uris` and not `allow_all_uris` has every call refused as well, credential or not (`refuse: "unauthorized"`; the platform proxy answers `403 unauthorized_target`) — an empty authorized set authorizes nothing (AFPS §7.9), never an SSRF-gated relay to any host. The platform refuses a value that would drop an entry when the connection is created or its credentials are updated (`unrenderableAuthorizedUriFields`, `@appstrate/afps-shared/authorized-uris`), so that state is reached only by a connection stored before the check. **What this covers, and what it does not**: a TEMPLATED credential cannot leave the rendered `authorized_uris` — a host+path bound, not a tenant bound: an allowlisted multi-tenant API (`https://discord.com/api/**`) still reaches other tenants' endpoints on that path. An injected credential is bounded at manifest write as well: an auth whose credential the proxy injects over HTTP must name its hosts — `allow_all_uris: true`, no `authorized_uris`, or a host-unbounded entry is refused (`findUnboundedInjectedCredentials`, `@appstrate/core/integration`) — and the MITM listener refuses such a call too (`request-refused`, `reason: "credential not host-bounded"`). Messages name the target host as the target TEMPLATE names it (`templateHost`: `{{field}}` for each rendered part, a literal host as written), so an echo never holds a value nor tells whether a guessed host matches one; redirect hosts, chosen by the upstream, keep the value scrub (`redactCredentialHost`, `redactionFields`).
- **SSRF layering** (target and every redirect hop): three tiers, all sharing the single blocklist in `@appstrate/afps-shared/ssrf`. (1) literal floor — `isBlockedUrl` refuses IP-literal/known-internal targets everywhere; (2) DNS rebind layer — `resolveAndCheckHost` (`@appstrate/afps-shared/ssrf-dns`) resolves every A/AAAA record and refuses if ANY lands in a blocked range (fail-closed on every hop: a target or redirect hop with no DNS answer is refused `upstream_unresolvable`, a blocked one `blocked_target` — the platform proxy's 502 and 403; the sidecar answers status 0 with the code); (3) resolve-and-pin — an `api_call`, on all three paths (`fetchApiCall`, `@appstrate/afps-runtime/resolvers`, over `guardedFetchChain` in `@appstrate/afps-shared/guarded-fetch`), connects each hop to the DNS-validated address by default (logical hostname kept on `Host` + TLS SNI), and so do the raw-socket egress paths (forward proxy, egress listener) and the MITM listener's upstream request (`guardedFetch`, its redirect returned unfollowed; the check at CONNECT gates the leaf mint only). The pin is off only for a call routed through a Bun `proxy` (the proxy resolves the name and matches its ACLs on it) or a test-injected transport. The platform's CIMD metadata-document fetch is its own pinned boundary — next bullet. **Internal hosts** — one rule, in `fetchApiCall`, for the three paths: a host skips the SSRF gate only when two parties agree. The manifest must name it in a DECLARED `authorized_uris` entry (never one rendered from a connection value) whose host segment is wildcard-free (`hostLiterallyAllowlisted`, `@appstrate/afps-shared/authorized-uris`), never under `allow_all_uris`: a glob-host entry (`https://**`) never exempts, the concrete host being agent-chosen. And the operator of the network the call leaves from must allow that host (`internalHost`, required, no default): on the sidecar and the platform credential proxy, `EGRESS_ALLOW_INTERNAL_HOSTS`; on `appstrate run --integrations=local`, always, since the network is the caller's own. A manifest alone never opens the operator's network, and an operator-listed host the manifest does not name literally stays gated, whether the agent, a connection value or a redirect picked it. The rule is per host and the same on every redirect hop: scheme, port and path are the allowlist's to bound, not the exemption's.
- **CIMD metadata fetch**: the boundary is `@better-auth/cimd/node`'s transport — HTTPS only, a single `dns.lookup(all: true)` whose every answer must be publicly routable, the connection pinned to that address through Node's `lookup` option, no redirect following, a 5 s timeout and a 5 KB body cap. On top of it the platform's `isCimdMetadataDocumentUrlAllowed` hook (`modules/oidc/auth/plugins.ts`) applies the LITERAL denylist from `@appstrate/afps-shared/ssrf` — it resolves no DNS, so it re-opens no rebind window — which is what refuses the run network's Docker aliases `sidecar`, `agent` and `host.docker.internal`: ordinary names that upstream's public-routability check lets through because they resolve nowhere outside a container.
- **Transparent egress for `delivery.env` integrations (#779)**: the plain CONNECT egress listener assumes a proxy-cooperative HTTP client, but most third-party MCP servers ship clients that ignore `HTTPS_PROXY` (undici/`fetch`) or speak non-CONNECT forward-proxy for HTTPS (axios → 405). In docker mode the sidecar therefore also mounts a per-run **transparent plane**: a UDP :53 responder (`integration-dns-responder.ts`) answers every external A query with the sidecar's own IP on the per-run bridge, and SNI-passthrough splicers on :443/:80 (`integration-transparent-listener.ts`) peek the TLS ClientHello SNI (or plain-HTTP `Host`), check the name, at the listener's own port, against the connecting runner's own allowlist (before any DNS resolution of it), apply the **identical SSRF floor** (literal + resolve-and-pin), and blind-splice raw TCP — no TLS termination, no CA, cert pinning keeps working. Runner containers whose egress is the plain CONNECT kind get `--dns <sidecarIP>` (Docker's embedded DNS still serves the `sidecar` alias locally and only forwards external lookups); MITM-delivery runners are excluded (splicing would bypass credential injection). The platform grants the sidecar `net.ipv4.ip_unprivileged_port_start=0` (netns-scoped sysctl, `CapDrop: ["ALL"]` intact) only when the run declares integrations. Requires Docker ≥ 27 for embedded-DNS forwarding on `internal` networks. **Process mode** mounts the same plane (one builder, `startTransparentEgressPlane`) on `127.0.0.1`, which only a Firecracker guest reaches (process mode spawns runners only on a runner uid pool), and starts it on the first plain-CONNECT runner's spawn: the responder answers with `127.0.0.1`, and the splicers bind `127.0.0.1:443`/`:80`. A run whose runners are all MITM-delivery starts no plane, so their redirected DNS lands on an unbound `127.0.0.1:53` and fails closed. The runners share the guest's `/etc/resolv.conf` with the sidecar, which needs real DNS, so there is no `--dns`: the guest nftables redirect UDP/53 from the runner uid pool to `127.0.0.1:53` in the kernel (`FIRECRACKER.md` → guest firewall). Instead of the sysctl, the guest supervisor starts the sidecar with ambient `CAP_NET_BIND_SERVICE`, so only the sidecar can hold :53/:443/:80 and neither the agent nor a runner can squat them first. The redirect is per uid, not per egress kind, so a MITM-delivery runner's lookups land on the plane too, and the plane refuses its connections, as in docker. Setup failure, in either mode, degrades gracefully to the proxy-env-only contract.
- **Runner egress allowlist (#1458)**: a local runner holds a decrypted secret, so where it may send traffic is bounded by its connection's **rendered** `authorized_uris` (`IntegrationSpawnSpec.egress`; how it is rendered: `docs/architecture/INTEGRATIONS_RUNTIME.md`). Every runner egress path enforces it, compiled once by `compileEgressPolicy` (`@appstrate/afps-shared/authorized-uris`): the CONNECT listener checks `host:port` after the SSRF literal floor and before resolve-and-pin, then relays the server's bytes at once (a server-speaks-first banner, SSH or SMTP, is not held back) and vets only the client's first bytes: a TLS ClientHello whose SNI the policy does not grant, or that is not self-contained in the first record, is refused; first bytes that are not TLS (plaintext HTTP, a STARTTLS protocol) are relayed without an SNI check; a tunnel where neither side sends within the preamble timeout is closed with an event; the transparent plane checks SNI / `Host` against the policy of the runner the peer belongs to; the MITM listener checks the SNI, at the port the runner CONNECTed to, before minting a leaf cert, forwards to that same port, and checks every decrypted request URL, answering 403 (`request-refused`, `reason: "not-authorized"`) instead of forwarding it un-injected. **Port rule** (TCP level): only `scheme://` patterns grant anything and the path is ignored; an explicit `:port` grants that port; without one a pattern grants ONLY its scheme's default port (https/wss 443, http/ws 80, ssh/sftp 22), and an unknown scheme without a port grants nothing; a bare `scheme://**` stays the catch-all (any host, any port). `mtls` runners get the CONNECT and transparent routes too: they relay blindly, so client-certificate TLS works end to end. **uv runners**: `uv run` materialises the bundle's venv at startup from the package index, through the runner's own egress, so the index (`pypi.org` + `files.pythonhosted.org`, or a private one) is reachable only if the integration's `authorized_uris` declares it; otherwise the bundle must vendor its dependencies. There is no platform exception: a runner reaches exactly what its manifest declares. **Residuals**: (1) the blind paths (CONNECT, transparent) bind the TLS SNI, which stops SNI-routed fronting through a shared CDN front, but inspect neither the HTTP `Host` inside TLS nor HTTP/2 connection coalescing, so a CDN-fronted entry bounds the front, not the tenant behind it; plaintext HTTP is not `Host`-checked on CONNECT at all (first request included), and on the transparent plane only a connection's first request is. Only the MITM path checks the full URL of every request. The CONNECT listener vets the outer SNI only: a ClientHello without SNI, or with Encrypted Client Hello, is relayed (refusing ECH would break Chrome-based runners, which send GREASE ECH), so an ECH-capable CDN front bounds the front, not the inner name. (2) Runners on one per-run network can reach each other directly: inter-container traffic stays enabled because the agent and the runners reach the sidecar over that bridge, so two hostile runners in one run can relay through the one with the wider policy. Closing it needs a network per runner (not done). The process-mode counterpart is the same class: runners sharing one Firecracker guest share its loopback and its abstract unix socket namespace, so two hostile runners can talk over `127.0.0.1` or hand each other connected sockets (`SCM_RIGHTS` over an abstract socket, which no file permission guards), and the narrower one can borrow the wider one's route. Separate uids and private groups do keep each runner's files, HOME and `/proc/<pid>/environ` (its decrypted credentials) out of its siblings' reach. A runner can also reach the agent's loopback listeners, so a runner that gets the agent to relay for it (e.g. a prompt injection making the agent run a socket relay) reaches the agent's forward-proxy egress: attribution sees the agent's uid, not the runner's. **Peer checks**: each listener checks who is connecting, and every adapter attributes peers to its own runners (`IntegrationRuntimeAdapter.peerAttribution()`): a per-integration listener admits only its own runner, the transparent plane uses the peer's runner policy and refuses any other peer, and the agent's forward proxy refuses runner peers. Every such refusal is logged with `reason: "peer-not-allowed"` — as `integration egress event`, `integration mitm event` (`connect-rejected`), `transparent egress event`, or `forward proxy event` (`request-refused` / `tunnel-refused`, with the target and the peer address) for the agent's proxy. A failed lookup refuses the peer everywhere. _Docker_: every runner is on the same per-run bridge as the agent and the other runners, so `runner-peers.ts` maps a peer IP to the runner container it belongs to (registered at spawn, resolved lazily through `docker network inspect`). With no runner registered the lookup makes no Docker call (every peer is "not a runner", so the agent's proxy works); an IP that is not a registered runner's is "not a runner"; only a failed `docker network inspect` refuses the peer. _Process mode_: runners share `127.0.0.1` with the sidecar and the agent, so the process adapter tells them apart by uid instead: each runner execs on a uid of its own from the `APPSTRATE_RUNNER_UIDS` pool, and a peer is attributed through `/proc/net/tcp` — the ESTABLISHED row keyed by the connection's exact 4-tuple (peer end as local, listener end as remote) names the uid owning the client socket (`socketOwnerUid`). A uid outside the pool is "not a runner"; a pool uid no runner holds, no matching row, or an unreadable table refuses the peer. The guest firewall gives the pool loopback only, so every route out of a runner crosses one of these listeners (`FIRECRACKER.md` → guest firewall). The MITM listener's inner TLS servers (one per upstream authority, `host:port`) inject credentials into whatever reaches them and check no peer themselves, so they listen on unix sockets in a 0700 sidecar-owned directory, not on a loopback port: no process sharing the loopback (a runner, the agent) can reach one except through the outer listener's peer check.
- **A local integration runner is only as isolated as the thing that spawned it**: a `source.kind: "local"` integration runs third-party bytes, and the sidecar holds the run's whole credential surface in its own environment (platform API key, run bearer token, proxy basic-auth, every connected integration's decrypted tokens). The docker adapter puts a container between the two; the Firecracker guest supervisor puts a microVM plus a uid per runner (it sets `APPSTRATE_RUNNER_EXEC` to a setuid wrapper every runner execs through, and `APPSTRATE_RUNNER_UIDS` to the uid pool that wrapper accepts). Host process mode has neither: the runner would be a plain same-uid child, and a same-uid process reads its parent's environment out of `/proc/<pid>/environ` in one syscall. **The env allowlist in `SubprocessTransport` does not close that** — it bounds what the sidecar HANDS the child, not what the child can reach — and no portable primitive fixes it (user namespaces / `PR_SET_DUMPABLE` / `hidepid` / landlock / seccomp are Linux-only and unreachable from Bun, and `Bun.spawn` exposes no `uid`/`gid` option at all — passing one neither errors nor takes effect — so a "mitigation" there would be a false assurance rather than a boundary). So the boundary is admission, not scrubbing: `integration-runtime-adapter-process.ts` **refuses to spawn** a local runner unless `APPSTRATE_RUNNER_EXEC` names a regular file carrying the setuid bit and `APPSTRATE_RUNNER_UIDS` parses as a `<first>-<last>` uid range (the setuid bit is what is checked because a file without it cannot change the child's uid, whatever it does once running — any executable, `/usr/bin/env` included, would otherwise pass and leave the runner on the sidecar's uid), and the refusal names the remedies (`INTEGRATION_RUNTIME_ADAPTER=docker` while the run itself stays in process mode, `RUN_ADAPTER=docker`, or `RUN_ADAPTER=firecracker`). It costs almost nothing in practice: of the 67 integrations shipped in `system-packages/`, 59 are `source.kind: "none"` (api_call only) and 6 are `remote` — neither spawns anything — and the two `local` ones (`@appstrate/github-git` → `@appstrate/github-git-mcp`, `@appstrate/ssh` → `@appstrate/ssh-mcp`) are both first-party. `remote` and `none` integrations keep working on the process adapter untouched.
- **Redirect handling** (`fetchApiCall`, one implementation for the platform proxy, the sidecar and the CLI resolver): manual 30x follow to capture `Set-Cookie` from every hop (#473). Three defence-in-depth rules apply to every hop (#475): (1) per-hop SSRF gate (literal + DNS, pinned) refuses redirects to loopback/RFC1918/link-local/metadata regardless of `allowAllUris`; (2) per-hop `authorized_uris` check refuses off-allowlist redirects as `unauthorized_target` (the platform proxy's 403); (3) one credential rule — a hop to an origin the allowlist names keeps the credential headers, Cookie and body (Dropbox `api ⇄ content`, Twilio `api ⇄ lookups ⇄ verify`); any other origin change strips them. Userinfo + fragment are stripped from every redirect `Location` before policy checks and before re-issuing the fetch (no attacker-injected basic-auth on the next hop). A streaming body cannot be replayed, so its 30x is returned unfollowed (the credential stays on the initial, allowlist-checked origin); only the platform proxy sends one. Every exchange has a 30 s deadline (`API_CALL_TIMEOUT_MS`).
- **Sticky-cookie jar scoping** (`cookieScope`, `packages/afps-runtime/src/resolvers/cookie-jar.ts`, shared with the platform credential proxy): a `Set-Cookie` lands in the bucket of the origin that sent it — each redirect hop's own origin, host-only as in RFC 6265, never the initial target's — keyed by `(credential scope, gate, origin)`. The credential scope is the integration id plus the bound connection id (`credentialScope`, `runtime-pi/sidecar/credential-proxy.ts`), so two connections of one integration never share a cookie nor a persistent-401 verdict (`reportedAuthFailures`). A cookie keeps its expiry — `Max-Age` (capped at 400 days, RFC 6265bis), else `Expires` (RFC 6265 §5.2.1–5.2.2), as an absolute time taken at capture — and an expired one is never sent (checked when the header is composed, purged from its bucket at that bucket's next capture); one with neither attribute lives as long as the jar (the run in the sidecar, the `X-Session-Id` session on the platform). A call sends ONE `Cookie` header, by name: sibling-origin cookies < the injected credential / caller cookies < the target's own-origin cookies, so a rotated session sticks, a deleted or expired one falls back to the credential, and no other host can override it. Sibling origins are folded in only when both hosts are named LITERALLY by a declared `authorized_uris` entry (`hostLiterallyAllowlisted`, the manifest half of the SSRF exemption); `allow_all_uris` and a glob-matched host (`https://**`, `https://*.myshopify.com/**`) keep strictly origin-scoped buckets, since the host is agent-chosen there. A cookie captured over https never reaches a non-https request (RFC 6265 `Secure`, applied to every https-captured cookie since only the expiry is stored, not the `Secure` attribute), so neither a literal `http:` sibling nor an https→http redirect carries it in cleartext. Cookies are host-only — `Domain` is ignored: a cookie `id.vendor.example` sets with `Domain=vendor.example` does not reach `www.vendor.example` unless both hosts are literal `authorized_uris` entries (the remedy: list both). Honouring `Domain` safely would need the Public Suffix List, and the glob / `allow_all_uris` case is exactly the cross-tenant boundary. `Path` is ignored likewise: a same-name cookie scoped to another path shadows the injected one on every path of that origin. A bucket keeps at most 50 cookies (RFC 6265 §6.1's per-domain floor), evicting the least recently set names, so an upstream minting per-request names cannot grow the header into a 431. The redirect follower composes every hop's header, the first included, from the call's uncomposed `Cookie`, so a cookie deleted mid-chain falls back on the next hop; once it strips credentials on a cross-origin hop, that `Cookie` is dropped for the rest of the chain. The `substitutesCredential` guard does not cover replay — a replayed cookie carries no `{{field}}` template — and for `connect.tool` session integrations the cookie IS the whole credential.
- **Upstream rejection streak**: a 401 on an injected credential goes to the platform `/refresh` (one per connection per run on `api_call`, `reportedAuthFailures`; the per-auth cooldown on the MITM), which counts it against a credential it cannot refresh and answers `502` below `INTEGRATION_REFRESH_MAX_FAILURES`, `410` once flagged. The count is a streak that a success ends: the credentials source (`integration-credentials-source.ts`) holds a pending streak — `rejection_streak` in the boot payload, or a `502` it received for a non-OAuth2 auth in this run — and the first 2xx on the injected credential afterwards, from the `api_call` tool, the MITM listener or the remote-HTTP transport, sends ONE fire-and-forget `POST /internal/integration-credentials/{scope}/{name}/upstream-success?connection_id=…` (`reportUpstreamSuccess`), which resets the count. With nothing pending the sidecar sends nothing; a caller-override header or a credential the agent substitutes itself (`credentialInjection` other than `inject`) reports neither a rejection nor a success. The source holds the payload's `credential_revision` and sends it on both calls; a `200` from `/refresh` replaces the payload and its pending streak (it may hold a credential that replaced the one in use). A success report that is refused or fails is logged and not retried (the next run's boot payload announces the streak again), and the remote-HTTP transport reports only when the final response came from the origin the credential was sent to.
- **Upstream metadata envelope** (`_meta["dev.appstrate/upstream"]`): every `{ns}__api_call` `CallToolResult` carries `{ status, headers }`. `status: 0` = no upstream response reached the agent: the sidecar answered itself, with its failure code on `_meta["dev.appstrate/api-call-error"]` when it has one. `headers` = allowlisted projection (no Set-Cookie, no Authorization).
- **Proxy cascade**: Outbound requests route through proxies in priority order: agent-supplied `proxyUrl` arg → `PROXY_URL` env var (infrastructure). Agent-level and org-level proxy config is resolved by the platform before container creation.
- **Transparent pass-through**: Sidecar forwards upstream responses as-is (HTTP status code + body + Content-Type). Truncation (>50KB) signaled via `X-Truncated: true` header. A failure the sidecar answers itself (credential fetch, URL policy, unreachable upstream) is an `isError` result with upstream `status: 0`, never a 4xx/5xx.
- **Prompt building**: `renderPlatformPrompt()` (in `@appstrate/afps-runtime`) generates the 9-section preamble (User Input, Configuration, Pinned slots, …) + appends raw `prompt.md`. No Handlebars. Memory archive and run history are NOT rendered as prompt sections — they are exposed as MCP tools (`recall_memory`, `run_history`) whose descriptions self-document the capability.
- **Output validation**: If `output.schema` exists, it is handed to the sidecar (`SidecarLaunchSpec.outputSchema` → its `OUTPUT_SCHEMA` env var) and becomes the input schema of the `output` runtime tool (`runtime-tool-defs.ts`) — the model sees the exact JSON Schema in the tool definition and the call is AJV-validated sidecar-side. At ingestion, AJV re-validates the result against `output.schema` (replace-on-emit semantics, `tool-output@2.0.0`). On mismatch, the run is marked **failed** (no silent warning).
- **Unified memory surface (#273)**: a single `package_persistence` table (Drizzle) with `(actor_type, actor_id)` scope (`member` / `end_user` / `shared`) and two orthogonal attributes `(key, pinned)` covering 3 quadrants: archive (key=null, pinned=false — written via `note(content)` built-in runtime tool, read via `recall_memory` MCP tool), pinned memo (key=null, pinned=true), and pinned named slot (key=`<string>`, pinned=true — written via `pin(key, content)` built-in runtime tool, read by the prompt builder). The platform exposes `pinned: Record<string, PinnedSlot>` on `RunResult`; `runs.checkpoint` (DB) is preserved but only as the per-run snapshot consumed by the `run_history` MCP tool. Legacy `runs.state` + `package_memories` table + the standalone `/memories` REST surface + the `memories:read|delete` permission are gone — superseded by `package_persistence` and the unified `persistence:read|delete` permission. REST surface: `GET /api/agents/{scope}/{name}/persistence?kind=pinned|memory` (list/aggregator), `DELETE …/persistence?kind=…` (bulk), and `DELETE …/persistence/memories/:id` + `DELETE …/persistence/pinned/:id` (per-row).

### Reserved `_meta` vocabulary (`dev.appstrate/*`)

All first-party MCP `_meta` keys are reverse-DNS namespaced under `dev.appstrate/` (AFPS §2.2 / Appendix B). They split into two surfaces — tool-**descriptor** markers (stamped on `tools/list` entries) and tool-**result** keys (carried on `CallToolResult._meta`). Every key name below is verified against its code constant; the constant is the source of truth.

**Tool-descriptor markers** (`packages/mcp-transport/src/tool-meta.ts`) — set by the sidecar on trusted descriptors and consumed by the agent runtime (`runtime-pi/mcp/direct.ts`) to route by capability instead of pattern-matching the `{ns}__api_call` / `{ns}__api_upload` tool name. Capability detection is by key presence; the payload is load-bearing for sibling identity. `McpHost` strips both privileged markers from non-trusted MCP descriptors before they reach the runtime, so a third-party server cannot claim either capability.

- `dev.appstrate/api-call` (`API_CALL_TOOL_META_KEY`) — marks the generic credential-injecting `api_call` tool and carries `{ tool_key }`, the canonical auth-scoped key (`api_call` or `api_call__<authToken>`). The runtime wires the `fromFile` / `responseMode.toFile` resolvers onto it.
- `dev.appstrate/api-upload` (`API_UPLOAD_TOOL_META_KEY`) — marks the resumable `api_upload` tool and carries `{ api_call_tool_key }`. The runtime pairs it with the unique `api_call` carrying that key **inside the same McpHost namespace**, then wires the chunked-upload orchestrator onto it.

**Tool-result keys**:

- `dev.appstrate/upstream` (`UPSTREAM_META_KEY`, `packages/mcp-transport/src/upstream-meta.ts`) — set by the sidecar's `api_call` handler, consumed by the runtime-side parser `readUpstreamMeta()` (`runtime-pi/mcp/upstream-meta.ts`). Carries `{ status, headers }`. **MUST be present on every `api_call` `CallToolResult`, success or failure** — the runtime throws `sidecar protocol violation` on a missing payload (the pre-`_meta` compat shim is dead code; sidecar and runtime ship from the same source tree). **`status: 0` means "no upstream response reached the agent — the sidecar answered"**: a pre-flight refusal (credential fetch failure, URL not in `authorized_uris`, body too large) and an exchange that failed after bytes were sent (`upstream_timeout`, `upstream_unreachable`, a refused redirect hop) all ship `status: 0`, `headers: {}`, so the runtime can tell them from "upstream returned 5xx" without relying on the absence of `_meta`. `headers` is re-filtered through `UPSTREAM_HEADER_ALLOWLIST` on parse (defence-in-depth against a compromised sidecar).
- `dev.appstrate/api-call-error` (`API_CALL_ERROR_META_KEY`, `packages/mcp-transport/src/upstream-meta.ts`) — set by the sidecar's `api_call` handler beside a `status: 0` when its failure has a shared code (afps-runtime's `ApiCallFailureCode`: `blocked_target`, `upstream_timeout`, …), consumed by `readApiCallErrorCode()` (`runtime-pi/mcp/upstream-meta.ts`). Carries `{ code }`; the agent sees it as `[api_call status=0 code=<code>]` (`apiCallStatusLine`), or as the `code` of a `responseMode.toFile` descriptor. The CLI path (`--integrations=local`) leads the thrown error with the same line.
- `dev.appstrate/events` (`RUNTIME_TOOL_EVENTS_META_KEY`, `packages/core/src/runtime-tool-defs.ts`) — the trusted channel the platform's own runtime tools (`output`/`log`/`note`/`pin`/`publish_file`) use to surface canonical run events; consumed by the platform's event pipeline. A third-party integration has no legitimate reason to set it, so the sidecar's `McpHost` strips it from every third-party upstream result (`stripForgedRuntimeEvents`, `runtime-pi/sidecar/mcp-host.ts`) to prevent run-event forgery.

**Retired**: `dev.appstrate/token-budget` was a third tool-result key, set on every text-path result and carrying the spill accounting (`estimatedTokens`, `consumedTokens`, `decision`, `reason`, …). It is gone — the constant, the type and every attachment site were deleted, and nothing emits or reads it. It never had a reader: `callToolResultToPi` drops `_meta` on the way to Pi, so nothing agent-side ever saw it. The accounting it carried is not lost, it just lives where it is actually consulted — the sidecar's own structured logs (`runtime-pi/sidecar/README.md` → "Token-aware context budgeting"), and the outcome the agent observes is the `resource_link` a spilled result arrives as. Do not re-add it without a named reader.

Not to be confused with the **manifest-side** `_meta` vendor extensions in the same namespace (`dev.appstrate/api`, `dev.appstrate/mcp-server`, `dev.appstrate/workspace`) — those live in AFPS package manifests, not on the MCP wire; see `docs/architecture/INTEGRATIONS_RUNTIME.md` and the AFPS spec.

Per the MCP spec, clients ignore unknown `_meta` keys — adding a key to this vocabulary is wire-compatible; renaming one is a protocol break on both Docker images at once.

### The sidecar `/mcp` is not a general-purpose MCP server

It is host-header-gated to `sidecar` / `127.0.0.1` / `localhost` and has exactly one supported client: the agent runtime's MCP bridge (`runtime-pi/mcp/direct.ts`). Several `api_call` capabilities are **declared** in the tool descriptor but **implemented in that bridge**, because the sidecar has no view of the agent workspace:

| Capability                  | Declared                                             | Implemented                                                       | Against another client                                                         |
| --------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `body.fromFile`             | `CREDENTIAL_PROXY_INPUT_SCHEMA`                      | `runtime-pi/mcp/api-call-body-resolver.ts`                        | Hard error — the sidecar refuses an unresolved `{fromFile}` as "a runtime bug" |
| `responseMode.toFile`       | same (description says "Resolved agent-side")        | `runtime-pi/mcp/api-call-response-resolver.ts`                    | Silent no-op — the handler never reads the field                               |
| `{ns}__api_upload`          | full descriptor, so it cannot drift from the runtime | `runtime-pi/mcp/api-upload-extension.ts`                          | Hard error — the sidecar handler is advertise-only                             |
| `api_upload` `connection`   | injected by `McpHost` on `api_upload` and `api_call` | `runtime-pi/mcp/api-upload-resolver.ts` (put back on every chunk) | Hard error — the sidecar handler is advertise-only                             |
| workspace resource spilling | not declared                                         | `packages/runner-pi/src/runtime-tools/resource-spill.ts`          | Resources stay as `resource_link`s, never materialised                         |

This is a deliberate trade-off — the descriptors live next to the credential proxy so they cannot drift from it — and it is safe only because the bridge is the sole client. **Do not point a generic MCP client at this server**, and do not add a capability that depends on the bridge without adding a row here.

The converse rule governs the result shape. `api_call` declares **no `outputSchema`** and attaches **no `structuredContent`** on the inline path (issue #876). Declaring an `outputSchema` makes the MCP SDK client demand a `structuredContent` on every non-error result; the sidecar then attached `{ status }`, which does not mirror `content`, and clients that prefer `structuredContent` (Claude Code, VS Code) handed the model `{"status":200}` and discarded the response body. The rule: **anything the model must see lives in `content`.** `_meta` is for the bridge, and `structuredContent` is only ever a verbatim mirror of a `content` text block.

### MCP transport retry: Bun-side error codes (#critical for the integration-runtime race)

`packages/mcp-transport/src/client.ts` retries the initial `client.connect(transport)` handshake on connection-level failures (sidecar boot race, DNS not yet propagated, etc.). The retry classifier matches `err.code` against `RETRYABLE_CODES` — and that set **must include both Node and Bun naming conventions**:

- **Node / undici**: E-prefix UPPER_SNAKE_CASE (`ECONNREFUSED`, `ENOTFOUND`, `ETIMEDOUT`, …)
- **Bun fetch**: PascalCase, no E-prefix (`ConnectionRefused`, `ConnectionTimeout`, `DNSNotFound`, …)

Missing Bun aliases means `isFatalConnectError()` would classify a Bun-side `ConnectionRefused` as fatal (the `TypeError` fallback fires when no recognised retryable code is found) and bypass the retry loop entirely. The agent container would then fail its very first MCP handshake against a still-booting sidecar instead of riding through the warm-path race window (~50-200ms). The container-per-integration path made this race much more visible because spawning a runner container before answering the agent's `tools/list` extended the sidecar's warm-up window.
