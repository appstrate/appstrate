# AFPS Integrations — Runtime

Operational narrative for the integration runtime (env-delivery, container-per-integration, MITM credential injection, niveau-2 scope model, remote HTTP MCP). AFPS wire spec (canonical): <https://github.com/appstrate/afps-spec/blob/main/spec.md>.

### AFPS Integrations runtime (Phase 1.4, env-delivery + container-per-integration)

AFPS integrations with `source.kind: "local"` declare `source.server.{name, version}` pointing to an `mcp-server` package. The mcp-server's `server.type` (`node` | `python` | `binary` | `uv`, all MCPB-vocabulary values) and `server.entry_point` (snake_case per AFPS §3.4) determine the runtime image. The Bun runtime selection uses an MCPB-vocabulary `server.type: "node"` (since MCPB's `server.type` enum is `node|python|binary|uv` — no `bun`) + an Appstrate `_meta["dev.appstrate/mcp-server"].runtime: "bun"` override read by `integration-spawn-resolver` on the mcp-server manifest. The platform validates the agent's `dependencies.integrations[id]`, looks up the installed package + each `integration_connections` row the run's snapshot bound to it, decrypts each credential blob, and builds one `spawnEnv` per connection from `manifest.auths.{key}.delivery.env` (`apps/api/src/services/integration-spawn-resolver.ts`). The resolved spawn plan is serialized into `INTEGRATIONS_TO_SPAWN_JSON` on the sidecar container's env at create time — the sidecar fetches each bundle via the internal `GET /internal/mcp-server-bundle/:scope/:name` endpoint (authenticated with the run token, dep + install double-check) so we don't fight Linux env-var size limits.

The sidecar's `integrations-boot.ts` then spawns one MCP server **per spawn spec — i.e. per BOUND CONNECTION**, one per integration in the ordinary single-connection case — in its own runner container:

```
sidecar (Bun, +docker-cli, /var/run/docker.sock mounted, runs as root only when integrations.length > 0)
  ├─ readIntegrationSpecsFromEnv()                  ← INTEGRATIONS_TO_SPAWN_JSON
  ├─ selectIntegrationRuntimeAdapter()              ← INTEGRATION_RUNTIME_ADAPTER (set by the launching
  │                                                    orchestrator to mirror RUN_ADAPTER; no auto-detection)
  ├─ adapter.prepare(runId)                         ← returns { listenerBindHost, proxyUrlFor(port) }
  │
  ├─ for each spec:
  │     ├─ fetchBundleBytes()                       ← platform /internal/mcp-server-bundle/...
  │     ├─ extractBundle() → /tmp/afps-integ-{ns}-XXX/  ← fflate unzip in-sidecar
  │     ├─ adapter.spawn({ runId, spec, bundleRoot, mitm })
  │     │     ── docker adapter ──
  │     │     RUNNER_IMAGE_BY_TYPE[server.type]:
  │     │       node   → appstrate-mcp-runner-node:latest    (75 MB)
  │     │       python → appstrate-mcp-runner-python:latest  (49 MB)
  │     │       binary → appstrate-mcp-runner-binary:latest  (11 MB)
  │     │     docker create --rm -i --cap-drop ALL --memory 256m --pids-limit 128 \
  │     │         --network appstrate-exec-<runId> -e <spawnEnv...> \
  │     │         --label appstrate.run=$RUN_ID --label appstrate.managed=true \
  │     │         <image> /bundle/<entry_point>
  │     │     docker cp /tmp/afps-integ-{ns}-XXX/. <id>:/bundle/
  │     │     docker cp <ca.pem> <id>:/tmp/appstrate-ca.pem      ← MITM only
  │     │     → SubprocessTransport(["docker","start","-ai",<id>])
  │     │     ── process adapter (Firecracker guest / tests) ──
  │     │     HOST_INTERPRETER_BY_TYPE[server.type]:
  │     │       node → "node", python → "python3 -u", binary → exec entry directly
  │     │     → SubprocessTransport({ command: $APPSTRATE_RUNNER_EXEC,
  │     │         args: [--workspace?, <pool uid>, command, ...args], cwd, env: { ...spawnEnv, ...mitmEnv } })
  │     ├─ Client.connect → initialize → tools/list   ← MCP handshake
  │     └─ McpHost.register({ namespace, client })    ← tools exposed to the agent as {ns}__{tool}
  │
  └─ on shutdown: close MCP clients → adapter.shutdown() → close MITM listeners → unlink CA file
```

Key invariants:

- **Sidecar minimal by design**: no `node`, no `python`, no `bun` baked in. Adding a new language is one `runtime-pi/runners/<lang>/Dockerfile` + one entry in `RUNNER_IMAGE_BY_TYPE` (in `integration-runtime-adapter-docker.ts`) — the sidecar image (132 MB) doesn't grow.
- **Bun runtime via `_meta` (MCPB-vocabulary `server.type` preserved)**: MCPB's `server.type` enum is `node|python|binary|uv` — no `bun`. The mcp-server manifest is AFPS-native at the root with MCPB-vocabulary fields (`server` / `tools` / `user_config`) carried verbatim — NOT a strict-MCPB manifest (AFPS dropped that interoperability claim; a publish-time projection to strict-MCPB is reserved for a future minor, see AFPS §3.4 + §10.2). A bun-native server therefore keeps an MCPB-vocabulary `server.type: "node"` and declares the real runtime under `_meta["dev.appstrate/mcp-server"].runtime: "bun"`. `integration-spawn-resolver` reads the override (`getMcpServerRuntime` in `@appstrate/core/mcp-server`) and falls back to `server.type` when absent — so the effective runtime drives both `HOST_INTERPRETER_BY_TYPE["bun"]` (process mode, host subprocess, no Docker) and `RUNNER_IMAGE_BY_TYPE["bun"]` (docker mode, dedicated `appstrate-mcp-runner-bun` container with full cgroup/cap-drop/network isolation). The override lives on the mcp-server manifest only — the integration manifest carries auth/policy + the `source.server` reference, never server/runtime fields. There is deliberately NO in-process-bun-inside-the-docker-sidecar path: the sidecar runs as root with the Docker socket mounted when integrations are present, so running third-party bun code in its process tree would hand it root + socket → host-escape surface. Containerising bun in tier 3 keeps the security boundary intact.
- **Pluggable runtime adapter** (`integration-runtime-adapter.ts`): the sidecar's `bootIntegrations` is orchestrator-agnostic. `selectIntegrationRuntimeAdapter()` picks the adapter purely by `id` from `INTEGRATION_RUNTIME_ADAPTER` — **no availability probing / auto-detection**. The platform orchestrator that launches the sidecar sets it to mirror its own `RUN_ADAPTER` (`docker-orchestrator` → `docker`, `process-orchestrator` → `process`), so the integration runtime deterministically matches the run runtime and the sidecar never guesses its backend (an earlier `docker info` auto-probe selected Docker for a process-mode run whenever a daemon was reachable — removed). Each adapter owns: how to spawn the runner, what host the MITM listener should bind to (`listenerBindHost`), what URL the runner uses to reach it (`proxyUrlFor(port)`), where the CA cert lands inside the runtime, and how to tear down. Adding Firecracker is one new `integration-runtime-adapter-firecracker.ts` that calls `registerIntegrationRuntimeAdapter({ id, create })` plus teaching the orchestrators to emit that id — nothing in `integrations-boot.ts` changes. The var is also an operator override (both orchestrators honour a value already in the environment).
- **Docker socket gated by need**: `docker-orchestrator.createSidecar` only adds `binds: ["/var/run/docker.sock"]` + `user: "0:0"` when `spec.integrations.length > 0`. Runs without integrations keep the default `nobody:nobody` user with no socket.
- **Bundle delivery is HTTP, not env**: `INTEGRATIONS_TO_SPAWN_JSON` carries only manifest metadata + decrypted spawn env. Bundle bytes (potentially several MB) ship out-of-band via `GET /internal/mcp-server-bundle/:scope/:name`.
- **mcp-server resolves to ONE concrete version — manifest and bytes never skew (#588)**: `integration-spawn-resolver` resolves `source.server.version` to a single published version via the canonical exact → dist-tag → semver-range resolution (`resolveMcpServerForSpawn` in `integration-service.ts`), reads THAT version's manifest from `package_versions.manifest`, and stamps the resolved version onto `spec.manifest.server.version` (alongside `server.packageId`). The sidecar forwards it as `GET /internal/mcp-server-bundle/:scope/:name?version=…`, so the runnable bytes come from the same version as the manifest the resolver read. This closes the prior split where the manifest was read from `packages.draft_manifest` (version-blind) while the bytes came from the latest non-yanked version (pin-blind, and independent of the manifest) — a `publish` that didn't also overwrite the draft left the run executing one version's bytes under another version's manifest ("publish ≠ deploy" footgun). An unsatisfiable pin or an mcp-server with no published version **skips the integration with a loud structured warning** rather than silently running on whatever bytes are latest. System mcp-servers (boot registry, single version) carry no `server.version` and are served by id alone — the only case in which `?version=` may be absent. For any other mcp-server the byte route rejects an absent `?version=` with a 400 rather than serving whatever is newest, so the closed skew cannot reopen through the byte route itself.
- **Auto-cleanup**: `docker create --rm` auto-removes the container when stdio closes; the docker adapter's `shutdown()` is the explicit-kill belt-and-suspenders path for misbehaving servers; orphan reaper sweeps anything missed by `appstrate.managed=true appstrate.run=<runId>`.
- **Process mode**: when the run is launched by `process-orchestrator` (`RUN_ADAPTER=process`, sidecar a host subprocess), it pins `INTEGRATION_RUNTIME_ADAPTER=process` and the process adapter spawns integrations as host subprocesses (`node`/`python3`/… against the host PATH) — same MCP wire, no container isolation. It spawns a `source.kind: "local"` runner only through a setuid `APPSTRATE_RUNNER_EXEC` wrapper onto a uid of its own from the `APPSTRATE_RUNNER_UIDS` pool, which only the Firecracker guest supervisor provides; host process mode refuses the spawn (`docs/architecture/SIDECAR.md` → "A local integration runner is only as isolated as the thing that spawned it"). Tests run in this mode (they set the var explicitly, with a pass-through fixture wrapper).
- **MCPB-vocabulary `server.type` preserved**: the `server.type` field uses the MCPB vocabulary exactly (`node|python|binary|uv`). The mcp-server manifest as a whole is AFPS-native, not strict-MCPB, so `.afps` bundles are NOT drop-in installable as `.mcpb` extensions in strict-MCPB hosts; a publish-time projection to a strict-MCPB bundle is reserved for a future AFPS minor (§3.4 + §10.2).
- **Tools surfaced to the LLM**: the sidecar's `McpHost` multiplexes spawned tools under a namespaced prefix (`{namespace}__{tool}`). The agent's `runtime-pi/mcp/direct.ts` discovers them via `tools/list` and registers one Pi extension per advertised non-first-party tool that forwards verbatim to `mcp.callTool`. **The per-connection selector**: a run binds a SET of connections per integration (connection model, below), and a namespace holding more than ONE gets a REQUIRED `connection` property injected on each of its tools — `type: "string"`, `enum` = the labels of the connections serving that tool (a single label when only one does), description pairing every label with its `accountId` so an opaque label is still tellable apart (`withConnectionParam`, `mcp-host.ts`). Dispatch is keyed by `(tool name, connection label)` — per-tool, not per-namespace, since `intoNamespace` lets one namespace aggregate tools from several clients — and the host strips the selector before forwarding; an absent or unknown value comes back as a tool-level error listing the labels, never as a guessed connection. The N connections serving one upstream tool share ONE advertised descriptor: sibling routes are keyed by the upstream tool's original name, so the name the first connection registered is the one the others join. A namespace holding a SINGLE connection is advertised exactly as its upstream declared it, byte-identical to the one-connection model — the degenerate case, not a mode. No tool of a namespace holding several connections may declare a `connection` property of its own, even one a single connection serves: `register` throws `connection_param_conflict` before indexing anything (the integration lands in the boot report's `failed[]`, which aborts the run) rather than shadowing the upstream's parameter.
- **Two gates, not one — the platform DROPS and marks, the sidecar ABORTS**: an integration can fail to reach a run at two different moments, and they are resolved in opposite directions on purpose. **Platform side (run kickoff, `integration-spawn-resolver.ts`)**: `resolveIntegrationSpawns` returns `{ specs, dropped }`, and a declared integration that cannot be resolved is DROPPED — the run still starts, with the subset that resolved. "Run with what you have" is a supported product mode (the pre-flight picker models unconnected integrations explicitly — the readiness verdict's `error_code`), so this must not throw. It is no longer silent, though: every drop travels back to `run-context-builder.ts` → `run-pipeline.ts`, which writes one `warn` `run_logs` row per drop as the `integration_dropped` event (`INTEGRATION_DROPPED_EVENT`), carrying `integrationId`, a machine-readable `reason`, an optional `detail` and, when the drop is about one bound connection, its `connectionLabel` — the drops of one bound set share `integrationId` and differ by label. It is written right after `createRun` (the `run_logs.run_id` FK forbids writing it any earlier, since the context is built BEFORE the run row), awaited so it is ordered ahead of the container's own logs, and best-effort — a failed marker write is logged, never allowed to fail a kickoff. Without it a run that started with a subset of its tools is indistinguishable from an agent that simply chose not to call them. The `reason` vocabulary is exactly one value per drop site in `resolveOne` — `not_found`, `not_integration`, `invalid_manifest`, `not_active`, `remote_source_invalid`, `local_server_ref_missing`, `mcp_server_unresolved`, `mcp_server_not_runnable`, `no_delivery`, `bound_set_incomplete`, `resolve_error` — and `no_delivery` is deliberately the one bucket that collapses several server-side causes (missing connection, decrypt failure, no delivery mapping), because from the operator's seat they all mean "no usable credential". **A bound set is spawned whole or not at all**: when one member of a set of two or more connections yields no delivery, the integration is dropped entirely — the lost member marked `no_delivery`, every survivor `bound_set_incomplete` — because a lone survivor gets no `connection` selector and would silently take every call meant for the lost member. Two cases are not drops: an integration the cascade left unbound because its effective tool selection is empty is skipped with no marker (nothing to expose), and an integration that exposes tools while the run's snapshot binds no connection to it is a `resolve_error`. One case is NOT a drop and never was: an unsatisfiable `source.server.version` pin raises `DEPENDENCY_UNRESOLVED` and fails the whole run with a structured 422 (#686) — a pinned run must never silently spawn without the integration.
- **Sidecar side: boot IS a hard gate — a declared integration that doesn't start aborts the run, every tier**: past kickoff the calculus flips. The platform decided this integration WOULD be there, so a spawn/connect failure inside the sidecar is a broken promise, not a degradation the product offers. `bootIntegrations` records an `IntegrationBootReport` (`@appstrate/core/sidecar-types`) — `ok`, `declaredConnections`, `adapter`, `spawned[]`, `failed[]`, and an ordered, timed `breadcrumbs[]` trail (runtime adapter, MITM CA, per-connection `spawn Xms · connect Yms · ready` / `failed`). Entries are per BOUND CONNECTION, not per integration: `spawned[]` carries `connectionLabel` (and `failed[]` optionally does), an agent-run spec that binds no connection lands in `failed[]` rather than spawning an uncredentialed runner, and each breadcrumb is labelled `{integrationId} [{label}]`, so an integration bound to two connections contributes two attributable trails and a half-failed boot names which half. The sidecar serves it at `GET /integrations/boot-report` (agent-authenticated like `/mcp`, with the run's `x-appstrate-sidecar-auth` token — the per-run network is NOT a boundary, integration runners share it; see `docs/architecture/SIDECAR.md` → “Agent authentication” — and it awaits the boot promise so the answer is final). After the MCP handshake the agent (`runtime-pi/entrypoint.ts`) fetches the report, relays every breadcrumb into `run_logs` as `appstrate.progress` events (`emitBootProgress` in `@appstrate/runner-pi`), and **`die()`s the run** (`failed`) when `ok` is false or the report can't be fetched within `BOOT_REPORT_DEADLINE_MS` (60 s). A runner that cannot start (a missing `python3`, say) therefore fails the run instead of leaving an empty toolset the LLM reports as "not connected". The agent also emits `bundle loaded` + `MCP connected` breadcrumbs of its own; `emitRuntimeReady`'s `runtime ready in Xms` stays the terminal line.

### AFPS Integrations MITM credential injection (Phase 1.5, `delivery.http`)

When an integration's `manifest.auths.{key}.delivery.http` declares a header (`api_key`, `oauth2`, `basic`, `mtls`, `custom` — see AFPS §7.2), Phase 1.5 routes its upstream HTTPS calls through a MITM proxy hosted **inside the sidecar**, one per spawn spec (per bound connection, so two connections of one integration never share a listener or a credential cache). The same holds for the sidecar's `api_call` session state: its sticky-cookie jar and its persistent-`401` verdicts are keyed by (integration, connection) (`credentialScope`, `credential-proxy.ts`), so a cookie captured through one connection is never replayed on another and one connection's auth failure does not suppress another's refresh. The integration's MCP server never reads the credential — the proxy injects the configured header on the way out, refreshes the underlying OAuth2 token transparently when it nears expiry, and recovers from a mid-run `401` by force-refreshing and retrying once.

```
sidecar
  ├─ planCaBundle() + createOpensslCertGenerator()   ← per-run CA, openssl-backed
  ├─ createCertMinter({ caCert, caKey })             ← lazy per-SNI leaf certs
  ├─ for each SPAWN SPEC (one per bound connection) with httpDeliveryAuths:
  │     ├─ GET /internal/integration-credentials/<id>?connection_id=<uuid>  ← initial payload
  │     ├─ createIntegrationCredentialsSource()                  ← cache + refresh hook
  │     ├─ createIntegrationMitmListener() (binds 0.0.0.0 in Docker mode) ← one inner Bun.serve per upstream authority (host:port), each on a unix socket (0700 dir)
  │     └─ docker create … --network appstrate-exec-<runId>     ← per-run bridge, DNS alias `sidecar`
  │             -e HTTPS_PROXY=http://sidecar:<port>
  │             -e NODE_EXTRA_CA_CERTS=/tmp/appstrate-ca.pem
  │             -e SSL_CERT_FILE / REQUESTS_CA_BUNDLE / CURL_CA_BUNDLE
  │        docker cp <ca.pem> <id>:/tmp/appstrate-ca.pem
  │
  └─ on upstream 401:
        listener.refreshOnUnauthorized(authKey)
          → POST /internal/integration-credentials/<id>/refresh?connection_id=<uuid>
          → swap in-cache payload, retry the upstream call once
```

Platform surface:

- `GET /internal/integration-credentials/{scope}/{name}?connection_id=<uuid>` — live credentials + `HttpDeliveryPlan` per auth + `expires_at`. OAuth2 tokens refresh proactively when within `OAUTH_REFRESH_LEAD_MS` of expiry. Auth: same Bearer run-token as `/mcp-server-bundle`. Same dep-and-activation guard (the running agent DECLARES the integration and the space has it ACTIVE) so a leaked token can't enumerate credentials across the org. `connection_id` is REQUIRED on both routes and must be one the run's `resolved_connections` snapshot bound for that integration — `400` otherwise, naming the bound ids. There is no "the run's connection" left to default to, and a run token therefore cannot reach a connection its own kickoff did not bind.
- `POST /internal/integration-credentials/{scope}/{name}/refresh?connection_id=<uuid>` — force-refresh the named connection's credential, never another connection of the integration. `410` when it cannot be recovered — a revoked refresh token, or an OAuth2 connection holding no refresh token — with the connection flagged `needsReconnection` and the failure stamped on the run; the sidecar stops retrying and the integration receives the upstream `401` unchanged. An auth nothing can refresh (not OAuth2, or OAuth2 with no refresh client) is counted instead, since one `401` can be a transient upstream fault: `502` while fewer than `INTEGRATION_REFRESH_MAX_FAILURES` consecutive rejections are counted, then `410`, flagged, like the above. The count is a streak, not a window: a successful (2xx) call through the credential ends it (`clearUpstreamRejections`, a non-OAuth2 connection only — an OAuth2 count tracks refreshes), so a dead key is flagged on its Nth rejected run however far apart the runs are, and a working key that sometimes gets a 401 is not. Two counts have no success to end them and accumulate until a reconnect: an OAuth2 connection whose refresh cannot run (no resolvable client, no token endpoint), and a local MCP server that reports a rejected credential through the `dev.appstrate/credential: rejected` tool-result meta (e.g. `@appstrate/ssh` — its successes cross no proxy). "Consecutive" is approximate besides: the sidecar's success report is best-effort, one fire-and-forget call per streak it knows of. The platform credential proxy (`/api/credential-proxy/proxy`) counts its unrefreshable 401s through the same `recordUnrefreshableRejection`, relaying the upstream `401` unchanged, and ends the streak on a 2xx itself. `/refresh` takes `credential_revision`, the revision of the rejected credential (from the payload): when the connection no longer holds it, the forced refresh is a plain read — `200` with the current credential, nothing refreshed or counted. Without it (a local MCP server with no credentials source), the rejection counts against the current credential.
- `POST /internal/integration-credentials/{scope}/{name}/upstream-success?connection_id=<uuid>&credential_revision=<rev>` — `204`; ends the named connection's rejection streak, on that credential only. Same run-token, dependency and bound-connection checks as the GET; the reset is one UPDATE scoped to the run actor's reach (own or shared, same space and integration) and to that revision, so nothing is reset with no actor, lost reach, a replaced credential, or a connection already flagged `needsReconnection`. A connect run gets `409 connect_run_no_refresh`. The GET and `/refresh` payloads carry `credential_revision` (a short sha256 of the stored ciphertext: every credential write changes it, and so does a re-key, which only makes one verdict miss) and, while a non-OAuth2 connection has one, `rejection_streak` (on the GET, and on a `/refresh` `200` that answers a superseded revision with the current credential; a non-OAuth2 forced refresh otherwise answers `502`/`410`, and an OAuth2 connection has no streak). The sidecar calls this once, fire-and-forget, on the first 2xx after a streak it knows of (announced at boot, or counted by a `/refresh` `502` in this run).

Refresh helper: `apps/api/src/services/integration-token-refresh.ts:forceRefreshIntegrationConnection` mirrors `@appstrate/connect/token-refresh.forceRefresh` (which targets `user_provider_connections`) but writes back to `integration_connections`. Same `RefreshError` taxonomy (`revoked` vs `transient`); `invalid_grant` flips `needsReconnection`.

Key invariants:

- **Network model**: each run gets its own user-defined bridge network `appstrate-exec-<runId>` (created by the platform launcher, sidecar attached with alias `sidecar`). Runner containers join the same network and reach the MITM listener via Docker's embedded DNS (`http://sidecar:<port>`). The earlier attempt to share the sidecar's network namespace via `--network container:<id>` was abandoned because `docker start` raced against the daemon's short-id lookup on Docker Desktop, frequently leaving the runner stuck in `Created`. Process mode inherits the parent's NS — `127.0.0.1:<port>` reaches the listener directly.
- **Egress is a per-connection allowlist (#1458)**: a local runner reaches only what its connection's `authorized_uris` grant, **rendered** for that connection. The platform sets `IntegrationSpawnSpec.egress = { authorizedUris, allowAllUris }` for every local runner whose resolved auth declares `authorized_uris` or `allow_all_uris`, whatever its delivery: the MITM listener for `delivery.http`, otherwise the CONNECT listener + transparent plane (`mtls` included), and `connect.tool` login runners too. No `egress` means no egress route at all. A pattern may reference connection fields as `{$credential.<field>}` (e.g. `ssh://{$credential.host}:{$credential.port}`), rendered by `renderAuthorizedUris` (`@appstrate/afps-shared`). Import validation (`packages/core/src/integration.ts`) allows two forms: placeholders in the host and port of a `scheme://` entry, or the **URL form** — exactly one `{$credential.<field>}` at index 0, then nothing or a placeholder-free suffix starting with `/` (`{$credential.site_url}/**`, `{$credential.webhook_url}`). Every referenced field must be declared AND `required` in `credentials.schema`; credential templates are forbidden on an `oauth2` auth and on an auth that declares `connect`, and allowed on one exposing `api_call` (#1627). A pattern may also reference a connection variable as `{$variable.<name>}` — on an `oauth2` or `connect` auth too, provided the entry shares the origin of the URL template that chooses the upstream its credential is for (a templated `source.remote.url`, else a templated oauth2 `issuer`) — rendered under the rules of "connection variables" below. At render time a host/port value outside `[A-Za-z0-9.-]` (so no `*`, `/`, `:`, `@`, whitespace), a value made only of dots, or a missing field DROPS the pattern; a URL-form value renders only when it is an absolute `http(s)` URL without userinfo, `#`, an empty `?` or `*`, and without a query unless the entry is the bare placeholder — an exact match the query cannot widen (origin + path + query; before a suffix, one trailing `/` is dropped), otherwise the entry is dropped. A connection whose submitted value would drop an entry is refused at connect time (`FieldsStrategy`, 400 `validation_failed` naming the field). An empty result denies everything. Invariant: every `api_call` path (sidecar, local resolver, platform proxy) matches the target against the RENDERED list, while the SSRF-exempt pins (a literal `api_call` host) and cookie sharing come from the DECLARED literal hosts only — a user-supplied value never becomes a pin. A manifest cannot protect against its own author; rendering from the connection is what bounds the target to what the USER entered. A `uv` runner resolves its dependencies from the package index at startup through this same egress, so the index must be in `authorized_uris` or the bundle must vendor them. The TCP-level port rule (no explicit port = the scheme's default only), per-listener enforcement (incl. the SNI binding inside CONNECT tunnels), peer checks (by source IP in docker mode, by socket-owner uid in a Firecracker guest), and what the blind paths do not bound (CDN tenants behind a front, runner-to-runner traffic): `docs/architecture/SIDECAR.md` → "Runner egress allowlist".
- **Refresh storm protection**: per-`authKey` 5 s cooldown + in-flight dedup on `refreshOnUnauthorized` so a mis-scoped 401 (the credential is fine, the request itself is wrong) can't hammer the platform endpoint.
- **CA hygiene**: per-run CA, 1 h validity (matches max run duration), private key lives in memory on the sidecar — only the cert PEM (not the key) lands on local fs (`mode 0444`) for `docker cp`. Unlinked on `bootIntegrations().shutdown()`.
- **Graceful degradation**: if openssl is missing or CA bring-up fails, the sidecar logs `HTTP-delivery integrations will skip` and continues with env-delivery-only integrations. `delivery.env` integrations are unchanged from Phase 1.4 — credentials baked in at container create time.
- **`auths.{key}.delivery.http.allow_server_override`** (snake_case per AFPS §7.6): defaults to `false`. When the integration sets its own header of the same name as the injection target, the proxy strips it before forwarding (defence against integration code accidentally pre-empting the injection).
- **`delivery.http.encoding: "base64"`** (AFPS §7.6, opt-in): applied AFTER the `{$credential.*}` template expands but BEFORE `prefix` is prepended — the recipe for HTTP Basic auth (`{ prefix: "Basic ", value: "user:{$credential.api_key}", encoding: "base64" }` → `Authorization: Basic <b64('user:'+key)>`). In live use by several shipped system integrations (zendesk, twilio, woocommerce, freshdesk, wordpress, teamwork). Type: `ManifestDeliveryHttp.encoding?` (`integration-manifest-helpers.ts`).
- **Trust-store env block** (`buildMitmEnvBlock` in `integration-runtime-adapter.ts`): exports the per-run MITM CA path into four CA-bundle env vars so common HTTP clients trust it — `NODE_EXTRA_CA_CERTS` (Node/Bun fetch via undici), `SSL_CERT_FILE` (OpenSSL/libcurl), `REQUESTS_CA_BUNDLE` (Python requests/httpx), `CURL_CA_BUNDLE` (curl CLI) — plus the proxy vars pointing at the listener.
- **Operator observability** (`MitmListenerEvent`, `integration-mitm-listener.ts`): `request-forwarded` carries `{ url, status, authKey, retried }` (URL query string stripped — no `code=`/`token=` leak; header values are NEVER logged); `request-refused` carries `{ url, reason }` when the URL is off the connection's allowlist (`not-authorized`) or when the credential it would inject belongs to an auth whose `authorized_uris` leave the host to the caller (`credential not host-bounded`, the `credentialUrlPolicy` rule of `api_call`) — the request is answered 403 and never forwarded; `upstream-error` fires when the fetch threw before any response (TLS/DNS). `request-forwarded` only emits once a response landed.
- **Scope of the host-bound rule**: it is checked on every request that would carry an injected credential, the replay after a refresh or a `connect.tool` re-login included, and it bounds WHICH HOSTS receive the credential. It does not stop an allowlisted host from reflecting a value it received back in its response, so an `authorized_uris` list should name only hosts trusted with the credential.
- **Dev reference fixture**: `@appstrate/mitm-test` (under `local-test-packages/`, not shipped) — a pure-stdlib Python MCP server with a `call_upstream` tool that fetches `https://api.test.appstrate.dev/<path>`. Its `api_key` auth declares `delivery.http` with `X-Mitm-Test-Token`. The integration never reads the API key — proves the injection happens entirely sidecar-side.
- **`delivery.http.encoding: "base64"`** (AFPS §7.6, opt-in): applied AFTER the `{$credential.*}` template expands but BEFORE `prefix` is prepended. Recipe for GitHub git smart-HTTP (which rejects `Authorization: Bearer` and requires HTTP Basic with `x-access-token` as the username): `{ prefix: "Basic ", value: "x-access-token:{$credential.access_token}", encoding: "base64" }` → `Authorization: Basic <b64('x-access-token:'+token)>`. Same integration keeps a separate Bearer header for REST (`delivery.http` is mutually exclusive with `delivery.env` per auth, but each auth has its own delivery block).
- **Trust-store env block** (`buildMitmEnvBlock` in `runtime-pi/sidecar/integration-runtime-adapter.ts`): exports five CA-bundle env vars + four proxy vars into the runner so the per-run MITM cert is trusted by every common HTTP client family. `NODE_EXTRA_CA_CERTS` (Node fetch + Bun fetch via undici), `SSL_CERT_FILE` (libcurl, OpenSSL), `REQUESTS_CA_BUNDLE` (Python requests), `CURL_CA_BUNDLE` (curl CLI), and `GIT_SSL_CAINFO` (git — it wraps libcurl but reads its own env var and IGNORES `CURL_CA_BUNDLE` / `SSL_CERT_FILE`, so the dedicated var is load-bearing for any git-shelling integration like `@appstrate/github-git-mcp`).
- **`process.env` inheritance gotcha**: integration code that shells out (e.g. `Bun.spawn`, `child_process.spawn`) MUST spread `process.env` into the child's `env` rather than passing a fresh object — `Bun.spawn({ env: {...} })` REPLACES the env, it does not merge. Dropping the proxy + CA vars silently bypasses the MITM listener and the request fails, on both backends: in docker it fails with `Could not resolve host` (the per-run network is `internal: true`, so direct egress is blocked); in a Firecracker guest the runner uids have loopback-only egress and their DNS is redirected to `127.0.0.1:53`, where the transparent plane, once the run's first plain-CONNECT runner has started it, answers with `127.0.0.1` and then refuses a MITM-delivery runner's connections; with no plain-CONNECT runner there is no plane, and the lookup fails against an unbound port. The plane serves only a runner whose egress is the plain CONNECT kind, so a proxy-unaware client there still gets out, bounded by that runner's allowlist. Reference: the `runGit` helper in `scripts/system-packages/mcp-server-github-git-1.0.2/server/index.ts` was bitten by this and now does `env: { ...process.env, ...local }`.
- **`delivery.files` has two consumers**: `mtls` (client cert + key) and `@appstrate/ssh` (an OpenSSH private key at `/run/secrets/ssh_key`, mode `0600`). Both are read by a process running as uid 1001 in the runner image, which is why the docker adapter streams the staged tree through `docker cp -` as a USTAR archive re-owned to that uid (#1462) — `docker cp <hostdir>` stamps the sidecar's uid and an owner-only mode then locks the runner out of its own credential. The SSH server (`scripts/system-packages/mcp-server-ssh-1.0.1/server/index.ts`) is the second first-party server that shells out — to the `ssh`/`sftp` clients the bun runner image bakes in next to `git` — and it reaches a proxied target through an OpenSSH `ProxyCommand` (`server/proxy-connect.ts`) that speaks HTTP CONNECT to the sidecar's egress listener, since OpenSSH has no CONNECT support of its own. The listener tunnels only to the connection's own target: the manifest's `authorized_uris` is `ssh://{$credential.host}:{$credential.port}`, so `port` is required and `host` is a DNS name or IPv4 literal (the per-run bridge is IPv4-only). The private key never enters the agent container. **The connection's Unix account is the boundary**: `ssh_exec` hands its string to that account's login shell — SSH `exec` has no argv at the protocol level, so there is no narrower payload — and what the account may do is the whole of what an agent may do through the connection. Narrowing it (a dedicated user, sudoers, a restricted shell) is the operator's act on their own machine; the install block only authorises the key, with `restrict` and no `command=`. "Read-only" is per AGENT, not per connection: the platform's `toolAllowlist` withholds the writing tools — `ssh_exec`, `ssh_write_file`, `ssh_edit_file` — from an agent that must not change the target, so one connection serves a reader and a writer at once. Host keys are pinned (`StrictHostKeyChecking=yes` against a per-process `known_hosts` rendered from the connection's `host_key`); there is no trust-on-first-use, because nobody is present in an autonomous run to accept a key on first contact. The platform does not fetch that key — the user reads it off the target and supplies it on the connect form, from a session they authenticated themselves, which a remote scan by definition is not. The fingerprint the install block prints is read on the target too, so comparing it with the pinned one only confirms the user pinned this server's key; what guards a run against interception is `StrictHostKeyChecking` against that key. The key pair itself is minted by the platform: `services/connect/provisioning.ts` holds a code table keyed by package id and auth key (`@appstrate/ssh` / `primary`), and `readProvisioning` answers only for a package the platform loaded as a system package, so an org row carrying that id is never provisioned; no manifest declaration is read. The connect form also refuses a host the RUNNER could not reach (`isBlockedHost` on a literal, the runner's floor and not the platform's, which honours `EGRESS_ALLOW_INTERNAL_HOSTS`), so a connection is not created against an address every run would then fail on.
- **`delivery.files` under the process adapter, several connections per run**: every runner shares the host filesystem, so a declared path holds one connection's file per run. A runner whose spec declares a `delivery.files` path another connection of the run already holds is refused at spawn — it would read that connection's credential (`integration-runtime-adapter-process.ts`); an integration hardcoding its file path (the SSH integration's `/run/secrets/ssh_key`) therefore binds several connections only under the docker adapter. When the declared path cannot be written (`/run` for a non-root sidecar), the file falls back to a per-run scratch dir, `appstrate-mounts-<runId>/`, mirroring the declared path, and `APPSTRATE_FILE_MOUNT_<path>` names where it landed. The docker adapter needs none of this: each runner is its own container, and its files are copied into that container's filesystem at the declared path (`stageFileMountsOnHost`, `integration-runtime-adapter-docker.ts`).
- **Operator prerequisite for `@appstrate/ssh`: OpenSSH ≥ 7.2 on the target.** The installed key line starts with `restrict`, which an older sshd rejects, so the install block refuses an older sshd before writing anything.
- **Transparent egress for `delivery.env` runners (#779)**: the plain CONNECT egress listener (issue #543) only works for HTTP clients that honour `HTTPS_PROXY` **and** speak CONNECT — most third-party MCP servers don't (undici/`fetch` ignores proxy env vars; axios sends non-CONNECT forward-proxy for HTTPS → 405 → opaque tool timeout). In docker mode the sidecar therefore DNS-spoofs external hostnames to its own per-run IP (`--dns` on the runner container, UDP :53 responder) and blind-splices raw TLS on :443 / plain HTTP on :80 after peeking the SNI / `Host` header, checking it against the connecting runner's allowlist and applying the same SSRF floor as the CONNECT path. The runner's HTTP client believes it dials direct — its library choice becomes irrelevant; no CA involved, cert pinning unaffected. `HTTPS_PROXY` is still injected, so CONNECT-capable clients (curl, `request`) keep their existing path, including a non-default port when a pattern names it explicitly. MITM-delivery (`delivery.http`) runners are excluded from the DNS spoof — splicing would bypass credential injection. Mechanism details: `docs/architecture/SIDECAR.md`.
- **Operator observability**: `MitmListenerEvent.kind === "request-forwarded"` carries `{ method, url, status, authKey, retried, headerInjected }`. URL has query string stripped (no `code=`/`token=` leaks). Header values are NEVER logged. `headerInjected=true + 401` → upstream rejected the credential (token revoked, wrong format, scope insufficient). A URL off the allowlist never reaches upstream: it is a 403 with `kind === "request-refused"`, `reason: "not-authorized"`; so is a request whose injected credential's auth has a host-unbounded `authorized_uris` entry (`reason: "credential not host-bounded"`). `kind === "upstream-error"` fires when the fetch itself threw before any response landed (TLS handshake, DNS, etc.) — `request-forwarded` only emits when a response was received.

### AFPS Integrations — scope model & tool selection (niveau 2)

Integration manifests model OAuth scopes via AFPS's snake_case vocabulary, exposing discrete MCP tools the agent can pick from. The manifest declares the catalog under `auths.{key}.scope_catalog` (§7.4); agents declare which tools they consume; the runtime infers the minimum scope set per (user, integration auth, account) as `∪(tools_policy.{name}.required_scopes for tools any installed agent uses)`.

Three enforcement layers (Phase 0/1/2/3 schema + validation + runtime):

Two additive manifest fields (validated by `packages/core/src/integration.ts`, per AFPS §7.4 + §7.8):

- `auths.{key}.scope_catalog: Array<{ value, label, description? }>` — catalog of OAuth scopes the upstream IdP exposes for this auth. Optional. When declared, `auths.{key}.scopes` defaults and `tools_policy.{name}.required_scopes` are validated as a subset; the IdP remains the ultimate authority at consent time.
- `tools_policy.{name}: { required_scopes? }` — sparse per-MCP-tool policy table (the AFPS `tools.{name}` block). `required_scopes` is a **per-auth map** `{ <auth_key>: string[] }`: it binds the scopes a tool needs to one or more declared `auths` entries and drives the agent-install scope union for OAuth consent. Each key MUST be a declared auth and its scopes ⊆ that auth's `scope_catalog`. Keying by auth is consent inference only — NOT an exclusivity lock: an auth absent from the map (e.g. a `pat` alongside a scoped `oauth`) still serves the tool, and the run/schedule connection picker uses `connectableAuthKeysForAgent`, which offers every declared auth. `hidden_tools: string[]` (§7.8) additionally suppresses tools from `tools/list` regardless of agent selection. (The former `scope_auth_key` field and the per-tool `url_patterns` MITM envelope were removed — `auths.{key}.authorized_uris` is the URL boundary.)

Agent-side, the integration **version** is a bare semver string on `dependencies.integrations.<id>` (§4.1, flat like skills and mcp_servers); the per-integration **configuration** (tool/scope/auth selection) lives in the separate top-level `integrations_configuration.<id>` map (§4.4):

```jsonc
{
  "dependencies": {
    "integrations": {
      "@appstrate/github-mcp": "^1.0.0",
    },
  },
  "integrations_configuration": {
    "@appstrate/github-mcp": {
      "tools": ["list_issues", "issue_write"],
      "scopes": ["user:email"],
    },
  },
}
```

A dependency with no configuration leaves no `integrations_configuration` entry — all three dependency maps are flat `{name: semver-range}`. The config's `tools[]` drives the sidecar's `McpHost.allowedTools` allowlist + OAuth scope inference; `scopes[]` is the escape hatch; `auth_key` (§4.4) disambiguates a multi-auth integration. Every `integrations_configuration` key MUST match a declared `dependencies.integrations` entry — the dep map is the canonical "is this integration declared" gate, and an orphan config key is rejected at manifest validation. `parseManifestIntegrations(manifest)` merges both into `{ id, version, tools?, scopes?, auth_key? }[]`; `writeManifestIntegrations` splits them back. These two functions in `@appstrate/core/dependencies` are the single read/write path.

**Least-privilege selection**: `tools` and `tools: []` are NOT equivalent. An absent `tools` inherits the integration's declared `default_tools` (§4.4, `resolveEffectiveToolSelection` in `@appstrate/core/integration`) — for the ~60 system integrations that declare `default_tools: ["api_call"]`, adding the dependency alone already yields a callable surface. An explicit `[]` overrides the default and selects nothing. The agent author narrows or widens the selection per tool via the editor UI's checkboxes, "Select all", or the §4.4 wildcard.

**Zero callable tools is a broken agent, refused at both ends**: a _declared_ integration whose effective selection exposes nothing callable is a contract violation, not a degraded mode. This includes `tools: []`, an absent selection with no `default_tools`, and a non-empty selection whose tools are all hidden or absent from a known resolved catalog. Leaving it declared-but-unusable makes the model improvise unauthenticated HTTP instead of stopping. Two gates, one rule:

- **Wherever a version is frozen** (`requireCallableTools` in `apps/api/src/services/integration-scope-validation.ts`) — cutting a version, ZIP/GitHub import, `.afps-bundle` import, and the initial snapshot the create routes take (`createVersionSafe`, `routes/packages.ts`) refuse the manifest with a `no_tools_selected` field error on `integrations_configuration.{id}.tools`, naming the two ways out: select a tool, or drop the `dependencies.integrations` entry. This is where the author can still fix it. The create routes themselves keep ACCEPTING the empty manifest — the editor's flow passes through it — they simply do not freeze a version from it.

  A self-contained `.afps-bundle` is judged before its first write against the catalog that will exist after a successful import: existing and carried versions form one resolver input, forward-only version policy is simulated in bundle order, and `latest` movement is included. Existing system packages stay canonical because carried copies are ignored by both validation and import.

- **Runtime backstop** (`assertIntegrationExposesTools` in `runtime-pi/sidecar/integrations-boot.ts`) — a boot ending with 0 registered tools lands the integration on the boot report's `failed[]` and aborts the run. Still needed: a draft can be run straight from the editor without ever being published, and versions published before the gate existed are still runnable.

The publish gate does **not** cover a blind spot of the boot gate. An integration declaring **no** `auths` never reaches the spawn resolver at all — `@afps-spec/schema` refuses the manifest outright (AFPS §3.5, `integration MUST declare at least one auth method`), so there is no zero-auth integration for a spec to be emitted for or withheld from, and the resolver carries no branch for one. The spec is suppressed (`resolveDeliveries` → `null`, `integration-spawn-resolver.ts`) only when the integration declares an auth and no accessible connection resolves — and readiness already refuses that run with `not_connected`, exactly as it refuses an integration the space does not run with `integration_not_active` (`agent-readiness.ts`). So every "no spec emitted" path is already gated, just by a different, more precise error.

What the publish gate actually buys is **timing and attribution**: it refuses the manifest at the one moment the artifact is still editable, naming the `integrations_configuration.{id}.tools` key the author wrote, instead of ~30s into a paid container boot. A published version is immutable, so after the fact the only remedy is cutting a new one.

The gate reads the **pinned** integration manifest, not the integration's live draft: it resolves each `dependencies.integrations.{id}` spec through `resolveRunIntegrationVersions` — the same resolver that freezes `runs.resolved_integration_versions` — so callability at publish means what it will mean at boot. An agent pinned to `^1.0.0` whose v1 declares `default_tools: ["api_call"]` publishes fine even after the integration author drops `default_tools` from their draft. A pin that resolves to nothing (never published / unsatisfiable) leaves the entry **unjudged**: that run fails loud upstream with `dependency_unresolved` (422), and a gate that blocks a legitimate publish would be worse than one that defers to the backstop. Tool/scope subset checks use that same pinned manifest and its resolved nested mcp-server catalog.

**Draft saves are deliberately NOT gated.** The editor passes through the empty state between "add the integration" and "tick a tool", autosaving in between; refusing it there would make the editor unusable. `POST`/`PATCH /api/packages/agents` therefore run every other check but not this one.

**AFPS §4.4 wildcard `tools: "*"`** (opt-in, AFPS §7.8): when the integration manifest declares `allow_undeclared_tools: true`, the agent MAY set `tools: "*"` to forgo per-tool selection and accept every tool the upstream MCP server advertises at runtime. The platform emits `IntegrationSpawnSpec.toolAllowlist === undefined` for this case, which the sidecar's `McpHost` interprets as "no allowlist" (legacy passthrough). Per-tool scope inference is bypassed; required OAuth scopes fall back to the selected auth's `default_scopes` (§7.4). The integration's `hidden_tools` filter still runs, and the spawn resolver additionally unions the `connect.tool` login primitive's name into `hiddenTools` under wildcard so the credential-acquisition tool is never exposed to the agent's LLM. Zero-trust preserved: the agent author cannot bypass the policy table unless the integration author explicitly authorized the pass-through.

- **Phase 1 (import-time, `apps/api/src/services/integration-scope-validation.ts`)** — `POST/PATCH /api/packages/agents` + ZIP import refuse manifests whose `integrations_configuration[id].tools[]` selection includes an undeclared tool, or whose `scopes[]` selection escapes the `auths.{key}.scope_catalog` (per target auth). Field paths surface as `integrations_configuration.{id}.tools` / `integrations_configuration.{id}.scopes`. Configuration without a matching dep is rejected at manifest validation (the dep table is the canonical "is this integration declared" gate). The `requireCallableTools` option adds the zero-callable gate and the `auth_key`-serves-no-selected-tool gate on top, and is opt-in per call site: **on** for publishing a version, for `POST /api/packages/import`, and for `POST /api/packages/import-bundle`, **off** for draft writes (see "Zero callable tools" above). On `/import-bundle` the gate runs as a pure-read preflight in `handleImportBundle` (`services/bundle-import.ts`), before conflict detection and before the first write, so one invalid agent aborts the **whole** bundle with no rollback; each field error's message is prefixed with the offending `{packageId}@{version}` identity. Existing and carried integration/mcp-server versions are resolved as the post-import union; system package bytes carried by a bundle never override the platform's canonical system catalog.
- **Phase 2 (OAuth connect, `apps/api/src/services/integration-scope-resolver.ts`)** — `POST /api/integrations/.../connect/oauth2` requests `defaults ∪ caller-supplied ∪ computeRequiredScopes(installed agents) ∪ getCurrentGrantedScopes(actor)`. Granted is unioned for **incremental consent**: re-consent never silently shrinks the granted set. `GET /api/integrations/.../auths/.../required-scopes` surfaces the breakdown for UI previews + "agent install needs an upgrade" detection.
- **Phase 3 (runtime, `runtime-pi/sidecar/mcp-host.ts` + `integrations-boot.ts`)** — `IntegrationSpawnSpec.toolAllowlist` (an array by default; the platform builds it from the EFFECTIVE selection — `integrations_configuration[id].tools` when present, otherwise the integration's `default_tools` — OR `undefined` for the AFPS §4.4 wildcard form `tools: "*"`) propagates to `McpHost.register({ allowedTools })`. The host filters `tools/list` so the agent's LLM only sees the tools the author selected; excluded tools (including anything in the integration's `hidden_tools`) emit a `tool_excluded_by_allowlist` audit log. `undefined` (wildcard) disables the allowlist filter so every upstream tool surfaces; the connect-login primitive is still hidden via `hiddenTools`. An empty `[]` no longer means "spawns but exposes nothing" — `assertIntegrationExposesTools` fails the run instead (see "Zero callable tools" above).
- **Phase 4 (runtime MITM)** — _removed._ An earlier iteration enforced a per-tool URL envelope (`⋃ manifest.tools_policy[t].url_patterns` over the agent's `toolAllowlist`) in the sidecar MITM listener before credential injection. It shipped with zero adoption (no system integration declared `url_patterns`, and it only applied to local-runner integrations, of which none ship), so it was cut as speculative generality. The per-auth `auths.{key}.authorized_uris` allowlist (enforced on every runner egress path, see `docs/architecture/SIDECAR.md` → "Runner egress allowlist") is the sole URL boundary.
- **Phase 5 (UI, `apps/web/src/pages/integration-detail.tsx` + `apps/web/src/components/package-detail/agent-integrations-block.tsx`)** — agent-install scope diffs are computed **client-side** via `requiredScopesForAgent` (`@appstrate/core/integration`) using the installed-agents snapshot already in the React Query cache, avoiding an extra round-trip. The Phase 2 server endpoint `GET /api/integrations/.../auths/.../required-scopes` remains the authoritative source for headless / API consumers and the OAuth kickoff union. Trade-off: client computation must stay in lockstep with `computeRequiredScopes` on the server — both call into the same `@appstrate/core/integration` helper to keep them aligned. The "Reconnect to grant" CTA reuses the existing OAuth kickoff path — Phase 2 already unions defaults + required + granted at the backend, so a single click triggers an incremental-consent flow (IdP shows the upgrade screen, previously-granted scopes are preserved). The panel is silent when no diff exists or when there's no connection yet (first-connect already requests the full union).
- **Phase 5b (agent editor, `apps/web/src/components/agent-editor/integration-tool-picker.tsx`)** — agent authors pick per-integration tools and OAuth scopes directly in the editor's Integrations section. The picker fetches the integration manifest via `useIntegrationDetail`, renders a checkbox grid for `manifest.tools_policy.*` (with each tool's `required_scopes` displayed for transparency) and another for `auths.*.scope_catalog`. Quick-action buttons `Select all` / `Select none` cover the common cases. When the integration declares `allow_undeclared_tools: true`, the picker also renders an "Include all upstream tools (advanced)" toggle that sets `entry.tools = "*"` and hides the per-tool checklist + api_call rows (scopes then come from `default_scopes`, see Phase 2 wildcard path). `ResourceEntry` carries optional `tools?: string[] | "*"` + `scopes?: string[]`; `setResourceEntries('integrations')` writes via `writeManifestIntegrations`, splitting the version into `dependencies.integrations[id]` and the tools/scopes into `integrations_configuration[id]`. The `"*"` literal round-trips verbatim — never spread as a string into `["*"]`.
- **Phase 6 (refresh-time scope-shrink, `apps/api/src/services/integration-token-refresh.ts` + `integration-credentials-resolver.ts`)** — when an OAuth refresh response echoes a `scope` field, `forceRefreshIntegrationConnection` overwrites the connection's `scopes_granted` column (OAuth 2 §5.1 authoritative grant) and returns `shrinkDetected: true` if the new set is strictly narrower than the previously-stored one. The resolver then calls `computeRequiredScopes` and flips `needsReconnection=true` when the shrink drops the actor below the union required by installed agents. Responses that omit `scope` entirely (the common case — OAuth 2 says "same as before") leave `scopes_granted` untouched. Fast-path: the agent scan only runs when the refresh actually shrank scopes, so the steady-state cost is one extra SELECT per refresh.

Phase 0 is schema-only. Phases 0-3 and 5-6 of the niveau 2 scope model are landed; Phase 4 (per-tool MITM URL envelope) was removed as speculative — `authorized_uris` is the URL boundary.

### AFPS Integrations — Phase 7: remote HTTP MCP support

Integrations declare `source.kind: "remote"` + `source.remote: { url: "https://…/mcp/v1", transport: "streamable-http" }` (or `transport: "sse"`) to be backed by a remote Streamable HTTP / SSE MCP server (e.g. Google's `gmailmcp.googleapis.com/mcp/v1`, Anthropic-hosted MCPs, Composio, Linear, …). The remote source has no bundle, no MITM listener, no CA cert. The sidecar opens a Streamable HTTP MCP client directly via `createMcpHttpClient` (`@appstrate/mcp-transport`) instead of spawning a runner container. Credentials flow: `integration-credentials-source` (cache + `refreshOnUnauthorized`) → custom `fetch` wrapper that reads the current `access_token` and injects `Authorization: Bearer <token>` per request, retrying once on 401 after a force-refresh. Implementation in `runtime-pi/sidecar/integrations-boot.ts:connectRemoteHttpIntegration`; spawn-side propagation in `apps/api/src/services/integration-spawn-resolver.ts` (drops `httpDeliveryAuths` for `isRemoteHttp`).

Trade-off vs. local stdio runners — defence-in-depth coverage:

| Niveau 2 phase             | stdio runner (Phase 1.4/1.5) | Remote HTTP MCP (Phase 7) |
| -------------------------- | ---------------------------- | ------------------------- |
| 1 — install validation     | ✅                           | ✅ (same path)            |
| 2 — OAuth scope union      | ✅                           | ✅ (same path)            |
| 3 — `tools/list` allowlist | ✅ McpHost filter            | ✅ McpHost filter         |
| 5/5b — UI                  | ✅                           | ✅ (same path)            |
| 6 — refresh-time shrink    | ✅                           | ✅ (same path)            |

Other deltas: no `.afps-bundle` signing surface, every tool call exits the perimeter (no air-gapped self-host), the per-call audit trail collapses from "raw upstream HTTP" to "MCP tool call". Operators pick per integration based on trust model — `source.kind: "remote"` is the right choice for managed/upstream-trusted MCPs; `source.kind: "local"` (with the referenced mcp-server's `server.type` being `node|python|binary|uv`) stays the right choice for sandboxed local execution where the MITM gives you a meaningful security boundary.

Reference integration: `@appstrate/gmail-mcp@2.3.5` (in `scripts/system-packages/integration-gmail-mcp-2.3.5/`) — Gmail backed by Google's official remote MCP. The same tool catalog as Google's hosted server — no count is quoted here because the catalog is upstream-controlled and the conformance monitor, not this document, is what keeps the two equal — with per-tool `tools_policy.{name}.required_scopes` driving the niveau 2 scope inference (gmail.readonly | compose | labels | modify spread across the catalog).

### AFPS Integrations — connection variables (AFPS §7.12)

An integration whose upstream is chosen per connection — a self-managed GitLab, a Coolify instance, a self-hosted Twenty — declares top-level `variables.schema` (string properties, every one `required`) and references the values as `{$variable.<name>}`. Reference packages: `@appstrate/gitlab-mcp`, `@appstrate/twenty-mcp`, `@appstrate/coolify-mcp` (`scripts/system-packages/integration-{gitlab,twenty,coolify}-mcp-1.0.0/`). The authoring rules — grammar, where a placeholder may appear, the origin rule for `authorized_uris` and for the delivery templates of an `oauth2` or `connect` auth — are in `docs/guides/writing-an-integration-with-connect.md` → "Connection variables"; the manifest shape is enforced by `@afps-spec/schema`, and `findUnevaluableExpressions` (`@appstrate/core/integration`) refuses a reference to an undeclared variable on the write paths.

**Storage.** `integration_connections.variables` (`jsonb`, `NULL` ⟺ the integration declares no variables) holds the values the user submitted, in plaintext. They are not credentials: they may be displayed (connection rows show them under the label) and logged. They are written in the same statement as the credential, at creation and at reconnect, so a stored credential is never paired with values naming another upstream. The values name the instance the connection's account lives on, so a reconnect to other values is refused like one to another account — 409 `identity_mismatch` from `persistCredentialBundle`, the row untouched — and another instance is a new connection. A reader takes the values from the statement that read the ciphertext it decrypts (`loadAccessibleConnectionById` and `selectAccessibleConnection`, `services/integration-connections.ts`), so it never pairs a credential with values a concurrent reconnect wrote; a token refresh rewrites the ciphertext alone and leaves the values. That refresh is pinned to the connection as its caller read it (`RefreshTarget`, `services/integration-token-refresh.ts`): under the refresh lock the row must still carry the same `client_ref`, `oauth_resource` and variables, and the write-back is a compare-and-set on the `client_ref` and the ciphertext it refreshed; otherwise nothing is exchanged or written, the refreshed token is discarded, and the refresh fails transient. In the sidecar, a remote MCP request carries the credential only to a URL inside the connection's rendered `authorized_uris` (`connectRemoteHttpIntegration`): the server URL is rendered once at spawn, and a credential swapped in for another upstream mid-run never reaches it.

**Validation at connect.** `POST /api/integrations/{packageId}/auths/{authKey}/connect/fields`, `…/connect/oauth2` and the hosted portal's `POST /connect/submit` take `variables`. They are validated with AJV against `variables.schema`; then every URL template the chosen auth uses (`source.remote.url`, its `issuer`) must render and pass `checkEgressUrl(url, { requireHttpsForUntrustedHost: true })`, and every `authorized_uris` entry of the auth must render. A failure is a 400 `validation_failed` on field `variables.<name>` with code `unrenderable_variable`; missing variables for an integration that declares them, or variables for one that declares none, are a 400 too. On the hosted portal an oauth2 auth of such an integration does not redirect straight to the provider: `GET /connect/start` lands on `/connect`, which collects the variables (prefilled from the reconnected connection, else from each `default`), and `POST /connect/submit` begins OAuth with them and answers `{ ok: true, redirect_url }`. The page starts one authorization request: a submit that begins it spends the page cookie's jti and clears the cookie, and only a refusal that leaves the form usable (a variable to correct) hands the jti back. `POST /connect/submit` is rate-limited per IP and `…/connect/oauth2` per caller. `GET /connect/context` carries `variables: { schema, values }`, `null` when the integration declares none.

**Rendering, per connection.** A URL-valued field renders through `renderUrlTemplate` (`@appstrate/afps-shared/connection-variables`), by substitution and concatenation, never by resolving one part against another:

- URL form (`{$variable.base_url}/api/v4/mcp`) — the value must be an absolute `http(s)` URL with a host and no userinfo, query (an empty `?` included), fragment or `*`. Without a template path it renders as the WHATWG serialisation of the value; with one, as its origin and path with every trailing `/` removed, then the template path — `https://git.example.com/gitlab/` renders `https://git.example.com/gitlab/api/v4/mcp`.
- Host form (`https://{$variable.tenant}.example.com/mcp`) — the value is one or more `.`-separated labels of 1 to 63 letters, digits and `-`, none starting or ending with `-`; the rendered host is at most 253 characters.

The platform uses the WHATWG serialisation of a rendered URL, which lowercases its host, and matches and egress-checks a host as the WHATWG parser reads it (`0x7f000001` is `127.0.0.1`).

The renderer does not demand `https`: the egress check does, and accepts `http` only for a host listed in `EGRESS_ALLOW_INTERNAL_HOSTS` — the operator designation §7.12 allows. Value templates (`delivery.http.value`, `delivery.env.*.value`, `delivery.files.*.value`) substitute the raw value, as for a credential field (`renderCredentialTemplate(template, bag, { variables })`). `authorized_uris` entries render through `renderAuthorizedUris(patterns, bag, variables)` (`@appstrate/afps-shared/credential-template`): a URL-form entry follows the URL-form value rules and renders as origin + path, every trailing `/` removed, then the suffix (a bare entry renders the value URL itself); in the authority form the variable fills the host, alone or before literal labels, under the host-form rules. An entry that does not render is dropped and an emptied list refuses every credentialed call, exactly as for `{$credential.<field>}` entries.

The spawn resolver (`integration-spawn-resolver.ts`) renders `source.remote.url` inside the per-connection loop (`renderConnectionRemoteUrl`) and puts it through the same egress floor as a declared URL (`remoteUrlRefusal`). A connection whose URL does not render is dropped with `remote_url_unrenderable`, one whose rendered URL the guard refuses with `remote_url_blocked`. A bound set is spawned whole or not at all: when several connections are bound to the integration and any one of them is dropped, every other member is dropped too, with `bound_set_incomplete`, so a call meant for the lost connection never runs on a survivor — the integration then spawns nothing for the run, and the drops travel back with the specs for the caller to surface. When every member renders, each spec carries its own URL, so N connections to N instances open N MCP clients. The connection's variables reach every other renderer as well: the delivery renderers, the `authorized_uris` the sidecar's credential policy and the runner egress allowlist match against, the integration credentials resolver, the credential proxy (`services/credential-proxy/integration-resolver.ts`) and the CLI-side `api_call` resolver (`packages/afps-runtime/src/resolvers/integration-api-call.ts`).

**Per-connection authorization server.** `hasPerConnectionAuthServer(manifest, auth)` (`services/integration-manifest-helpers.ts`) is true for an `oauth2` auth whose `issuer` is a URL template, and for every `oauth2` auth of an integration whose `source.remote.url` is one. The user who creates the connection, not the package author, then chooses the authorization server, and the platform treats every URL it renders — or learns from a response to one, including a body, a `WWW-Authenticate` `resource_metadata` parameter, a redirect or a discovery document — as user-supplied: each goes through the SSRF-guarded fetch and egress checks of remote MCP (`ssrfGuardedFetch`, `isBlockedUrl`, `checkEgressUrl`). For such an auth:

- **Client acquisition is DCR only.** The client is auto-provisioned (RFC 7591, public client, PKCE) and keyed by `(space, integration, auth_key, issuer)` — `integration_oauth_clients.issuer` (`docs/architecture/SPACES.md`) — so a client belongs to one authorization server and one integration, never shared between two of either, and is presented only to the endpoints of that server's validated metadata. Before registering a new one, `pruneUnusedPerConnectionClients` deletes the clients of `(space, integration, auth_key)` bound to an issuer that no connection's `client_ref` names and that are older than an OAuth state (`OAUTH_STATE_TTL_SECONDS`), so whoever opens connect flows cannot grow the table past the clients in use. The auth must declare `token_endpoint_auth_method: "none"` (`ensurePerConnectionOAuthClient` refuses it otherwise), so no client assertion is signed; AFPS §7.3 requires one, for a server whose metadata the user controls, to carry the validated `issuer` as its sole audience. An org or space client an admin registers by hand is refused (`assertClientAuth`, `services/integration-connections.ts`), since no single registration could serve servers each connection names. A server that advertises no `registration_endpoint` (a GitLab instance whose administrator turned dynamic client registration off) cannot be connected.
- **The issuer.** A templated `issuer` on a non-remote source is the rendered issuer: RFC 8414 / OIDC discovery against it, with the issuer-equality check, yields the endpoints, and no RFC 8707 `resource` is sent. A templated `source.remote.url` runs RFC 9728 discovery against the rendered URL (`discoverProtectedResourceMetadata`, `packages/connect/src/mcp-oauth-discovery.ts`), in the MCP order: the `resource_metadata` of a `WWW-Authenticate` challenge to an unauthenticated request, then the path-inserted well-known location, then the root one. A document is used only when its `resource` is identical, modulo trailing `/`, to the identifier its location was derived from — the rendered URL for the challenge and the path-inserted location, its origin for the root location (RFC 9728 §3.3; the rule holds for every remote source, templated or not) — and otherwise the next location is tried; with none left the connection is refused. The authorization server is an entry of the document's `authorization_servers` equal to the rendered manifest `issuer` when the auth declares one (a template over the URL's variables — `@appstrate/gitlab-mcp` declares `{$variable.base_url}`, which covers an instance served under a path prefix), and otherwise one with the rendered URL's origin; with none the connection is refused, so a server the user named cannot advertise `https://gitlab.com` and collect a gitlab.com authorization. Endpoints come only from discovery of that issuer — such a manifest can declare none — and for a remote source the RFC 8707 `resource` (the document's) is always sent on the authorize and token requests.
- **Mix-up defence** (RFC 9700 §4.4, AFPS §7.3 _Client binding_). The DCR client's redirect URI is per authorization server: `<integration callback URL>/<tag>`, where `tag` is the first 22 characters of `base64url(SHA-256(issuer))` (`authorizationServerTag`, `lib/integration-callback-url.ts`). `GET /api/integrations/callback/:tag` is the same handler as `/callback` and refuses a response whose tag differs from the tag of the issuer the state names; a per-server response arriving on the plain `/callback`, or the reverse, is refused too (`mixUpRefusal`, `packages/connect/src/integration-oauth.ts`). For every integration OAuth flow, per-connection or not, an `iss` authorization response parameter (RFC 9207) must equal, by simple string comparison, the `issuer` of the validated metadata of the server the request was sent to, and a response without one is refused when that metadata advertised `authorization_response_iss_parameter_supported: true` — a flag stored in the state record when the flow begins.
- **Refresh** reads the issuer from the client row's `issuer` when it is set and from the manifest otherwise; a `NULL` issuer means the manifest's fixed authorization server. The token endpoint discovered for a client-row issuer goes through `checkEgressUrl(url, { requireHttpsForUntrustedHost: true })` again before the refresh token is sent: an unresolvable host fails the refresh transient, any other refusal leaves the connection unrefreshable.
- **The resource on refresh.** A refresh is a token request, so it sends the RFC 8707 `resource` the token was requested for (AFPS §8.6). Every acquisition stores the `resource` its authorize and code-exchange requests carried in `integration_connections.oauth_resource`, in the write that stores the token (`NULL` when none was sent, and for every non-`oauth2` credential); the refresh write-back leaves it, and `buildIntegrationOAuthRefreshContext` hands it to `performRefreshTokenExchange`. This holds for every `oauth2` connection, per-connection server or not.

### AFPS Integrations — Phase 8: per-run shared workspace volume + MCP Roots

`mcp-server` packages may opt into a per-run shared workspace volume the agent can read/write. The motivating use case is the clone-edit-commit-push-PR loop in `@appstrate/github-git-mcp`: the server's `clone` tool writes to `/workspace/<repo>`, the agent's Pi runtime tools (`Read`/`Edit`/`Bash`) then mutate those files in place, and the server's `commit`/`push` tools read them back. Without a shared volume the agent and the server would see disjoint filesystems.

Opt-in surface (`mcp-server` manifest):

```jsonc
{
  "_meta": {
    "dev.appstrate/workspace": {
      "mount": "/workspace", // absolute POSIX; rejects `..`, control chars, root (`/`), kernel prefixes (`/proc`, `/sys`, `/dev`, `/etc`)
      "access": "rw", // "ro" (default) | "rw"
    },
  },
}
```

Parsed by `getMcpServerWorkspaceMount` (`@appstrate/core/mcp-server`); validation runs in `mcpServerManifestSchema.superRefine`, when the manifest is written or imported, so a malformed mount is rejected before publish. Validation rules: `mount` must be a non-empty string when present (a non-string is rejected, not silently coerced to the default), an absolute POSIX path, free of `..` traversal segments and control chars, and neither root (`/`) nor a kernel-managed prefix. `access` defaults to `"ro"` (least-privilege). Note the `ro`/`rw` mode is kernel-enforced only on the docker adapter (the `:ro` bind flag); on the process adapter (tier 0-2) it is advisory — there is no read-only bind for a host directory, so a server needing hard write-denial must run in docker mode.

End-to-end topology:

```
Platform launcher
  ├─ if any installed mcp-server opts in:
  │     ├─ tier 3 (docker): create named volume `appstrate-ws-<runId>` (label `appstrate.managed=true`)
  │     └─ tier 0-2 (process): create host tmpdir under `os.tmpdir()/appstrate-ws-<runId>/`
  ├─ build `WorkspaceHandle` (discriminated union on IsolationBoundary, `@appstrate/core/platform-types`)
  └─ propagate as `WORKSPACE_HANDLE_JSON` env into sidecar

Sidecar (integrations-boot)
  ├─ mount the same volume at `/workspace` on the agent container (`pi` user, UID 1001)
  ├─ for each opted-in mcp-server runner: bind `-v <vol>:<manifest.mount>[:ro]`
  │     + set `APPSTRATE_WORKSPACE=<manifest.mount>` for runtime convenience
  │     (process adapter, Firecracker guest: `APPSTRATE_WORKSPACE=<dir>` + the wrapper's
  │     `--workspace`, which grants group `workspace` 1003; a runner that did not opt in
  │     has no supplementary group and cannot reach /workspace)
  └─ MCP Roots: advertise `capabilities.roots.listChanged: false` to the runner; on
        `roots/list` return `[{ uri: "file://<mount>", name: "workspace", _meta: { ... access ... } }]`
```

**MCP Roots contract** (`runtime-pi/sidecar/integrations-boot.ts`): the sidecar IS the MCP Roots provider for spawned runners. `listChanged: false` because the root is fixed for the run lifetime — there's no UI surface to add/remove roots mid-run. Reference compatible servers: the modelcontextprotocol `filesystem` server and the cyanheads `git-mcp-server` both consume roots via this exact protocol.

**UID 1001 invariant** (cross-cuts security + workspace writes): the agent's `pi` user and ALL five runner images (`runtime-pi/runners/{bun,node,python,binary,uv}`) ship as UID 1001 / GID 1001. The init step that chowns the empty volume on first mount uses a marker file (Docker resets `uid:gid` on first mount of a fresh named volume to the daemon's defaults, typically root:root, which would 403 the agent). Adding a new runner image MUST keep this alignment or workspace writes silently fail with `Permission denied`. The github-git MCP server additionally prepends `-c safe.directory='*'` to every `git` invocation because git refuses to operate on a working tree whose uid differs from the EUID, even when the uid is correct — a defensive belt against ownership drift across image rebuilds.

**Cleanup**: `cleanupOrphanedVolumes()` mirrors the network reaper — runs at platform boot, removes any `appstrate-ws-*` volume whose corresponding run has terminated. Sidecar shutdown does NOT explicitly remove the volume (the platform owns the lifecycle), only the runner containers. Boundary creation (`DockerOrchestrator.createIsolationBoundary`) races the network + volume create via `Promise.allSettled` and tears down whichever side succeeded if the other rejects, so a partial create never orphans a resource ahead of the boot reaper.

**git ref/branch injection guard** (github-git server, `assertSafeRefArg`): every agent-supplied value that lands in a positional `git` argument (`clone.ref`, `checkout_branch.branch`/`base`, `push.branch`) is screened before the spawn. git treats a leading `-`/`+` as an option/force-refspec and `:` as a refspec separator, so an unguarded value (`ref: "-f"` → `git checkout -f` discards the working tree; `branch: ":main"` → `git push origin :main` deletes the remote branch) would reach git as a flag/refspec rather than a ref. Tools spawn git via an argv array (no shell), so this is purely git's own option/refspec parsing — not shell injection — but the blast radius (working-tree data loss, remote branch deletion) is real, hence reject-not-sanitise. Workspace-relative paths are independently floored by `resolveInWorkspace` (strip leading slash, reject `..`, re-assert the resolved path stays under the workspace root).

### AFPS Integrations — connection model

The connect lifecycle for integrations is **agent-driven** (not integration-driven), because OAuth scopes are inferred per-agent from `tools[]` selection. The integration detail page (`/integrations/:scope/:name`) is **admin-leaning**: activate/deactivate through the platform's one pair of doors (`POST /api/spaces/{id}/packages` and `DELETE /api/spaces/{id}/packages/{scope}/{name}`, the same pair every package type uses — `docs/architecture/RBAC_PERMISSIONS_SPEC.md` §6.10), non-destructive twice over since a deactivation sets `enabled = false` and leaves the `space_packages` row with its settings, while FK'd connections survive either way; OAuth client (`integration_oauth_clients`) registration, read-only auth declarations + connection list, and a passive `RequiredScopesPanel` diff for audit. It does NOT surface user-facing connect/disconnect.

User-facing connect/upgrade lives on agent surfaces (`AgentConnectionsSection` + `MissingConnectionsModal` on the run-kickoff 409). Both render `<InlineConnectButton>` from `components/integration-connect/` which picks OAuth popup vs api_key/basic/custom fields modal based on `auth.type` and forwards the agent's per-tool scope inference (`tools_policy.{name}.required_scopes`) to the OAuth kickoff so consent asks for the minimum required.

**Multi-connection model**: a multi-auth manifest (e.g. GitHub MCP declaring `oauth` + `pat`) lets an actor hold N connections at once across any mix of declared auths. `saveIntegrationConnection` (`apps/api/src/services/integration-connections.ts`) deliberately has **no** single-auth gate — it just inserts. The runtime binds a **SET** of them per integration per run — 1..`MAX_CONNECTIONS_PER_INTEGRATION` (20, `@appstrate/core/integration`) — through a 6-layer cascade (`integration-connection-resolver.ts`): admin pin → org default `enforce` → launch override → member pin → org default soft → actor fallback. **Every layer yields a set**, the first non-empty one wins (an empty array is "this layer has no opinion", which is why every write refuses one), and every member of the winning set must pass `checkHealth`. The launch override is ONE layer fed by whichever launched the run — the run body's `connection_overrides` or the firing schedule's (a scheduled fire carries no run override) — and the bound set records which in its `source` (`run_override` / `schedule_override`) for the audit trail in `runs.resolved_connections`. Under an admin pin or an enforced org default, a launch override must name a subset of that governing set, which it then narrows to; one naming any connection outside it is refused with `override_outranked` (an item of the `409 missing_integration_connection`, at kickoff and at an enabled schedule's write), never silently outranked. Every explicit layer (1-5) whose set names a connection the actor can no longer reach fails the run — `pinned_connection_unavailable` for a pin or an org default (`source` `org_default_enforced` or `org_default`), `override_connection_unavailable` for a launch override — and never binds the reachable rest nor falls through to the fallback: the soft default binds whole or fails like the enforced one, the two differing only by position (a launch override or a member pin beats the soft one). Since the fallback never binds a shared connection, a soft default is the one way to route members onto a shared account without a pick of their own, which is why it cannot degrade silently. Only the fallback binds without an explicit pick, so it binds only what is unambiguously the actor's: among the accessible connections on an auth serving the selection, **exactly one OWN** (`user_id`, or `end_user_id` for an end-user) binds, dead or not — a dead one reports `needs_reconnection` on that row. Everything else is a `409 must_choose_connection`: two own connections (a dead one counts, so an expiry never silently switches the run to the other account), and **a connection shared by another member alone — a shared connection is never resolved implicitly**, for a member or an end-user alike; it is used through an explicit pick (admin or member pin, org default, run or schedule override). That also means the fallback **never auto-binds N** — a fan-out is always a human's act. A scheduled fire has nobody to ask, so the choice is made when the schedule is written: creating or updating a schedule that is (or stays) enabled, when its actor's resolution for the definition it fires (with its frozen `connection_overrides`) would fail on the schedule's own choice — `must_choose_connection`; `override_connection_unavailable` when those overrides name a connection the actor cannot reach (deleted, unshared, another identity's); or `auth_serves_no_selected_tool` when the schedule's OWN overrides bind a connection on an auth serving none of the selected tools (bound by a pin or a default, that one is the pin's to fix and is accepted) — is refused with the same `409 missing_integration_connection` carrying only those items (`assertScheduleConnectionsChosen`, `services/schedule-connections.ts`); every other verdict is accepted — it is repaired without editing the schedule, and a fire it still blocks records a failed run. A schedule whose actor is not its writer resolves with the actor's reach, but the writer sees and binds only what both reach: a connection id the write newly names in `connection_overrides` must be one shared in the space (else `override_connection_unavailable`, one answer whatever the id, so it cannot probe for private rows), the `must_choose_connection` candidates are filtered to shared connections — possibly to none, when only the actor (a member pin of their own) or an admin (an admin pin) can make the choice — and ids already on the row for the same actor are not re-judged (changing the actor resets them) — an item about one of those that is not shared, the actor's own private row, carries a generic message naming no label or account, and keeps its `connection_id` only because the schedule's set already names it (`withSharedCandidatesOnly`, `services/schedule-connections.ts`). Naming another member as the actor at all, and any later write to a schedule running as one (a `PATCH` of any field, enabling and disabling included, or a `DELETE`), is an org owner/admin act (`403` otherwise, `mayGovernMemberSchedule`, `routes/schedules.ts`; the RBAC spec owns the rule). A `PATCH` is a compare-and-set on the row every one of these checks read: `updateSchedule` (`services/scheduler.ts`) writes only while the row's `updated_at` is still the one the patch read, and answers `409 schedule_modified_concurrently`, writing nothing, when the schedule was written in between — another patch (`updateSchedule`), a delete of a connection its overrides name (`forgetDeletedConnection`) or an unshare of one its actor does not own (`disableForeignSchedules`), a fire disabling it for an actor who lost access (`disableScheduleForInvalidActor`), its actor's removal from the organization (`removeMemberInTx`, `services/organizations.ts`), or a lock on one of its input fields (`dropLockedFieldsFromSchedules`); a fire's own `last_run_at` / `next_run_at` bookkeeping leaves the stamp alone; a held row lock is not an option there, since the readiness checks read through `db` and would deadlock PGlite's single connection. A fire reads the same row: the repeatable queue job carries only `{ scheduleId }`, so no job can replay an actor or `connection_overrides` the row no longer holds, and a deleted or disabled schedule's fire is skipped and its job removed (`triggerScheduledRun`, `services/scheduler.ts`). An actor who could never fire the schedule (no `agents:run` in the space, or an end-user absent from it — the check every fire repeats, `assertScheduleActorValid`, `services/scheduler.ts`) is refused before any resolution with `400` on `actor`, when the schedule is created or updated while it is (or stays) enabled. The schedule form lists every refusal at form level, integration by integration, even where no picker row renders; when the schedule runs as another member it offers only the shared candidates, or says the actor must choose — every write for another member, armed or not, may name only shared connections (`assertScheduleOverridesReachable`); for an end-user actor, whose connections the organization's application manages, it offers the end-user's own. Its `candidate_connections` list every serving accessible row, own and shared, live and dead, each with `owned_by_actor` and `needs_reconnection` — the list the picker shows. The label is the address the sidecar's `connection` argument carries, which is why `integration_connections.label` is `NOT NULL` and unique per (space, integration) — compared verbatim, enforced by the unique index `idx_integration_conn_label` — so a bound set never needs a label check: an insert suffixes a taken label ` (2)`, ` (3)`, … under the per-(space, integration) advisory lock, cutting the base so the whole stays within the 80-character cap (`CONNECTION_LABEL_MAX`, `lib/connection-label.ts`), and a rename to a taken one is `409 connection_label_taken`. **A write replaces the whole set** in one upsert — pins and org defaults take the full set on `PUT` and `DELETE` clears it, there is no unitary add/remove, and it is the WRITE (pins, org defaults, `connection_overrides`) that enforces the cap, never the resolver. A pin or an org default is ONE row per key holding `connection_ids uuid[]` (`CHECK` 1..10, GIN index for the reverse lookup the unshare guard uses). Postgres has no foreign key on array elements, so deleting or unsharing a connection an admin pin or an org default — enforced **or soft** — names is refused (`409 connection_pinned`, `assertConnectionsUnpinned`): each binds whole for every member of the space, so removing one member would fail everyone's runs at once, and they are the references an admin can clear and a run cannot route around. Every pin or org-default upsert validates its targets first (`validatePinTargets`, `services/integration-pins-service.ts`: a target unknown, of another space or integration, not shared for an admin pin or an org default, or neither the caller's own nor shared for a member pin, is one `404` whatever the reason, so a pin write cannot probe for a colleague's private connection id). The two are not serialized: an upsert racing an unshare or delete can commit a set naming a connection that is no longer reachable, which the resolver reports as `pinned_connection_unavailable` — the same state an access loss leaves. A schedule write is not serialized against them either: one that arms a schedule naming a connection, judged while it was reachable, can commit after its unshare or delete disabled the others and leave that schedule armed, whose fire then fails with `override_connection_unavailable`. Losing access is the one unshare that guard does not stop: when an owner loses access to the space, their shared connections are unshared in the same transaction as the access change (`unshareConnectionsOfOwnersWithoutAccess`, `services/space-members.ts`), and a pin or default still naming one then fails with `pinned_connection_unavailable`. That unshare, like an explicit `shared_with_org: false` by the owner or an `integrations:configure` holder, disables in the same transaction every other actor's enabled schedule naming the connection (`disabled_reason` `connection_unshared`, `disableForeignSchedules`, `services/schedules-naming-connection.ts`), its overrides kept; the owner's own schedules stay as they are. Every explicit writer locking several schedules locks them in id order in one statement, since one transaction's own schedule is another's foreign one; a cascade delete (an agent, a space, an end user) locks them in the order it walks them, so a deadlock with one stays possible, and Postgres detects it and aborts one side. Deleting an end user (`deleteEndUser`), whose connections go by cascade, disables nothing: an end user's connection cannot be shared (#1775, PR #1801), so no other actor's schedule names one. Only a member shares a connection: an end user's serves that end user's runs, so it never enters an admin pin or an org default and its deletion with its end user (the `end_user_id` cascade) strands no id in either — sharing one is `409 end_user_connection_not_shareable`, and the CHECK `integration_connections_end_user_not_shared` (`NOT shared_with_org OR user_id IS NOT NULL`) holds the rule in the database. Nor can a share slip past the access-loss unshare: sharing (`shared_with_org: true`) goes through one gate, `assertConnectionShareable` (`services/space-members.ts`), which refuses an end user's connection, then locks the owner's `org_members` row and the space row and re-checks, in the sharing transaction, that the owner still reaches the space (`409 connection_owner_without_access`); a space member removal share-locks the space row and an org role change the spaces where the member shares a connection (`lockSpacesOfSharedConnections`) before reading access, and closing a space updates that row — so a share, a close, a removal and a demotion serialize, and whichever commits second sees the others. A member pin never blocks (only its owner can clear it, so blocking would lock a colleague's credential behind someone else's preference): it keeps the id, and a member that becomes unreachable stays in the set, so the run fails loudly (`pinned_connection_unavailable`) instead of the set shrinking to its survivors, until someone re-picks. The one exception is the deletion of the connection itself — by its owner, or by an admin deleting the custom OAuth client that minted it (`deleteIntegrationOAuthClient`), both through `forgetDeletedConnection`: in the same transaction it removes the id from the owner's own member pins **and their own schedules' `connection_overrides`** — a pin it empties is dropped (the cascade falls back), a schedule override it empties drops that integration key AND disables the schedule (`enabled = false`, `next_run_at` cleared) — an unattended run must never silently fall back to another account, or to a choice left open; its owner re-picks and re-enables it — and an emptied map is stored `NULL`. The route then removes the queue jobs of the schedules it disabled, after the commit (`removeScheduleJobs`) — a kept one needs nothing more, its next fire reading the pruned row (`GET /api/me/connections/{id}/delete-impact` lists these rewrites beforehand, serialized from the same plan the delete applies (`planConnectionForget`); empty for an id that is not a UUID, unknown or not the caller's; a bound credential sees its org (and space) only — empty outside it, and inside it only the owner's schedules of that org (and space), though the delete also rewrites the owner's schedules elsewhere; a pinned connection is still listed, its delete answering `409 connection_pinned`; each schedule entry's `disables` says whether the delete disables the schedule — enabled, and one of its sets empties — and the delete dialog announces those schedules). Other members' pins keep the id; another actor's enabled schedule naming it is disabled (`connection_deleted`) with its overrides kept — never refused, never shrunk to the survivors, so re-enabling it makes that actor choose again. The preview counts those (`other_schedules_disabled_count`, within a bound credential's org and space) and never lists them: they are not the caller's, so the dialog says how many, naming none. A member of an explicit set whose auth exposes none of the agent's selected tools (auth-scoped `api_call` tools, `authKeysServingSelection`; an empty serving set means no constraint) is refused too, `409 auth_serves_no_selected_tool`, always naming that member in `connection_id`. The fallback never picks one: with no accessible connection on a serving auth it reports `not_connected`, its `auth_key` chosen among the serving auths. The agent's own `auth_key` (AFPS §4.1) naming a declared auth that serves none of its selected tools is not a connection problem and is answered before any of this — before the `auth_key` candidate filter, pins, overrides or the fallback look at a connection: `409 auth_key_serves_no_selected_tool` with `required_auth_key` and no `connection_id`, no connect offer, and the run-kickoff modal and the agent page's picker offer neither a pick nor a connect. Publish and import refuse the same configuration up front (`400`, field `integrations_configuration.<id>.auth_key`); a draft save does not, since the editor sets the auth and the tools one at a time; an inline run gets the resolver's 409. Downstream, the platform emits one `IntegrationSpawnSpec` per bound connection (same `integrationId`, same `namespace`, the same tool selection except that the `connect.tool` login tool of the connection's own auth, when it has one, is withheld from the agent, and only the `api_call` tools of that connection's auth; `spec.connection = { id, label, accountId }` is carried on every spec spawned from a bound connection, a single connection included, its `label` and `accountId` read from the kickoff snapshot, `accountId` the row's `account_id` with the placeholder `default` mapped to `null` — absent in exactly one case, a **connect run**, whose whole purpose is to create the row that does not exist yet), so one runner holds exactly one credential and the live-credentials route is keyed by a run-bound `?connection_id=`. The external credential proxy (`/api/credential-proxy/proxy`, a remote runner's `api_call`) selects under the same rules (`selectAccessibleConnection`, `services/integration-connections.ts`). It authorizes the call against a PUBLISHED manifest — the version an `X-Run-Id` run froze (`runs.resolved_integration_versions`), else `latest` — never the draft; an integration with no published version is a `404` (`credential_not_found`). Every response carries RFC 9209 `Proxy-Status` (`received-status` on a relayed upstream response, `error` on the proxy's own refusal). With `X-Run-Id` — an in-flight run of the calling actor in this space, re-checked on every call and on the `401` refresh — it is bound to that run's snapshot, every layer already applied: one bound connection is used, several need an `X-Connection-Id` among them (`409 must_choose_connection` without, `400 connection_not_in_run` for another id). Without it no agent is in play, so the per-agent layers (admin and member pins) and the agent's `auth_key` apply to runs only and the space-level ones pick in the resolver's order: an enforced org default's set (an `X-Connection-Id` outside it is `400 connection_not_in_org_default`), else the named connection, own or shared, else a soft default's set, else the caller's single own connection. A default binds whole (an unreachable member is `409 pinned_connection_unavailable`) and a set of several is a `409 must_choose_connection` over it; a bound connection that needs reconnecting — the caller's lone own one, the named one, or any member of the default's set — is `409 needs_reconnection`; with no default and no name, several own connections or only colleagues' shared ones are a `409 must_choose_connection` carrying the candidates, and nothing accessible is a `404`. Both `401`-refresh paths of `proxyCall` (`services/credential-proxy/core.ts`) name the connection the failed call used instead of re-running the selection, which could land on another row if a connection was added or a default changed in between; naming it still re-checks the caller's reach (run membership, enforced default). A remote runner (`appstrate run`) exposes `{ns}__api_call` only for the `api_call` tools the agent's effective selection grants — the spawn resolver's rule: the agent's `tools`, else the integration's `default_tools`, `"*"` granting all and an `api_upload` pick granting its `api_call` (`buildApiCallExtensionFactory`, `@appstrate/runner-pi`, reading the integration manifest through `readIntegrationManifest`, `@appstrate/afps-runtime/resolvers`) — so it never offers a tool whose integration the run's snapshot skipped as inert, which the proxy would then refuse. That `api_call` takes no connection argument, so `POST /api/runs/remote` refuses up front (a `remote_binds_one_connection` item of the `409 missing_integration_connection`, `services/run-creation.ts`) a run whose snapshot binds several connections to one integration. The member picker on the agent surface is where that choice is made and persisted (a member pin). It reads `GET /api/agents/{scope}/{name}/connection-readiness`, whose per-integration verdict is the resolver's own vocabulary — `source` (the layer that bound the set, or whose set failed; every layer-bound error carries it) and `error_code` (the 409 code), both `null` when no manifest could be loaded — and whose `candidates` pass the same serving-auth filter as the `must_choose_connection` 409, so the picker never offers a connection the run would refuse. Letting multiple shapes coexist matches real workflows (interactive OAuth in the UI + PAT for CI agents on the same integration).

**CI / automation pattern**: a single human who wants OAuth interactively _and_ a PAT for CI can either keep both connections on their own actor (the resolver/member-pick disambiguates), or isolate them via the headless actor model — create an end-user (`POST /api/end-users`), connect _its_ GitHub via PAT, run agents from CI via an API key with `Appstrate-User: eu_…` impersonation so the two never share a candidate set.
